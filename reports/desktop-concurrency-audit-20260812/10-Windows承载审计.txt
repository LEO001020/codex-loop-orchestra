**事实**（本次验证）
1. 防护已失效：`hooks/desktop_spawn_guard.py`（旧版含 `DEFAULT_CAP=8`、`active>=cap` deny、8765 只读、fail-open 语义，证据保留在 `.pyc`/报告中）已被删除；`~/.codex/hooks.json`（描述行+SessionStart/SubagentStart）未注册任何 PreToolUse；`hooks/hooks.json.example` 亦无 spawn_guard 条目。当前 hard deny 实际已不存在。
2. 双平面聚合机制本机可用：8765 在跑，counts 合并 Desktop 原生与 headless（`harness/dispatch.py:182-185`）；headless 经 `codex exec` 承载（`dispatch.py:5-12`），每单 worker 一个独立进程。
3. 进程层证据：父进程树为 CLI `codex.exe`（本机会话），16 个原生子会话对应 16 个宿主进程句柄（本机观测分布在 4:46:34-45）；IAB 关联与 Desktop ptype=browser 崩溃迹来自用户背景陈述。
4. 策略十字严丝合缝：`config/orchestration_policy_v2.toml:183` `desktop_is_control_and_observation_plane=true`。

**漏洞**
- 硬上限已落空（无 hook 被动）：正确方案的本质不能用“删掉 hard deny”来填，否则 wind 回落到 16/16 原生之路径，重新诱发集中 IAB 路由与崩溃。
- guard 孤立化：cap 由 env/hook 持有，但调度器（`dispatch_v2.py:212-217`）自行判断 plane，二者无共享权威源，易错配。
- 8765 读取失败 fail-open，观测退化为唯一盲点即管控盲点。

**三方案对比**
- 8原生+8 headless：原生侧 IAB/IPC 压力减半，headless 隔离崩溃域；代价是 WSL/CLI 启动开销与 token 峰值爆发（治本仍靠流程）。
- 16原生：吞吐峰值等同但崩溃风险最高，违反 **v2.toml:183** 与 AGENTS.md“原生≤8”传输约束。
- 全 headless：崩溃风险最低，但 Desktop 退化为纯观察面，丧失 Desktop-native 任务类型兼容/调试闭环。

**最小修复**
1. 把 native cap 从 env 上提为权威配置（如 `orchestration_policy_v2.toml` 中 `native_cap = 8`），`dispatch_v2` 与 guard 同源读取。
2. 恢复 PreToolUse 注册 `hooks/desktop_spawn_guard.py`（从 `.pyc` 语义重建），超阈 deny 消息直接携带 headless fallback 指令（拒绝即决策而非死路）。
3. 8765 读取失败升级为告警阈值软门；防“盲点自由飞”。

事实/假设分界：进程双平面与配置字段已验证；conc 崩溃与 IAB 路由的因果链按用户背景作为**假设**采信，未独立重放。
