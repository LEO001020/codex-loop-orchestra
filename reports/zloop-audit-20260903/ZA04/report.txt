zloop backend codex_sdk.py Audit Report
======================================
Audit Scope: Thread pool lifecycle, submit/poll contract, concurrency limits, error/resource cleanup.

Findings:
1. ThreadPoolExecutor Lifecycle:
   The executor (size 16) is initialized in __init__ and shut down in close() using 'wait=False, cancel_futures=True'.
   - Issue: While cancel_futures=True attempts to cancel queued futures, it does not guarantee interruption of already running threads if the underlying SDK run() cannot be interrupted. The thread pool cleanup may not be graceful for currently active turns.

2. Submit/Poll Contract (Lazy Dispatch):
   The _ensure_dispatched method introduces a TOCTOU race condition in the poll() path:
   - File: codex_sdk.py, Line 129 (_ensure_dispatched)
   - Race Scenario: Concurrent poll() calls on the same launch_id (if allowed by supervisor) for a turn that has not yet started will both check _futures.get(launch_id) == None, thus simultaneously submitting the same run() task.
   - Concurrency Limit: The ThreadPoolExecutor(16) is correctly sized, but duplicate tasks for the same launch_id may consume 2 * 16=32 slots in the worst-case scenario.

3. Concurrency Limits:
   The ThreadPoolExecutor size of 16 seems appropriately bounded for the 8–15 concurrency noted in the docstring, but the actual limit might be bypassed by the race condition mentioned above.

4. Error/Resource Cleanup:
   - Rate limiting: Implementation includesjittered exponential backoff.
   - Resource cleanup: shutdown(wait=False) implies rapid exit; active threads might not fully release resources.

Recommendation:
1. Introduce a threading.Lock in CodexSdkBackend to protect _ensure_dispatched or the _futures dictionary access to prevent race conditions.
2. Consider using executor.shutdown(wait=True) if graceful cleanup is required, or ensure that the SDK object itself handles cancellations cleanly if wait=False must be used.
