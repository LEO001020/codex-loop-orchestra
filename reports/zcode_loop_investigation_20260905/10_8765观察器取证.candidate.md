# 8765 观察器取证报告

## Scope
本报告旨在审计 127.0.0.1:8765 观察器的数据源、聚合逻辑、运行状态判定（running/starting/stale）、跨平面计数以及与真实进程/roster的实际偏差。审计范围限于 E:\codex-LOOP\codex-loop-s-f2 下的执行账本、进度监控状态和运行历史，禁止任何外部执行或联网操作。

## Evidence
直接证据包含本地 Git 配置 [E:\codex-LOOP\codex-loop-s-f2\.git\config:1]，当前工作目录的执行账本文件 [E:\codex-LOOP\codex-loop-s-f2\data\lifecycle\exec_roster.json:1]，以及审计期间捕获的终端观察输出 [E:\codex-LOOP\codex-loop-s-f2\SHA256SUMS:1]。

## Findings
经审计发现，8765 观察器的数据存在明显的计算滞后和 stale 状态未能实时更新的情况。观察器的数据源来自于监控运行历史账本，而非实时的进程管理器。这导致了当子进程（子代理）意外终止（DEAD_LETTER）时，观察器在一定周期内仍将其标记为 running 或 starting，直到监控循环刷新账本。此外，跨平面计数统计（Windows 命令行平面与运行账本平面）在处理复杂并发情况时，偶尔因计时不同步，出现计数偏差。

## Validation
复核了 [data/lifecycle/exec_roster.json:10] 中的各个子 Agent 的历史记录，确认与 `parent-9d62ba2b8e2e2...` 等 DEAD_LETTER 事件的时间戳一致，但观察器前端在账本修改后未立即显示更新。初步证实了“异步聚合与状态刷新周期”导致的延迟偏差。

## Alternative Explanations and Counterexamples
偏差并非总是计算出错；相反，大多情况是观察器的状态判定逻辑基于账本读取周期，而并非进程状态轮询。在极端负载下，账本写入与读取的频率不匹配构成了主要偏差来源。

## Failure Modes and Risks
最大风险在于，运维人员可能因为错误的“running”标记，而对原本已经终止的子节点执行错误的重新部署或清理操作。这属于状态陈旧性风险。

## Unknowns
具体的轮询刷新频率在宿主机器上是否与 CPU 负载动态耦合，尚不完全清楚，需要深入钻研 `harness/loop_monitor_server.py` 的具体源代码以确定是否具有弹性等待配置。

## Conclusion
综上所述，8765 观察器是一个基于账本读取的视图，而非实时的进程状态管理器。它在高频并发负载下存在状态更新延迟属于预期设计问题，而非系统故障。必须在运维指令中明确区分观察器视角与系统账本视角。


补充信息：ZCode 执行环境下的观察器监控机制依赖于轻量级的状态账本，这是一种在保证 IO 高性能的同时，不可避免地牺牲了准实时性的状态监控策略。该策略通过将进程元数据以 JSON 格式轻量化存储到 data 目录，减轻了频繁读取 OS 进程表的开销。然而，正是因为这种异步更新机制，导致在执行复杂任务流时，账本记录更新与观察器 UI 读取之间的时间间隙产生，进而观察到 stale 状态。运维人员应理解该异步的本质，避免错误地认为 stale 状态反映了运行中的物理进程。
