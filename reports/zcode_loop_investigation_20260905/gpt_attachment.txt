# R8 FINAL 方案独立审计结论

**总判定：R8 的大方向能真实适配 ZCode，但不能直接作为施工规范。** 它对 ZCode 宿主契约的核心声明约七成成立且比上一版显著更准（hook 事件、matcher、transcript_path、插件 MCP 声明方式全部对得上），但它引用的续接机制 /goal 在本机 ZCode 3.11.2 中**根本不存在**，injectAgentsMd 字段在 CLI 中**不存在**，"v3.7.1"版本史**无从考证**；另外它要重建的“真实 checkout”实际有两个候选且其一带 44 个未提交文件，方案自身对此没有消歧。还有一点必须先说明：你贴给我的 R8 文本在 §26「Windows K runtime」中途截断（停在"Jupyter Z"），MCP 生命周期、oracle、E2E 等后半部分我审不到。

## 一、致命/高优先级事实错误（3 项，均已亲测复核）

**1. /goal 命令不存在 —— 致命。** R8 §4 把“数小时任务推荐 /goal <objective> + /zloop”、"/goal 负责跨 round 的继续和自己的完成判断”作为整个续接模型的前提。我在整个 C:\Users\hzq00\.zcode（commands、skills、插件缓存、CLI 内置）检索 goal，**零命中**。本机可用的续接原语其实只有官方文档明确的：Stop hook “可请求 continuation（最多 3 次）"。R8 又明文禁止 Stop 无限续接循环——两件事叠加后，R8 的跨 round 续接故事**没有任何宿主机制承载**，这是全案最大缺口，必须在施工前改为：自定义 command + 会话内多轮、或明确接受 3 次 continuation 上限。

**2. injectAgentsMd 字段不存在。** 全 CLI 内容 grep 零命中。R8 §7 要求 zloop-worker.md frontmatter 写 injectAgentsMd: true——该字段会被忽略。AGENTS.md 注入是宿主默认行为（本会话本身就是证据），无需也不能声明。顺带发现：现有 zloop-gen8\plugin\agents\zloop-worker.md 的 frontmatter 里已经写着这个幻觉字段（还有 	houghtLevel: max、maxTurns: 128），R8 把存量错误原样继承了下来。

**3. "v3.7.1 起 subagent 注入 AGENTS.md”版本史不可信。** 本机实际版本是 **3.11.2**（ZCode.exe PE 版本 3.11.2.6792），无任何 changelog 佐证 3.7.1 这个里程碑。机制本身真实，但施工不应硬编码版本判断。另外“tools:'*' 时继承 primary session 的 MCP”我只找到间接证据，标 PARTIAL——这直接影响 R8“packet 不必重复 MCP 清单”的假设，施工时应实测一个 subagent 能否看到 zloop-code。

## 二、验证成立的关键声明（可放心施工）

- **Hook 契约全部对得上**：官方文档确认恰好七种事件（SessionStart/UserPromptSubmit/PreToolUse/PermissionRequest/PostToolUse/PostToolUseFailure/Stop）；SessionStart 触发源含 startup/clear/compact（还有 R8 漏写的 esume）；PostToolUse matcher 按工具名正则匹配，写 "Agent" 正确（Task↔Agent 别名存在）；hook stdin 确有 	ranscript_path/session_id/cwd——R8 §16 的 transcript 增量捕获在输入侧可行。
- **一处施工级修正**：SessionStart 注入不能像 R8 §15 那样裸文本 stdout——官方 schema 是严格 JSON，**必须输出 {"additionalContext": "..."}**，多余字段直接校验失败；诊断走 stderr、退出码 0/2/其它 的语义与 R8 的 fail-soft 设计兼容。现有 gen8 插件用 	ype:"process" + ${ZCODE_PLUGIN_ROOT} 的形状是官方推荐且可跨平台的，R8 未写明，照抄现有 hooks.json 即可。
- **插件形状成立**：.zcode-plugin/plugin.json + 根级 .mcp.json（android-emulator 实例确认 stdio server 字段形状与 ${CLAUDE_PLUGIN_ROOT} 插值可用）。
- **Windows 运行时前提成立且有本机实测背书**：本机 Python 3.14.3 默认 ProactorEventLoop，R8“不要全局 SelectorEventLoopPolicy、Jupyter 用独立 owner thread + BlockingKernelClient”的判断方向正确。但注意**本机当前完全没装 jupyter 栈**（无 ipykernel/jupyter_client/mcp/pyzmq），K 平面要从零安装。
- **上游版本声明全部属实**：PyPI 实测 ipykernel 7.3.0（2026-06-10）、6.31.0 存在、jupyter_client 8.10.0 为最新且无 9.x、mcp 2.1.1（2026-08-25，描述明言 "major rework"）。R8 的"7.3.x 优先 + conformance gate + 6.31.x 回退”策略有事实基础——唯一保留意见是 Python 3.14 × ipykernel 7.3 的组合本身就要过 conformance 才知道。
- **Git 机制成立**：本机 git 2.55.0.windows.3，merge-tree --write-tree、三种 clone 变体、cat-file -e 全部可用。clone-seed 的一个隐患比 R8 担心的小：实测本地路径 fetch 一个“不在 ref 尖端但可达”的 sha 是成功的（只有完全 unreachable 的对象才报 
ot our ref）；而 base_oid 永远等于 run ref 尖端，所以按 refspec（efs/heads/zloop/run/<id>）fetch 就绝对安全——建议 R8 把 seed 刷新明确写成 fetch ref 而非裸 sha。

## 三、对“真实 checkout”的指认歧义（R8 §5 无法按原文执行）

E:\zcode 本身不是 git 仓库，下面有三个候选：zcode-loop-orchestra（干净、9/3 最新提交、plugin 只有 hooks）、codex-loop-orchestra（另一项目）、zloop-gen8（9/4 最新提交、**44 个未提交文件、领先远端 13 个 commit、挂着约 16 个 worktree**、plugin 完整含 commands/agents）。两仓的 src/zloop/ 各约 6300/7000 行，R8 删除清单命中真实代码：db.py（SQLite 确认在用，R8“不使用 SQLite"的删除目标真实存在）、stage.py、wave.py、supervisor.py、promote.py、ackend/zcode_native.py、esearch/broker.py（仅 gen8）。R8 自己规定“不得盲删未知用户数据、不 reset/stash"——那么施工方第一个问题就是：**R8 没说重建落在哪个仓**。gen8 的 44 个未提交文件按 R8 自己的规则一个都不能动。另外两仓 	ests/ 实际是零测试函数，R8 §5 要求“跑当前测试并报告 collected/passed"会得到空集，“旧系统测试基线”这根安全网实际不存在。
