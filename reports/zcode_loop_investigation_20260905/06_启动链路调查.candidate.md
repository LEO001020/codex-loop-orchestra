《任务：在可能性潜空间中进行极其广泛但证据驱动的架构搜索，为下述已确定的异构模型矩阵寻找最能释放其并行推理与执行能力的 Pi Agent Loop production candidate，并亲手在沙盒中完成该 Pi Agent + Loop 的全部必要实现，最终交付完整、可安装、可启动、可实际使用、包含 desktop/UI 使用形态的 Pi Agent Loop。

不要只交付 architecture proposal、伪代码、局部 demo 或 skeleton。同时不得宣称已证明"全局最优"——最终方案应表述为：在已审计证据、当前 Pi runtime、当前模型矩阵与工程约束下，找到的最强 production candidate。》

一切围绕 LLM 推理能力与用户使用：harness 是为了 loop，loop 是为了 LLM——harness 与 loop 都是以 LLM 为中心的铺路，乃是为了最大化发挥 LLM 集群对可能性潜空间的最大探索的推理性能！

〇、本任务最稀缺的资源：信息与推理——二者是一件事；而理解本身是诠释学循环

这个任务最大的瓶颈不是工程，而是信息与推理：我们需要更多的推理来探索可能性潜空间，而更多的推理只能由更多的信息带来——没有新信息灌入，再强的模型也只是在一个贫瘠的语境里空转。信息获取就是推理能力本身的扩张。

资源层级与分工：
- 论文是感知（双眼）：系统化沉淀了"什么机制在什么条件下有效/无效"。它回答"该建什么、为什么这样建"。注意：论文在方向问题上最权威，但它不能回答"某个库当前版本提供什么 API"——那是源码的事（见"证据制度"一节）；
- GitHub 社区是双手（身体）：找到对应好问题/好论文的最佳开源项目，直接采用或仅做小幅调整，通常是时间成本最优的路径；从零重写一个已有良好实现的东西，默认是错误，除非你给出采纳不可行的具体理由（license、能力缺口、已审计的缺陷）；
- 好架构是大脑（神经）：神经发育学的第一原则，是先感知世界、再在与世界的反馈中发育。寻找好架构的同义词，就是"好论文 + 对应好论文的好 GitHub 项目"——Pi 生态自身的 extensions、pi-subagents、现成 GUI 包，都是"现成的手"的第一候选。

推论：当你发现自己在凭空设计一个组件时，先停下来——这个组件大概率已存在于某篇论文的 mechanism 或某个 GitHub 项目的实现里。第一动作永远是检索，第二动作才是设计。这条原则与"如无必要勿增实体"是同一件事的两面：采纳现成的，就是在不增实体的前提下获得能力。

更深一层：整个理解活动是诠释学循环。要懂整体（完整的 pi agent loop 架构），你必须先懂每一个部分（单篇论文、单个组件、单个机制）；而要真正懂每一个部分，你又必须先把它放回整体中去读——同一篇论文在不同的候选架构语境下会呈现出不同的意义。所以不要期待"先读完再动手"或"先动手再补读"的线性路线：局部阅读改变你对整体的设计判断，整体的设计判断又决定你下一轮深读哪些局部。这个循环不是缺陷，是机制本身——每一轮循环都让整体与局部同时变得更清晰。

【既定部署格局——用户已确定的物质基础，不是设计选项】

- GLM-5.3：单实例。深度推理、复杂规划、最终仲裁。
- Gemini 3.8 Flash：并发执行层，固定 10-20 并发（执行任务时下限 10 并发，通常维持该规模，无需更改此格局）。该模型 TPS 极高、费用极低，就是为吃量而生。
- GLM-5.3 Flash：1-8 并发，轻量快响应。不限于审计——可承担 selector、轻量协调、格式校验、快速复核等一切适合它的角色。

用户有多轮 loop 使用经验，此格局经过实践校准。其中"GLM-5.3 单实例 / Gemini 3.8 Flash 10-20 并发（执行任务时下限 10，作为运行基线）/ GLM-5.3-Flash 1-8 并发不限于审计"这三条资源规格是既定的；"格局"一词仅指这些资源规格，不冻结架构与角色问题。你的任务不是论证这个格局、也不是调整并发规模，而是在格局之内做出最好的架构。这意味着三个核心工程挑战必须被你的架构回答（注意：它们指出问题领域，不预设解法——解法由你的研究与推理决定）：

1. 不互相挤压——并发子 agent 不得在文件写入、工作区状态、任务边界上互相冲突踩踏；
2. 遏制错误传播——执行层模型推理能力弱于 GLM-5.3，其错误输出不得静默流向下游污染后续轮次；
3. 完成任务 ≠ 追求速度——返工是最大的敌人。一次草率的并发产出引发的来回返工，比慢而正确代价高得多。

除并发执行层外的角色-模型绑定是开放问题，由你基于证据裁决：owner/manager 用 GLM-5.3 还是与审计角色合并？auditor 用 GLM-5.3-Flash 还是 GLM-5.3 降频兼任？selector 需要独立角色吗？Gemini 能否承担部分轻规划？——这些只是我们想到的一部分，你的研究可能发现更多必须裁决的绑定问题。给出你的论证。

学术层面的改进（multi-agent 协作范式、graph engineering、聚合协议等）是允许且 encouraged 的，但须满足两条：有明确的 LLM 推理性能收益论证；遵循"如无必要，勿增实体"。

一、核心优化目标

所有研究、删减、架构和实现决策围绕一个中心：Harness 是为了 Loop，Loop 是为了 LLM 集群。

不要优化：agent 数量、系统组件数量、论文数量、代码行数、抽象层数量、prompt 长度、架构"漂亮程度"本身。

真正优化：verified task success，并同时考虑 total model/tool cost、latency、context efficiency、user friction、recoverability、long-horizon continuity、false-completion risk、implementation complexity。

在本格局下，并发规模已定，竞争的维度在质量：如何让海量并发的产出保持正确性、如何让聚合与验证拦截弱模型的错误、如何把返工率压到最低——这些是留给你的架构去回答的核心命题。

二、哪些东西可以推翻，哪些不能混淆

下面是历史方案，仅作为已经探索过的候选点，不是 architecture requirement：

PI-LOOP 曾被设想为 Pi Core runtime 之上，由 Manager 主控循环通过 pi-subagents 调度 RECON、EXEC、AUDIT 三类子代理，借助 pi-repl-py 执行 Python，并以 TaskState 持久化长程状态。这一角色拓扑、agent 数量、manager/executor/auditor 划分、memory representation、delegation policy、desktop 形态等全部可以推翻。附件中其他 agent 的探索也全部只是 hypothesis，不是要求。

但是：Pi 是本项目的平台。

历史研究曾基于源码审计建议：不要重新实现 provider runtime、model API loop、native session runtime、tool runtime、conversation transcript、compaction/session 机制、child-agent lifecycle 等实体（注：该清单针对特定上游版本，child-agent lifecycle 等部分可能存在于独立 package 而非 Pi core）。此建议方向可作初始参考，但须由你对当前实际安装版本重新做源码审计后裁决。同理，如果 pi-subagents、Pi RPC、现成 GUI/desktop、MCP、已有 package 已经提供需要的能力，优先复用。

不要为了"架构完整"重新创造：second agent framework、second provider framework、second transcript database、second task database、generic scheduler、generic model registry、worker farm、巨大 memory service。如果最终新增任何此类重型实体，必须给出：哪项用户需求或实验事实要求它存在；为什么现有 Pi/upstream primitive 不能完成；删除它后会产生什么可观测退化。答不出来则删除。该原则的一个正面表述是：优先采纳与小幅调整社区已验证的最佳实现（见〇节），三问义务只针对"新增重型实体"，不针对"采纳现成轮子"。

三、证据制度：科学问题与实现问题必须分开

不要使用单一证据等级处理所有问题。

A. 判断"某种机制是否可能提高 agent 能力"时，可从以下初始证据框架出发（排序本身是方法论假设，允许你的研究修正它）：peer-reviewed paper / original arXiv paper → 原始 benchmark 与实验材料 → 多篇独立论文的交叉证据 → AI 厂商公开工程研究 → GitHub implementation → issue / discussion / blog / anecdote。论文主要回答：为什么某个机制可能有效，以及它在什么实验条件下有效。所有 paper claim 必须阅读原文，而不是只读取搜索摘要。必须记录 limitation、backbone、benchmark、budget、是否存在训练、是否同 backbone、是否真正 causal ablation。

B. 判断"当前软件真实提供什么能力"时，证据权重一般随"离实际运行源码越近越可靠"排列（初始框架，可按场景修正）：当前沙盒实际安装源码 / types / lockfile / package metadata → 当前项目 pin 的 upstream commit/release → upstream 官方源码 → upstream 官方文档 → paper → README → issue/discussion → 模型记忆。源码和 runtime 才能证明：当前 API 到底存在什么、参数是什么、事件何时发生、状态如何改变。论文不能替代这一事实。

四、论文研究要求

极其大量搜索和阅读相关论文。最低要求：至少 200 篇去重的 original papers，但禁止用"快速读取 200 个 abstract"完成指标。

至少建立 durable reading ledger，记录：paper title、canonical identifier、研究领域、阅读的原文部分、核心 mechanism、主要实验、关键 quantitative result、能支持什么、不能支持什么、对 Pi Loop 的 design implication、external-validity limitation。

核心 architecture-changing papers 应深入原文阅读；外围论文允许针对 method、experiment、ablation、limitations 定向原文阅读。阅读顺序本身应服从诠释学循环：先泛读建立整体地图，再按当前候选架构的需要深读局部，候选架构的演化反过来指引下一轮阅读——不要按固定清单机械顺读。

重点研究领域包括但不限于：agent loop、agent-computer interface、long-horizon agents、context management、memory、programmatic memory、context compression、context rot、retrieval、repository navigation、tool use、planning、adaptive planning、test-time scaling、multi-agent coordination、multi-agent failure analysis、single-agent baseline、delegation、verification、independent patch verification、candidate selection、false completion、self-correction、error propagation、model routing、harness optimization、persistent execution environment、coding agents、desktop/local agent UX。这些领域只是此前探索的地图，不是边界。

尤其主动寻找：反对当前候选架构的论文和负面结果（例如 multi-agent 通信冗余、coordination 开销、selection bottleneck、弱模型错误级联等已有实证线索），不要只积累支持材料。如果某一机制只有一篇论文支持，默认应标注 weak / preliminary evidence（除非你论证该领域单篇证据的效力本就很高）。如果论文之间实验设置不可比，不要简单按 benchmark number 排名。

五、研究必须探索真正不同的 architecture families

不要围绕旧 PI-LOOP 做局部微调。主动产生并比较彼此真正不同的 candidate families——此前探索中出现过的方向（如 manager/executor 分层与并发 fan-out、episode-based context separation、programmatic history、Codex-style recoverable windows、summary-compaction、adaptive memory controller、multi-agent search with late fusion、conditional delegation、map-reduce 分解聚合、错误隔离与重试拓扑、强单 agent 对照等）仅是已知样本，你应从中超越并发现新的 families。

候选之间必须存在真正的结构差异，而不仅是"10 个并发 vs 20 个并发"。每个 major candidate 应携带一份你自己设计的评估框架，说明其结构特征、成本结构、适用边界与失败模式——具体维度由你的研究决定，不必套用既有模板。

六、并发不是目的，质量才是——聚合层与错误遏制是已知的关键战场

Gemini 层的并发价值在于：并行覆盖可能性空间、并行完成可分解工作量、生成多候选供选择。但弱模型并发有一个结构性风险：错误产出的传播与扩散。此前研究在此处留下过一些已知的战役地图（fan-in 时 complementary observations 与 competing solutions 的区分、selection bottleneck、错误传播链的斩断、并发重复劳动与资源挤压、哪些阶段适合 fan-out 哪些必须收拢到深推理串行）——它们值得你研究，但不是答案，也不是完整的问题清单。你在自己的架构中发现的新战场，同样必须被设计覆盖。

返工是最大的敌人：一次草率的并发产出引发的返工循环，代价远高于慢而正确。聚合层与验证层的核心 KPI 是降低返工率，而不仅是吞吐。"10-20 并发（执行下限 10）"是运行基线而非架构结论：如果证据表明某类任务阶段在基线并发下不划算，如实报告并给出你的运行建议——但资源规格本身不在本次改动范围内。

七、极简主义原则

遵循：如无必要，勿增实体。但必须区分"系统摩擦"与"correctness semantics"。

大胆删除：重复 wrapper、重复 state、重复 prompt translation、低价值 planning stage、无证据的 agent role、无必要的 broker、重复 confirmation、第二套抽象层、无法证明收益的 vector DB / graph DB / scheduler / ontology。

另有一类条目曾被上一轮研究归纳为"可能承载正确性语义"——例如 task identity、task revision/generation、candidate/workspace identity、writer ownership、stale-result rejection、cancellation semantics、artifact/evidence references、session replacement correctness、bounded state recovery、credential/workspace containment。这份清单只是先前探索的归纳示例，不是权威定论：哪些条目真正承载正确性语义、是否还存在清单之外的同类似项，须由你自己的研究重新推导与裁决。删除其中任何一条前，先证明另一 primitive 已提供相同 invariant；发现清单本身有误（多列了或漏列了），在 DEVIATIONS 中记录。

八、安全与权限的原则

不要构建重型 security framework，不要为理论上的长尾攻击牺牲主要 agent loop 的可用性。但也不要删除能直接防止以下情况的最小边界：用户数据被错误覆盖、credential 泄漏、任务取消后旧结果继续写入、stale patch 覆盖新 workspace、多个 writer 互相破坏（在大规模并发 agent 场景下，writer ownership 与 workspace 隔离是最现实的正确性风险之一）。目标是 minimum sufficient safety/correctness boundary，而不是 zero safety。在沙盒内允许 agent 高自由度执行任务，但 workspace scope、credential scope 和 destructive operation 的作用域必须明确。

九、沙盒环境契约——MCP 是传输和执行基础设施

通过 MCP 你可以：git clone 任意仓库；npm/pip 安装 package；执行 shell command 并获取真实 stdout/stderr/exit code；读写文件；在沙盒与外部之间传文件。

沙盒限制：无 root、无 systemd、无图形显示。如需 Node 22+，用无 root 的用户级安装方式解决（如官方 tarball 解压至用户目录或等效方案）。

可以克隆研究所需 GitHub repository 到沙盒中进行源码级审计。不要根据 README 猜测 API；能读源码就读源码。

十、Desktop / GUI

最终产品必须包含实际可使用的 desktop / GUI / TUI 形态。候选包括 Pi 自带 TUI、Pi RPC + thin desktop/web UI、社区现成实现，或经源码审计后你发现的其他更优 existing implementation——由你研究后自行选择。

方向性原则（可被证据推翻）：desktop 倾向于不拥有第二套 agent runtime 或第二套 task truth，优先让 GUI 成为同一 Pi backend 的 presentation/control surface。GUI 应能呈现并发 agent 集群的运行状态（哪些在跑、进度、fan-in 结果、返工标记）——如何呈现由你设计。

沙盒无图形环境不是删除 GUI 的理由。若 GUI 无法在沙盒完成视觉启动验证：仍必须完整实现、安装和配置，并在交付附录写明：宿主机 dependency、启动命令、首次配置步骤、哪些步骤未在 sandbox 中真实验证。不得声称未执行的 GUI 验证已经成功。

十一、真实模型调用

本任务矩阵的接入条件用户已具备：GLM-5.3 / GLM-5.3-Flash 经 OpenAI 兼容中转接入，Gemini 3.8 Flash 经本地代理接入（均为 OpenAI 兼容协议）。开工时列一份凭据需求清单（provider、credential 格式、key 文件应放的路径），用户会把凭据文件放进沙盒。

拿到凭据前：将相应 integration verification 标为 BLOCKED_CREDENTIAL，继续完成所有不需要 key 的工作（代码、配置、扩展、脚手架全都可以先建）。不要空等，不要伪造成功结果。

十二、实现阶段

研究与实现的关系由你自主编排——可以交错、可以并行、可以先建后读、也可以边读边推翻，任何节律都合法，唯一的硬约束是：最终交付必须完整、可运行、有真实运行证据；重大架构决策必须有你引用的研究证据支撑（证据标准见第三节）。

过程参考（仅为先前一轮工作使用过的节拍样本，不是推荐路线）：早期读取核心论文 + audit 当前 Pi ecosystem → 形成多个 candidate architecture → 验证 package/runtime seam → 扩大论文阅读至至少 200 篇 → 随证据删掉 candidate → 冻结 production architecture → 完整实现 → 最小必要运行验证（凭据到位后做真实多 agent fan-out smoke）→ 打包。

任何时候，如果新的原始证据推翻旧 architecture，应允许重构。不要因为已经写了代码而保护错误设计。

十三、测试与验证

本任务不要求建设独立、庞大的"测试组件"或额外 Test Agent Framework。但"完整可运行"必须通过真实运行证据支持。至少对能在当前环境中运行的部分提供真实运行证据（证据形态由你的架构决定，以下仅为常见示例）：install/build smoke check；CLI/runtime startup check；主要 loop vertical-slice check；child/delegation path check；persistence/resume path check（如果设计包含）；packaged artifact startup check。

记录真实：command、stdout、stderr、exit code、environment/version。不要为测试建立第二套复杂系统，优先使用现有 repository test/build/smoke facilities。任何未验证的功能必须明确标 UNVERIFIED，而不是写成成功。

十四、不得以"安全"为理由避免真正实现

除非当前环境或上游 API 确实不允许，不要只写 architecture proposal。你需要亲自在 sandbox：clone、install、inspect、write、modify、execute、package，最终产生真实代码。不得把主要实现工作推给"未来本地 agent"。"宿主机代执行"只适用于当前 sandbox 客观无法执行的步骤，例如真正 GUI display 或用户凭据相关验证。

十五、workspace 根目录中 0. 开头的目录（如存在）属于上一轮 archive，与本次实现无关，不得无意修改。

十六、最终交付

所有最终 production code 放入一个自包含目录。不得把临时 clone、论文 corpus、research cache、build garbage 混进生产包。
