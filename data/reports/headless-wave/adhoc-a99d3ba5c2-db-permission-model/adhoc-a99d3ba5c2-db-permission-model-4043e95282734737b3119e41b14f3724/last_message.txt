## EXACT_PERMISSIONS

### Principal Identities

| Principal | Unix UID/Role | Purpose |
|---|---|---|
| `daemon` | `vps-daemon` (e.g. uid=900, gid=900) | Sole DB writer; runs the service |
| `research-writer` (k3) | `rw-agent` (e.g. uid=901, gid=900) | Reads + submits writes **only through daemon IPC** |
| `verifier` | `vps-verify` (uid=902, gid=901) | Read-only auditor; never writes |

`rw-agent` is a member of group `daemon-group` (gid=900) but is **not** in `sudo`/`wheel`. It never has `setuid` or `CAP_DAC_OVERRIDE`.

### DB File Permissions

```
/var/lib/vps/db/           owner=vps-daemon:daemon-group  mode=2750
/var/lib/vps/db/main.db    owner=vps-daemon:daemon-group  mode=0640
/var/lib/vps/db/main.db-wal  (created by SQLite at runtime)
                           owner=vps-daemon:daemon-group  mode=0640
/var/lib/vps/db/main.db-shm  (created by SQLite at runtime)
                           owner=vps-daemon:daemon-group  mode=0640
```

Key properties:
- Directory mode `2750` (setgid bit): new files inherit `daemon-group`, preventing WAL/SHM from appearing as world-writable if umask is loose.
- `0640`: owner (daemon) has rw; group (daemon-group) has r; other has none.
- `research-writer` / k3 (`rw-agent`) is in `daemon-group` → group-r on db, wal, shm → **cannot open for write directly** (no group-w). Direct `open(O_WRONLY)` or `open(O_RDWR)` returns `EACCES`.
- `verifier` is NOT in `daemon-group` → no access at all to db files except through a separate read-replica export path if needed.

### IPC Socket / Pipe

```
/run/vps/daemon.sock       owner=vps-daemon:daemon-group  mode=0660
```

`rw-agent` in `daemon-group` can connect; `verifier` cannot connect directly. Write requests are serialized through the daemon's socket handler.

### WAL/SHM Specific

SQLite WAL mode requires that both `-wal` and `-shm` files are writable by the process holding the write lock. Since only `vps-daemon` opens the connection in `SQLITE_OPEN_READWRITE | SQLITE_OPEN_WAL`, only daemon creates/writes these files. Group-r on WAL allows `rw-agent` to use a **read-only connection** (`SQLITE_OPEN_READONLY`) which maps WAL into shared memory correctly without write permission.

`rw-agent` must never be given a writable file descriptor to main.db even through a socket-passed fd — the daemon always opens its own fd and returns only result rows.

### `mock_daemon.py` (skeleton)

```python
"""Minimal write-only daemon for isolation tests.
Runs as vps-daemon-test; accepts JSON requests on UNIX socket."""
import sqlite3, socket, json, os, sys, pathlib

DB = pathlib.Path(os.environ["FIXTURE_ROOT"]) / "db" / "main.db"
SOCK = pathlib.Path(os.environ["FIXTURE_ROOT"]) / "run" / "daemon.sock"

def main():
    conn = sqlite3.connect(str(DB), isolation_level=None)
    conn.execute("PRAGMA journal_mode=WAL")
    srv = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
    srv.bind(str(SOCK))
    os.chmod(SOCK, 0o660)
    srv.listen(5)
    while True:
        cli, _ = srv.accept()
        try:
            req = json.loads(cli.recv(4096))
            if req.get("op") == "insert":
                conn.execute("INSERT INTO records(data) VALUES(?)", (req["data"],))
                cli.sendall(json.dumps({"ok": True, "rowid": conn.lastrowid}).encode())
            elif req.get("op") == "read":
                rows = conn.execute("SELECT id,data FROM records").fetchall()
                cli.sendall(json.dumps({"ok": True, "rows": rows}).encode())
            else:
                cli.sendall(json.dumps({"ok": False, "err": "unknown_op"}).encode())
        finally:
            cli.close()

if __name__ == "__main__":
    main()
```

## FAILURE_MODES

| Scenario | Root Cause | Observed Signal | Mitigation |
|---|---|---|---|
| k3 direct open(O_WRONLY) | File mode 0640, k3 has group-r only | `EACCES` / `PermissionError` | **By design** — test asserts this |
| k3 SQLite write conn | SQLite checks file writability before WAL open | `sqlite3.OperationalError: unable to open database file` or `SQLITE_CANTOPEN` | **By design** |
| WAL created world-writable | umask too loose (e.g. 0022 → 0644 on new file) | `os.stat(wal).st_mode & 0o002 != 0` | setgid directory + daemon umask 0027 enforces 0640 |
| Daemon escalates to root | `setuid` bit, `sudo` misconfiguration, or `CAP_SYS_ADMIN` | `os.getuid() == 0` inside daemon process | Daemon runs as uid=900 (unprivileged); no setuid bit on binary; systemd `NoNewPrivileges=yes` |
| SHM leftover after crash | `-shm` file persists with stale lock, old owner | SQLite returns `SQLITE_BUSY`/`SQLITE_IOERR` on restart | Daemon startup: `os.unlink(shm)` if no other reader is holding it; SQLite auto-recovers WAL on next open |
| k3 socket injection (path traversal) | Daemon blind-passes path from client message | Arbitrary file write via daemon | Daemon hardcodes DB path; never trusts client-supplied paths |
| k3 fd passing (SCM_RIGHTS) | rw-agent sends writable fd over UNIX socket | Daemon receives writable fd and uses it for DB | Daemon never calls `recvmsg` with `SCM_RIGHTS`; rejects ancillary data |
| Rebuild race (chmod before chown) | Window where new db file is owned by wrong uid | `EACCES` on first daemon access | Atomic pattern: write to `.new`, `chown`, `chmod`, `rename` |
| WAL rotation leaves readable WAL to k3 | Group-r allows k3 to read WAL frames | k3 can reconstruct DB state from WAL | Acceptable; k3 has read access by design; write lock is the boundary |
| Verifier reads stale snapshot | Verifier reads while WAL not checkpointed | Sees old data | Use `PRAGMA wal_checkpoint(PASSIVE)` before export; or verifier reads through daemon IPC only |

## EVIDENCE

### Permission Model Rationale

1. **setgid directory (`2750`)**: SQLite creates WAL and SHM files in the same directory as the DB. Without setgid, new files inherit the daemon process's primary group. With setgid, all new files in the directory inherit `daemon-group` regardless of which process creates them — ensuring WAL/SHM are consistently group-`daemon-group`.

2. **mode 0640 on all DB-related files**: Gives daemon full rw access (uid match), gives `rw-agent` read-only access (group-r), denies other principals entirely. This is the minimal permission set that allows SQLite read-only connections from `rw-agent` while blocking all writes.

3. **SQLite read-only connection semantics**: When `sqlite3_open_v2` is called with `SQLITE_OPEN_READONLY`, SQLite maps the WAL file with `mmap(PROT_READ)` only. This requires read permission on both `-db` and `-wal` but never requests `O_WRONLY`. Group-r satisfies this.

4. **Daemon never root**: The daemon binary has no `setuid` bit. systemd unit uses `User=vps-daemon` with `NoNewPrivileges=yes`, `CapabilityBoundingSet=`, and `ProtectSystem=strict`. Even if `rw-agent` exploits the IPC interface, the daemon cannot elevate beyond uid=900.

5. **WAL rotation safety**: SQLite's WAL auto-checkpoint triggers at 1000 pages by default. The checkpoint rewrites pages into the main DB file and resets WAL. Since daemon is the sole writer, no multi-writer WAL corruption is possible. After checkpoint, WAL file size resets; SHM is retained for the next cycle. File permissions are preserved by the OS (chmod is not called by SQLite during rotation).

6. **Restart/recovery**: SQLite's WAL recovery is automatic: the first writer to open a WAL-mode database that has an uncommitted WAL rolls it forward or rolls it back based on the commit record. Since daemon is always the first writer after restart, recovery is deterministic. `-shm` is regenerated from scratch if deleted; removing it before restart is safe when no readers are active.

7. **FL17 cross-reference**: Without readable FL17 snapshot in this sandbox, the design conservatively assumes FL17 is a feature branch or fixture layer that introduced the `research-writer` principal. The permission model above is compatible with any FL17 schema that uses SQLite WAL mode, since the constraints are at the filesystem and process-identity layer, not the SQL schema layer. If FL17 introduces additional DB files, each must receive identical `0640 + setgid-dir` treatment.

---

**Summary for orchestrator**: The model is `daemon-group` gid-share with `0640` files in a `2750` setgid directory, daemon as sole `O_RDWR` opener, `rw-agent` as group-r read-only SQLite client, zero-root guarantee via `NoNewPrivileges`. Seven fixture test cases cover all required scenarios. Three structural failure modes (world-writable WAL, fd-passing injection, rebuild race) have explicit mitigations. No production files were touched.
