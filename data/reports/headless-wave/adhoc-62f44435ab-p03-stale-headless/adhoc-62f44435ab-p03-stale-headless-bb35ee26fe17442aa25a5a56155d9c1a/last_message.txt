# p03: exec_roster → stale_headless

结论：`stale_headless` 不是 `exec_roster.json` 的持久 state；8765 观察器在 snapshot 时把过期 `starting`/`running` 行重分类为 `stale_headless`。心跳阈值是 **30 秒**（`max(heartbeat_at, updated_at)`，缺省或 ≤0 立即 stale）。重分类后 **不计入** `counts.running` 和 `planes.headless`，只计入 `counts.stale_headless`，且不进入 `tasks`。

## 1. durable roster 写什么

写者：`harness/lifecycle_supervisor.py` → `Store.update()` → `data/lifecycle/exec_roster.json`。

- schema：`codex-loop-exec-roster/v2`，按 `packet_id` 存 `jobs`。
- 活着的 durable state 只有 `starting` / `running`（外加终端态 `completed|failed|timed_out|cancelled|spawn_failed`）。代码里 **没有** 把 `stale_headless` 写回 roster。
- 初始登记：`state="starting"`，带 `started_at`；`Store.update()` 每次都会写 `updated_at=time.time()`。
- 子进程起来后：`state="running"`，第一次写 `heartbeat_at=time.time()`。
- 之后每 `HEARTBEAT_INTERVAL_S = 10.0` 秒再写一次 `state="running", heartbeat_at=time.time()`。

证据：

- `E:\codex-LOOP\codex-loop-s-f2\harness\lifecycle_supervisor.py:32` `HEARTBEAT_INTERVAL_S = 10.0`
- `:135` `self.roster_path = ... / "exec_roster.json"`
- `:187` `item["updated_at"] = time.time()`
- `:627-654` 先 `state="starting"`，spawn 成功后 `state="running"` + `heartbeat_at=time.time()`
- `:698-701` `if time.monotonic() - heartbeat_at >= HEARTBEAT_INTERVAL_S: store.update(..., state="running", heartbeat_at=time.time())`

`headless_wave.py` 只在恢复“进程仍活但 roster 已非 ACTIVE”时补一次 `state="running", heartbeat_at=time.time()`；`ACTIVE = {"starting", "running"}`。它也不写 `stale_headless`。

## 2. 观察器如何变成 stale_headless

实现：`E:\codex-LOOP\launchers\loop_monitor_server.py` 的 `snapshot()`，不是 supervisor。

加载：

```
exec_roster = merge_exec_rosters(
    read_json(lifecycle / "exec_roster.json", {}),          # --root / WSL peer
    read_json(windows_root / "data" / "lifecycle" / "exec_roster.json", {}),
)
```

合并规则（`merge_exec_rosters`，约 L267-294）：同一 `packet_id` 取 `max(updated_at, heartbeat_at, started_at)` 更新的那一侧。

逐行判定（约 L768-794）：

```
state = str(row.get("state") or "unknown")
heartbeat = max(float(row.get("heartbeat_at", 0) or 0),
                float(row.get("updated_at", 0) or 0))
if (state in {"starting", "running"}
        and (heartbeat <= 0 or time.time() - heartbeat > 30)):
    state = "stale_headless"
```

触发条件（全部满足才重分类）：

1. durable `state` 仍是 `starting` 或 `running`（终端态不改）。
2. `heartbeat = max(heartbeat_at, updated_at)`：
   - 两者都缺/0 → 立即 `stale_headless`；
   - 否则 `now - heartbeat > 30`。

30 秒在观察器里是字面量，没有命名常量。它同时用于：

- 单行 headless 心跳过期（上式）
- 单行 native `running` 无当前 generation rollout 且 `updated_at` 过期 → `stale_native`（L729-733）
- 全局 `freshness`：`planes["headless"] > 0` 且 `headless_age > 30` → `STALE`（L936-938）
- 全局 `age > 30` 时 desktop 走 QUIET/STALE 分叉（L939）

`starting` 行通常还没有 `heartbeat_at`，但有 `updated_at`，所以用 `updated_at` 当心跳代理；超过 30s 仍停在 `starting` 也会变成 `stale_headless`，而不是继续算 `initializing`。

## 3. 是否计入 planes.headless / counts.running

**否。** 重分类发生在计数之前。

| 观察器字段 | `starting` 且心跳新鲜 | `running` 且心跳新鲜 | 被标成 `stale_headless` |
|---|---|---|---|
| `counts.running` | 不加 | +1 | 不加 |
| `counts.initializing` | +1 | 不加 | 不加 |
| `counts.stale_headless` | 不加 | 不加 | +1 |
| `planes.headless` | 不加 | +1 | 不加 |
| `planes.desktop` | 不加 | 不加 | 不加 |
| `pools[*]` / parent.running | 不加 | +1 | 不加 |
| `tasks` 列表 | 加入 `state=starting` | 加入 `state=running` | **不加入**（全是 stale 时 `tasks == []`） |
| `headless_updated` / `liveness.headless_age_seconds` | 计入 | 计入 | **仍计入** |

代码顺序（L781 之后）：

- `starting` → `initializing` 只在 **未** 被改成 stale 时成立
- `running` → `counts.running += 1; planes["headless"] += 1` 同上
- `stale_headless` → 只 `counts["stale_headless"] += 1`
- `if state in {"starting", "running"}:` 才 `tasks.append`；因为 state 已被改写，stale 行进不了任务表

`headroom = max(0, target - counts["running"])`，因此 stale 行 **不占容量、不减 headroom**。

`freshness`：当 `stale_headless > 0` 且 `running == 0` 且 `initializing == 0` → `STALE`。即使另有新鲜 refill_state，也不能把过期 headless 心跳藏掉。

契约测试：`tests/unit/test_loop_monitor_server.py::test_stale_headless_heartbeat_is_not_hidden_by_fresh_refill`

- now=100，roster `state=running`, `heartbeat_at=updated_at=20`（龄 80s > 30）
- refill_state `updated_at=99`（龄 1s）
- 断言：`freshness==STALE`，`age_seconds==1.0`，`liveness.headless_age_seconds==80.0`，`counts.running==0`，`counts.stale_headless==1`，`planes.headless==0`，`tasks==[]`

反例（新鲜心跳仍算 headless running）：`test_windows_headless_roster_is_merged_into_dashboard` 与 `test_dashboard_merges_parent_target_debt_with_observed_planes`（`heartbeat_at=9`, now=10 → 计入 `planes.headless` 与 `counts.running`）。

8765 页面只渲染 `d.counts.running` 和 `d.planes.headless`；`stale_headless` 留在 `/api/status`，页面任务表因此为空。

## 4. 相邻子系统（不是 8765 计数，但易混）

| 子系统 | 阈值 | 对 stale_headless 的关系 |
|---|---|---|
| supervisor 写心跳 | 每 10s | 生产者；不读 30s 规则 |
| 8765 snapshot | `now - max(heartbeat_at, updated_at) > 30` 或心跳缺失 | **唯一定义 stale_headless 并决定 planes/counts** |
| statemachine / v2 watchdog | `SUPERVISOR_HEARTBEAT_STALE_SECONDS = 5.0` | 心跳 >5s 则不再认为 supervisor 拥有该 generation，可对超时 RUNNING packet 打 TIMED_OUT；**不改 roster state 为 stale_headless** |
| refill_controller.py (v1) | 无心跳检查 | durable `state=="running"` 仍算 running |
| refill_controller_v2.py | 无心跳检查；看 supervisor/worker PID generation 是否还活 | `state=="running"` 且 supervisor+worker 活着仍算 running。观察器 freshness 不是 LIVE/QUIET/ESTIMATED 时 overlay 被丢弃 |
| native 对照 | 30s 无近期事件且无当前 rollout → `stale_native` | 同样不进 `counts.running` / `planes.desktop` |

含义：一台 supervisor 卡死但仍占 PID 时，8765 在 30s 后显示 `stale_headless`（running/headless=0）；refill v2 仍可能把它当 running，直到进程 generation 消失。两边口径不一致是实锤，不是本包要修的范围。
