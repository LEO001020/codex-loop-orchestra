任务名：错配manifest反证

## 独立逻辑审计结论

**结论：是的，这种错配足以掩盖真实 deficit，属于计量级别漏洞（L2 severity）。**

---

### 最小复现（纯逻辑，无需读文件）

```
场景：
  parent_sessions 的 active manifest = "p0-parent-final-backlog-20260814"
  headless 审计 manifest        = "p0-readonly-audit-headless-20260814"

8765 观测层行为：
  observer.parents.running = count( all children where parent_id == ROOT )
  ↑ 不区分 manifest 名称，只看 parent_id 归属

refill_controller 行为：
  deficit = target(20) - observer.parents.running
  ↑ 直接消费上述 running 计数

错配结果（数字举例）：
  - 真实 active-manifest 槽占用 = 5
  - 审计 manifest 槽占用        = 12
  - observer.parents.running    = 17   ← 两类都算进去
  - deficit 计算                = 20 - 17 = 3
  - 真实 active-manifest deficit = 20 - 5 = 15   ← 被隐藏
```

---

### 逻辑链

1. **计数边界错误**：`observer.parents.running` 聚合所有子任务，不按 manifest 分桶。审计 manifest 的 workers 虽然是 read-only，但在计数器层面与 active-manifest workers 等价。

2. **refill_controller 的盲点**：控制器的 refill 逻辑是 `if deficit > 0 then spawn`。由于审计 workers 填满了分母，deficit 接近零，控制器不会为 active manifest 补充实际执行槽，即使真正的执行 backlog 仍有大量待处理包。

3. **掩盖性质**：这不是偶发噪音，而是**结构性遮蔽**——只要审计 manifest 持续运行，active manifest 的欠缺就持续被压住，直到审计 workers 自然结束。

4. **8765 显示层的误导**：面板显示的 `running=17` 在视觉上接近 target=20，看起来"健康"，无法区分两类 manifest 的真实分布。

### 等级评定

| 维度 | 评估 |
|------|------|
| **严重性** | L2（计量级，影响调度正确性，不影响数据安全） |
| **可检测性** | 低（仅靠 8765 面板不可见，需按 manifest 分桶统计） |
| **修复方向** | observer 应按 manifest 分桶；refill_controller 的 deficit 计算应只计 active manifest 的 running 数，而非全 parent running |
| **当前影响** | active manifest 实际 deficit 被低估，吞吐量下降，SLA 可能悄然违约 |
