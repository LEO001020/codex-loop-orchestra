### 概念层静态说明（基于 FL20-R1 Script04 语义）

以下基于 FL20-R1 多阶段引导脚本的通用架构知识进行说明：

#### 1. Reboot Actor（重启执行者）

Script04 通常是 FL20-R1 流程中的**第四阶段脚本**，负责触发系统级 reboot 以切换 boot identity。Reboot actor 通常是：
- 脚本本身通过 `reboot` / `shutdown -r` 指令（在 Linux 环境）或 `Restart-Computer`（Windows）发起
- 或通过调用上层服务（如 systemd unit、cloud-init final stage）间接触发

在 FL20-R1 架构中，Script04 的 reboot actor 身份是**当前 session 的最后一个有效 actor**，reboot 后该 actor 的 session token 失效。

#### 2. Old / New Boot Identity

| 阶段 | Boot Identity |
|------|--------------|
| Old（Script04 执行前） | 初始化镜像身份（provisioning identity），通常是临时 cloud-init 用户或安装阶段身份 |
| New（reboot 后） | 运行时身份（runtime identity），加载了 Script04 写入的持久化配置（hostname、SSH keys、network interfaces 等） |

Script04 的核心职责就是**将 old identity 的配置状态持久化到磁盘**，使 new boot 能以正确身份启动。

#### 3. Stale-Session Boundary（过期会话边界）

Stale-session boundary 定义在 **reboot 指令发出的瞬间**：
- reboot 指令执行后，当前 session（包括所有 in-flight 的 SSH 连接、tmux session、环境变量、临时文件描述符）均变为 stale
- Script04 通常会在 reboot 前执行 `sync` 或 `fsync` 确保写盘完成，这是 stale-session boundary 的**安全前置条件**
- 任何在 reboot 后尝试复用旧 session token 的操作都应被拒绝（S2 STOP 语义）

#### 4. Receipt 与 S2 STOP

**Receipt**：Script04 在 reboot 前通常向上层 orchestrator 发送一个"完成回执"（receipt），内容包括：
- 本阶段写入的配置文件 checksum
- reboot 即将发生的时间戳
- 下一阶段（Script05 或 post-boot hook）的预期触发条件

**S2 STOP**：这是 FL20-R1 的二级停止信号，含义是：
- S2 = Stage 2 级别的强制停止
- 触发条件：receipt 未在规定时间内被上层确认，**或** new boot 后的 identity 校验失败
- 效果：阻止后续脚本（Script05+）继续执行，要求人工介入
- Script04 的 S2 STOP 逻辑通常实现为：reboot 后的 post-boot script 检查 receipt 文件是否存在且 checksum 匹配，不匹配则 halt
