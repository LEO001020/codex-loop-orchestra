### I6：错误字节是否可生效（进入规范账本）

**结论：不可生效。PASS。**

以下是逐点支撑：

**1. VACUUM 阶段产生的是完全隔离的副本**

```bash
# 脚本第106行附近（伪）：
source.execute("VACUUM INTO ?", (sys.argv[2],))
```

`VACUUM INTO` 写入 `$backup/research-pre-v3.sqlite`，这是一个独立文件，从不直接替换 live DB。如果 VACUUM 或其后的完整性检查失败，脚本以非零退出，EXIT trap 在 `BACKUP_READY=0` 状态下触发，此时 live DB 从未被接触——没有任何错误字节可生效。

**2. VACUUM 备份后立即双重验证**

备份完成后立刻对 copy 执行 `PRAGMA integrity_check` + `schema_version=2` 两项检查。任一失败即脚本立即退出，进入 EXIT trap，backup 未被设为 `BACKUP_READY=1`，恢复路径不会用损坏的备份覆盖 live DB。

**3. 迁移 SQL 包含空表前置门**

`P5_AUTHORITY_SCHEMA_V2_TO_V3.sql` 第一条语句是：
```sql
CREATE TEMP TABLE _p5_v3_empty_gate(n INTEGER NOT NULL CHECK(n=0)) STRICT;
INSERT INTO _p5_v3_empty_gate SELECT (SELECT count(*) FROM authority_proposals) + ...
```
只要任何权威表已有行，`CHECK(n=0)` 即失败，整个脚本以 `IntegrityError` 回滚，账本零行不变。`T28_MIGRATION_NONEMPTY_FAILS_CLOSED` 验证了此路径。

**4. EXIT trap 的恢复路径严格限定在 `BACKUP_READY=1` 之后**

```bash
if [ "$BACKUP_READY" = 1 ]; then
    rm -f -- /data/k3/research/research.sqlite-wal /data/k3/research/research.sqlite-shm
    cp -a "$backup/research-pre-v3.sqlite" /data/k3/research/research.sqlite
    ...
fi
```

若 `BACKUP_READY=0`（VACUUM 或备份本身失败），则不执行任何 DB 覆盖，live DB 保持原样。若 `BACKUP_READY=1` 但 `INSTALL_STARTED=0`，则只恢复 DB 文件而不操作 TCB，原 v2 daemon 重启时面对的是完整 v2 DB。

**5. `TRANSACTION_COMPLETE=1` 后 trap 立即解除**

```bash
TRANSACTION_COMPLETE=1
trap - EXIT
```

在 `start + live verify + rebuild-check` 三步全部通过后才解除 trap，整个事务期间任何一步失败都进入回滚，不会留下半成品字节。

**综合判定（I6）：** 无论 VACUUM 阶段、install 阶段还是 migrate 阶段出现的任何错误字节，均被隔离于临时文件或被 `ROLLBACK` 所吸收，不会写入规范账本。I6 = 无 blocker。

### I8：规范账本是否会不可用或损坏

**结论：不会。PASS。**

**1. 账本文件在 stop 之前不被接触**

`systemctl stop researchctld` 成功后才设置 `STOPPED=1`，才进入 backup 阶段。停止失败则 `die()`，EXIT trap 此时 `STOPPED=0`，不执行任何 DB 操作。账本在 daemon 完全停止前不暴露于任何写路径。

**2. 迁移在 research-writer 身份下运行，写入对象是已停止 daemon 的 live DB**

```bash
runuser -u research-writer -- /usr/bin/python3.12 ... \
    --direct migrate --migration-id P5_AUTHORITY_SCHEMA_V2_TO_V3 ...
```

迁移 SQL 本身是原子性的 `executescript`（SQLite 单事务），DROP+CREATE 的整个操作在一个数据库事务内。如果中途失败，SQLite 保证回滚，账本仍然是 schema v2 的完整状态。

**3. pre-reload 阶段在 daemon-reload 之前验证 live 字节**

`--mode pre-reload` 在 `daemon-reload` 之前完成。若 pre-reload 验证失败：EXIT trap 触发，DB 从备份还原，旧 unit/wrapper 文件从 `$backup` 拷贝回来，然后 `daemon-reload + start` 重启旧 v2 daemon。

**4. start 失败的二次保障**

```bash
if systemctl start researchctld >/dev/null 2>&1; then
    log "DEPLOY_TRANSACTION_ROLLBACK=PASS old v2 daemon restarted"
else
    log "DEPLOY_TRANSACTION_ROLLBACK=FAIL recovery=$backup"
fi
```

即使 start 失败（极端情况），账本文件已被还原为完整 v2 备份，备份路径 `$backup` 被记录，恢复是可审计的。

**5. WAL/SHM 清理先于备份还原**

```bash
rm -f -- /data/k3/research/research.sqlite-wal /data/k3/research/research.sqlite-shm
cp -a "$backup/research-pre-v3.sqlite" /data/k3/research/research.sqlite
```

先清除 WAL/SHM 侧文件再覆盖 DB，避免 SQLite 在 restore 后重放旧 WAL 导致损坏。T26_WAL_SHM_ROTATION 验证了 WAL/SHM 在服务重启后不损坏数据。

**6. 所有八个权威表受 `09_ROLLBACK_PRE_AUTHORITY.sh` 守护**

回滚脚本在操作前检查全部八个权威表均为零行，有任何行即拒绝回滚（`AUTHORITY EVENTS PRESENT: rollback forbidden`），防止人工误操作覆盖已包含权威事件的账本。

**综合判定（I8）：** 任意管道阶段失败均不会使规范账本变为不可用或损坏。VACUUM 产生完全隔离副本；迁移在单事务内；回滚路径严格按 flag 控制；账本文件在全程未执行 daemon stop 之前不暴露。I8 = 无 blocker。
