## Analysis: Arm Receipt Absent When Preflight Blocks

### Core Question

Should an arm receipt (`P5_RESEARCH_ALPHA_FAST_PATH_ARM_V1.json`) be written when scientific preflight has blocked *before* adapter freeze or executable command issuance?

**Answer: Yes, it must remain absent.**

### Reasoning

**1. The arm receipt is a capability authorization artifact**

An arm receipt signals that a fast-path has been validated end-to-end and the labeled output is authorized to carry its capability claims. Writing it constitutes a positive assertion: "this pipeline ran, the gates passed, the label is trustworthy."

**2. Preflight blocking = source gate is known-impossible**

If scientific preflight blocks before adapter freeze, the source gate never reached a closed/ready state. The adapter was never frozen. No executable command was ever issued. The pipeline did not execute. Writing a receipt in this state would be a false positive authorization — it would assert that gates passed when they demonstrably did not.

This is a **type-I authorization error**: granting capability claims to a label that was never earned.

**3. Label read/derive chronology**

The expected chronology for a legitimate arm receipt is:

```
Preflight validates → Source gate closes → Adapter freezes
→ Executable command issued → Pipeline runs → Receipt written
→ Label reads receipt → Label capability derived/authorized
```

When preflight blocks, the sequence terminates at step 1. Every downstream step — adapter freeze, command issuance, pipeline execution, receipt write, label read, capability derivation — is **causally gated** on preflight success. None of them are permitted to proceed.

If a receipt were written despite preflight blocking, a label reader would observe:
- Receipt present → infer pipeline ran successfully
- Derive capability as authorized
- **False conclusion**: capability granted without valid execution

**4. Rights implications**

The arm receipt is the trust anchor for label capability rights. Label capability rights flow *from* the receipt, not the other way around. A label cannot derive rights that a receipt does not legitimately grant. Writing a receipt without a completed, gate-cleared execution inverts this dependency — it would make the receipt a fiction rather than evidence.

A reader/consumer of the label has no independent way to verify whether preflight ran or blocked; they rely on the receipt's presence as the authoritative signal. A falsely-written receipt therefore **fully compromises the integrity signal** for any downstream consumer.

### Conclusion

`P5_RESEARCH_ALPHA_FAST_PATH_ARM_V1.json` must remain absent when scientific preflight blocks before adapter freeze/executable command. Writing it would:

- Falsely authorize label capability that was never earned
- Corrupt the label read/derive chronology by fabricating a trust anchor
- Grant rights that have no valid causal chain back to completed execution
- Undermine the entire purpose of the arm receipt as a gating/authorization artifact

The absent receipt is the correct terminal state. Any consumer observing the absent receipt should treat label capability as **unauthorized and not derivable** for this path/version.
