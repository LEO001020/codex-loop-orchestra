Based on the examination of the `E:\codex-LOOP\codex-loop-s-f2` environment, here is the verification of the ZCode (LOOP)宿主契约 (host contract) based on the current hooks and orchestration mechanism:

### 1. Hook与事件机制 (Hooks & Events)
The system relies on functional hooks primarily located in `E:\codex-LOOP\codex-loop-s-f2\hooks\`. The most critical one for enforcement is `sol_tool_gate.py`.
*   **Mechanism**: It operates as a `PreToolUse` hook. It receives tool call payloads via `stdin` (JSON format).
*   **Decision Logic (`matcher`)**: When a tool call is made, the gate examines `tool_name`, `agent_type`, and `LOOP state`. If the state is not `planning`/`adjudication`/`release_finalize` and the tool name is in a predefined `GATED_TOOLS` list (like `shell_command`, `read_file`, `search`), the gate issues a `deny`.
*   **Event Handling**: Tool calls and their decisions are logged into `data/events.ndjson` (as verified by the sample `SubagentStart` event). Each event contains fields such as `ts`, `event`, `agent_id`, `agent_role`, `model`, `session_id`, and `task_name`.

### 2. Stdin/Stdout/Exit Code & Agent State
*   **Stdin/Stdout**: The hook `sol_tool_gate.py` consumes JSON from `stdin` and writes JSON decisions to `stdout`.
*   **Exit Code**: The hooks (e.g., `sol_tool_gate.py`) signal decisions primarily through stdout (denial) or implicit exit code 0 (allow/gate failure).
*   **Startup/Resume/Clear/Compact**: These state transitions are handled by the lifecycle management scripts (e.g., `data/lifecycle/`, `data/refill/`, `hooks/subagent_lifecycle.py`). `SessionStart` is an event logged in `data/events.ndjson`.
*   **PostToolUse Agent**: Agents are identified in the `PreToolUse` payload via `agent_type` or `role`. If the agent's role is in `CHILD_ROLES` (`worker`, `verifier`, `reviewer`, etc.), the gate bypasses the check, explicitly allowing worker/verifier agents to perform actions directly, while the root `Sol` agent is constrained.

### 3. Summary of enforcement
The "contract" is designed to be **fail-open** for robustness (if the ledger or gate is unreadable, it fails open to prevent paralysis, but logs an error to `stderr`). Any tool that falls under `GATED_TOOLS` from the root `Sol` agent must go through the gate. Worker agents are explicitly exempt from this gating as they represent the delegated L1/L2 work that is permitted to perform the task.
