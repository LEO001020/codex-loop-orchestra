## Pre-worktree throttling (`before_spawn`)

**Location:** `harness/dispatch.py`, lines 241–275, function `before_spawn(pid)`.

The gate runs in `dispatch_single` **before** `allocate_worktree`, `prepare_report_slot`, or any `dispatched` event emission. It checks four conditions in order:

1. **Backoff active** — reads `spawn_throttle_state.json`; if `blocked_until > now()`, raises `BirthThrottleError` immediately.
2. **Concurrency ceiling** — calls `observed_birth_counts()` which delegates to `RefillControllerV2.read_roster_counts()` (the canonical lifecycle truth source, not a stale text parser). If `initializing + running >= target_total` (default 80 from `refill_policy.toml`), raises `BirthThrottleError`.
3. **Initializing cap** — if `initializing >= max_initializing` (default 8), waits 200 ms and retries until the cap drains or a 30-second deadline passes, then raises `BirthThrottleError` with `blocked_until` persisted.
4. **Spawn interval** — enforces a 1-second minimum between births using `last_spawn_at` from the throttle state file.

The physical worktree is not allocated until **after** `before_spawn` succeeds. This is the design intent: a throttled packet must remain `DISPATCHABLE` and leave no filesystem artifacts.

**Config source**: all four thresholds (`spawn_interval_ms=1000`, `max_initializing=8`, `health_gate_every=8`, `failure_backoff_seconds=30`, `health_timeout_ms=2000`) come exclusively from `config/refill_policy.toml` `[spawn_throttle]` via `policy_int()`. No hardcoded magic numbers in the hot path.

## Durable `spawn_throttled` event

**Location:** `dispatch.py` lines 514–528.

When `before_spawn` raises `BirthThrottleError`, the catch block calls `append_event(pid, "spawn_throttled", {...})` with fields: `phase="pre_spawn"`, `error=str(exc)`, `role`, `model`, `run_id`, `attempt`. The event write is itself try/except guarded — failure degrades to a stderr warning rather than suppressing the re-raise, so `BirthThrottleError` always propagates to `main()`.

The event is written to `data/events.ndjson` under the global `.events.lock` (via `locked()`), so it is crash-durable before the exception unwinds. The packet remains at `DISPATCHABLE` in the ledger because neither a `dispatched` event nor a worktree allocation occurred.

**Statemachine interaction (latent concern):** `spawn_throttled` is **not** in `INFO_EVENTS` in `statemachine.py`. If `statemachine.py step` processes this event for a `DISPATCHABLE` packet, `("DISPATCHABLE", "spawn_throttled")` is not in the transition table `T`, which triggers the off-table → `DEAD_LETTER` path. In practice this would prematurely kill a packet that is merely backpressure-held. The unit test (`test_birth_throttle_is_fail_visible_without_traceback`) explicitly asserts `ledger state == "DISPATCHABLE"` after dispatch exits with rc=3, but does **not** run `statemachine.py step` afterward to confirm the event is harmless. The safe fix is to add `"spawn_throttled"` to `INFO_EVENTS`. This is not a bug that fires today (throttle has never fired in `data/events.ndjson`), but it is a latent correctness gap.

## Controlled rc=3

Three exit points in `main()` all use `return 3`:

| Line | Trigger |
|------|---------|
| 907–909 | `BirthThrottleError` from `dispatch_release_review` |
| 921–924 | `sol_budget_block` returns a block decision (Sol token-share hard cap) |
| 930–932 | `BirthThrottleError` from `dispatch_single` or `dispatch_csv` |

In every case: the error is logged to stderr as a plain one-line message (`"dispatch throttled: …"` or `"dispatch blocked: …"`), no traceback is printed, and the process exits cleanly with rc=3. The `sol_budget_blocked` path also appends a per-packet event to `events.ndjson` before returning 3, so even that policy-level block is durable. rc=3 is distinct from rc=1 (hard error) and rc=2 (nothing dispatchable), making it unambiguous for callers to distinguish a transient capacity refusal.

**No upstream consumer of rc=3 was found** in `harness/` beyond dispatch.py itself (no `statemachine.py` call to `dispatch.py` that checks the return code). The refill controller and state machine invoke dispatch as a subprocess and appear to treat non-zero exits as blocked/retry signals rather than fatal errors, which is correct for a transient throttle.
