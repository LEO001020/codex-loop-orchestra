### K3 Mount 装配链

K3 安全边界的设计是**三点挂载**：

| 挂载点 | 位置 | 状态 |
|--------|------|------|
| A1：dispatch 断言 | `kernel/index.ts → handleHostRequest() → assertDispatchGuarded()` | **已接线**，但默认 **inert**（`armed=false`） |
| A2：构造包装 | `agent-session.ts:8767 → applyK3DomainGuard(handlers)` | **已接线**，但默认 **identity**（无 boundary 时直接返回原 handlers） |
| 武装触发 | `security/index.ts → installK3SecurityBoundary()` | **未在生产路径调用** |

### 未接线风险（Gap）

**核心风险：`installK3SecurityBoundary()` 从未在生产代码路径中被调用。**

具体来说：

1. **`installK3SecurityBoundary` 只在测试文件中出现**（`k3-kernel-evidence.test.ts`、`k3-ledger.test.ts`、`k3-security-boundary.test.ts`），没有任何 `src/modes/`、`src/bin/`、daemon 启动链或 `createAgentSessionServices` 中调用它。

2. **因此 `armed=false` 永久成立**：
   - `assertDispatchGuarded()` 第一行 `if (!armed) return` — 完全不检查
   - `applyK3DomainGuard(handlers)` 第一行 `if (!installed) return handlers` — 返回原始未包装的 handlers

3. **K3 gate 挂载（`k3WrapGate`）也未接线**：`mount.ts` 的注释明确说它应 inline 在 `ipython.ts:707` 的 `wrapToolDefinition(...)` 调用处，但实际 `ipython.ts` 第 707 行只有 `return wrapToolDefinition(createIpythonToolDefinition(cwd, options))`，没有 `k3WrapGate` 包裹。

4. **`wrapKernelSpawn`（OS 隔离层）未被调用**：`boundary.ts` 实现了 landlock/bwrap/seccomp/seatbelt 的 spawn 包装，但 `kernel/index.ts` 的实际 spawn 调用直接用 `spawn(python, args, ...)` 而不经过 `planKernelSpawn()`。

5. **`createGoalCompleteGate` 未接线**：`agent-session.ts` 的 `_createKernelHostHandlers` 区块中 `goal.complete` 分支没有 `createGoalCompleteGate` 包裹（`mount.ts` 注释标注的 `agent-session.ts:8678` 插入点为注释标注，实际代码未执行）。

### 总结

README 描述的安全模型在源码层面是**已声明但未激活**的状态：

- `AgentSession → KernelManager → IPython kernel` 这条装配链是完整可用的
- `RLM child spawning` 路径（`rlm.run` → comm → `runRlmChild`）是完整可用的
- K3 安全边界（OS 隔离、dispatch 断言、goal.complete 门控、ipython 工具门控）全部处于"inert until armed"状态，而唯一的武装函数 `installK3SecurityBoundary` 没有被任何生产入口点调用
