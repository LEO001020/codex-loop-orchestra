### 二、各检查项逐项分析

#### 1. Canonical Signing Bytes（签名字节一致性）

**结论：存在 I7 级缺陷。**

`command_attach_signature`（第 223–231 行）的签名验证调用：

```python
verify_ed25519(public, canonical_json(payload), signature)
```

此时 `payload` 是从文件加载的无签名 payload dict（尚未含 `owner_signature` 键）。

`command_verify_signed`（第 234–241 行）的签名验证调用：

```python
unsigned = dict(payload)       # payload 此时含 owner_signature
unsigned.pop("owner_signature", None)
verify_ed25519(..., canonical_json(unsigned), signature)
```

两条路径名义上操作"相同"的字节，但存在一个关键结构性分歧：

**`load()` 用 `json.loads()` 解析 JSON 文件，而 `write()` 用 `canonical_json()` 写入文件。`canonical_json` 使用 `ensure_ascii=False`，而标准 `json.loads` 在解析时不规范化编码。`load()` 之后 `canonical_json()` 的输出与原始磁盘字节不一定相同。** 然而更关键的是：`command_invoke_signer` 写入文件的是 `canonical_json(payload)` 字节（通过 `write()`），而外部签名器对磁盘文件字节（`P5_CANONICAL_PAYLOAD_PATH`）签名——这些磁盘字节就是 `canonical_json(payload)`；`command_attach_signature` 则先 `load(args.payload)`（JSON 解析回 dict，再 `canonical_json()` 重新序列化），只要 payload dict 字段完全是 JSON 安全类型（字符串、数字、嵌套 dict/list），两次 `canonical_json()` 应产生相同字节。

**真正的 I7 缺陷在 `command_verify_signed` 和 `command_register_root` 的交互**：

```python
def command_register_root(args: argparse.Namespace) -> None:
    execution_gate(args)
    command_verify_signed(args)          # 用内存 dict 重序列化验证
    completed = subprocess.run(
        [args.researchctl, "delegation-register", "--payload", "@" + args.payload],
        ...
    )
```

`researchctl delegation-register --payload @<file>` 传递的是**磁盘文件原始字节**（`@` 前缀表明是文件引用），但 `command_verify_signed` 验证的是 `canonical_json(dict(payload))` — 即 `load()` 后重新序列化的字节，不是磁盘文件的原始字节。如果签名文件写入时（`write()`）和 `researchctl` 读取时产生任何字段顺序差异（例如 `resource_policy` 作为内嵌 dict 被重解析后键顺序改变），则 `verify_signed` 通过但 `delegation-register` 收到的字节与签名不符——生产端将拒绝签名。

**可执行夹具（fixture）**：

```python

                                 separators=(",", ":")).encode()

# {"resource_policy":{"a":2,"z":1}}   <- sort_keys=True 会重排嵌套键
# 结论：只要 canonical_json 用 sort_keys=True，重序列化和磁盘原始不一致
# 因为磁盘文件中 resource_policy 已被 write() 的 canonical_json 排序，
# 所以两者实际一致——除非 load() 读入的 payload 来自外部、非 write() 写入的文件
```

**实际 I7 缺陷确认**：在 `command_attach_signature` 中，`payload` 来自外部签名器产生的文件（即由 `command_materialize_root` 的 `write()` 生成），所以磁盘字节和 `canonical_json(load(...))` 是一致的。但该函数在**签名前**调用 `verify_scope(payload)`，`verify_scope` 在通过后不修改 dict，随后 `canonical_json(payload)` 作为被签名消息——这与 `command_verify_signed` 路径中 `canonical_json(unsigned)` 一致，**无分歧**。

**但存在一个不同的 I7 缺陷**：`require_receipt` 的 hash 检查逻辑：

```python

```

这里用了 **dict.get 的 default 参数** 作为被比较值的备用值——即若 `amendment_sha256` 键**缺失**，`get()` 返回 `expected`，条件 `expected != expected` 为 `False`，hash 检查**静默通过**。这意味着一个缺少 `amendment_sha256` 字段的 receipt 将绕过 hash 校验。

**结论：`command_register_root` 存在双重验证与文件传递的语义不对称（I1 次级）。**

### 五、结论

**I7 缺陷（F1）** 是根本性的：`require_receipt` 的 hash 检查使用了 `dict.get(key, default)` 的备用语义，导致缺字段时校验等价于 `expected == expected` 恒成立，完全绑过。这直接使 **I1 级的 C-before-D 顺序门（F2）** 在 ceremony 工具层面形同虚设。store 层（`authority_store.register_amendment_direct`）的 `C_FIRST_D_SECOND_REQUIRED` 硬检查仍然有效，但工具层防线已失，不应依赖单层防御。

**修复建议（仅记录，不执行）**：将 `require_receipt` 第 80 行改为：
```python
if value.get("amendment_sha256") != expected:   # 移除 default 参数
```
这样缺失字段时 `get()` 返回 `None`，`None != expected` 为 `True`，正确抛出异常。
