## 部署事务性检查清单

### 阶段 0：前置快照（事务开始前，全部幂等）

1. 确认当前运行守护进程标识为 `app-v2-pc7`，记录 PID 与启动时间戳
2. 确认 `event_count = 3079`，projection 哈希前缀为 `91b8...`，作为基线指纹
3. 确认 `/opt/p5` 路径**不存在**（这是已知事实，非异常）
4. 对 SQLite 数据库执行持久化备份，备份路径须含时间戳（`backup_<timestamp>.db`），验证备份文件 checksum
5. 记录当前 wheel 缓存目录与已安装包的精确版本清单（`pip freeze` 或等效快照）

### 阶段 1：停止守护进程（不可逆点前的最后检查）

6. 执行 `stop daemon`，等待确认进程已完全终止（检查 PID 消失）
7. **不可逆点检查**：再次确认数据库备份完整性，才可继续

### 阶段 2：文件部署（原子性要求）

8. 执行精确 manifest 复制（exact manifest copy），确保目标路径与源路径 checksum 一致
9. 提取 pinned wheel（固定版本 wheel 解压），**不允许**从网络拉取，仅使用本地缓存
10. 验证解压后文件与 manifest 中记录的文件列表完全吻合

### 阶段 3：数据库迁移（严格有序，不可跳步）

11. 执行迁移 `v2 → v3`，验证迁移成功（检查 schema version 标记）
12. 执行迁移 `v3 → v4`，验证迁移成功
13. **严禁**跳过中间版本或合并执行，每步须有独立成功确认

### 阶段 4：完整性校验

14. 执行 `verify_tcb`，须返回通过状态；任何失败立即触发回滚，不继续

### 阶段 5：守护进程重载与启动

15. 执行 `daemon reload`（重新加载配置）
16. 执行 `daemon start`，等待进程稳定（确认新 PID 出现且持续存活 ≥ 5 秒）

### 阶段 6：运行时验证

17. 执行 RM（Resource Manager）验证，确认通过
18. 必要时执行 RM rebuild，验证 rebuild 结果
19. 确认新 `event_count` ≥ 3079（不得回退），projection 状态与预期一致

### 已豁免的门控（owner/security gates）

- 原始脚本中的 owner 检查与 security gates **已被明确豁免**，本检查清单中不包含这两项，属已知豁免，无需补充

## 回滚不变量

以下条件任意一条触发，必须立即执行回滚，不得跳过：

| # | 触发条件 | 回滚动作 |
|---|----------|----------|
| R1 | 阶段 1 后守护进程未完全停止（残留进程） | kill -9，重新确认，不继续部署 |
| R2 | 阶段 2 manifest 复制 checksum 不匹配 | 删除目标文件，恢复备份，重启旧守护进程 |
| R3 | 任意迁移步骤（v2→v3 或 v3→v4）失败 | **不执行反向迁移**，直接从备份恢复整个数据库文件，重启旧守护进程 |
| R4 | `verify_tcb` 未通过 | 从备份恢复数据库，还原旧 manifest，重启旧守护进程 |
| R5 | 新守护进程启动后 5 秒内崩溃 | 停止新进程，还原旧 manifest + 旧 wheel，从备份恢复数据库，重启旧守护进程 |
| R6 | RM 验证失败 | 同 R5 |
| R7 | 新 `event_count` < 3079 | 立即停止，从备份恢复，视为数据丢失事故 |

### 回滚核心约束

- **数据库只能从备份整体恢复**，禁止尝试反向迁移（v4→v3→v2）
- `/opt/p5` 不存在是已知前置状态，回滚后无需重建该路径
- 回滚完成后，守护进程必须以 `app-v2-pc7` 标识重新启动，并验证 `event_count = 3079`，projection 哈希匹配 `91b8...`
- 整个回滚过程的最大允许时间窗口应在部署前明确设定，超时即升级人工介入
