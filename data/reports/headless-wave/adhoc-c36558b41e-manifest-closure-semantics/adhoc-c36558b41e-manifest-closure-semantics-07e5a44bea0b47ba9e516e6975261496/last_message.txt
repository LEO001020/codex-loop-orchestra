已获取所有必要信息。现在可以进行完整的语义闭包分析。

---

## 分析结论

### 一、问题的精确描述

**函数注释声称的语义**（`frozen_manifest_hash_set`，`pc6_alpha_materializer.py` 第270行）：
```
Collect every 64-hex sha256 value in the frozen PC6 executable data
manifest / revision lineage so staged objects can be membership-verified
mechanically (F01-A).
```
注释用斜杠并列了两个对象：**PC6 executable data manifest** 和 **revision lineage**。语义上暗示该 hash-set 应同时覆盖这两个文档的内容。

**实际调用**（`alpha_execution.py`，`_load` 方法，第192–199行）：
```python
manifest_path = self.scientific_root / "P5_PC6_EXECUTABLE_DATA_MANIFEST_V1.json"
manifest = json.loads(manifest_path.read_text(encoding="utf-8"))
mat.verify_staged_inventory_against_manifest(
    staged, mat.frozen_manifest_hash_set(manifest))
```
传入 `frozen_manifest_hash_set` 的**只有** `P5_PC6_EXECUTABLE_DATA_MANIFEST_V1.json` 的解析内容。**revision lineage 文档从未被读取、解析或传入。**

---

### 二、source SHA 的位置

`source_sha` 在 manifest 调用之前通过 `verify_staged_object_file` 计算并放入 `staged`：
```python
source_sha = mat.verify_staged_object_file(
    self.root, self.run.get("source_file"), self.run.get("source_sha256"), ...)
staged = [source_sha, *verified]
```
`staged` 包含 source 哈希，然后 `verify_staged_inventory_against_manifest` 验证 staged 中每个哈希是否在 manifest hash-set 中存在。因此 **source SHA 已在 membership 检查范围内**，这一环节本身没有遗漏。

---

### 三、"运行时追加 lineage 哈希"能否解决来源遗漏？

**不能，且这是一个错误的方向。** 原因如下：

1. **membership 检查的被检方是 `staged`（已暂存的执行输入哈希），不是 manifest 文档本身。** `frozen_manifest_hash_set` 的作用是把 manifest 文档中所有 64 字符十六进制串提取成一个参照集合（allowlist），然后验证 `staged` 中的每个哈希必须出现在这个集合里。追加 lineage 哈希到该集合，只会**扩大 allowlist**（允许更多哈希通过），而非收窄或加固校验。

2. **lineage 绑定已经在另一道防线执行**：`__init__` 中有：
   ```python
   if self.plan.get("revision_lineage_sha256") != bindings.revision_lineage_sha256:
       raise FailClosed("PC6_REVISION_BINDING_MISMATCH")
   ```
   `revision_lineage_sha256` 已通过 `FrozenBindings` 与执行计划绑定，并在 `_scientific_observations` 中通过 `allowed_revision_hash` 与 scientific root 中的 frozen 文件 hash 比对。lineage 完整性已被覆盖，不存在"遗漏"。

3. **"追加"操作本身是运行时修改 hash-set 的构造逻辑**，而该函数由冻结代码调用，只是纯递归 JSON walk。如果 lineage 文档也需要被覆盖，**正确方式是将 lineage 文档也传入并合并两个 hash-set**，而非在运行时拼接——但如第2点所述，这并不必要。

---

### 四、修改调用是否构成"冻结逻辑变更"？

**是的，这是一项冻结逻辑变更。** 证据：

- 整个 `_load` 方法涉及 F01-A 数据完整性校验，被 `AMENDMENT_IDENTITIES` 和科学根哈希体系（`T1_MATRIX_SHA256`、`FROZEN_SCIENTIFIC_VERIFY_SET_20_V1.json` 的20个对象哈希绑定）严格锁定。
- `pc6_alpha_materializer.py` 本身通过 `mat.materializer_sha256()` 的调用被封存在执行证明链中，其字节哈希出现在每一个 sealed artifact 中。
- 修改 `frozen_manifest_hash_set` 的传参（无论是换参数还是合并两个文档），都会改变 materializer 或 execution adapter 的字节内容，**直接使 materializer SHA 失效**，进而使所有现有 sealed results 的 `materializer_sha256` 字段失配。

---

### 五、总结

| 问题 | 结论 |
|------|------|
| 注释是否准确反映调用？ | **不准确**：注释声明 "manifest / revision lineage"，但调用只传入 manifest |
| source SHA 是否被包含在检查中？ | **是**，source_sha 在 staged 列表中，已参与 membership 验证 |
| 追加 lineage 哈希能否修复"遗漏"？ | **不能且无必要**：lineage 绑定已由独立路径（FrozenBindings + scientific observations）严格覆盖 |
| 修改调用是否为冻结逻辑变更？ | **是**，会破坏 materializer SHA 链和 sealed result 完整性 |

**实际存在的问题是注释措辞超出了代码实现**（注释过度声明 revision lineage 覆盖），而非代码本身存在安全漏洞。修复应限于更正注释，使其准确描述"仅针对 PC6 executable data manifest 的成员验证"，而不得触碰任何调用代码。
