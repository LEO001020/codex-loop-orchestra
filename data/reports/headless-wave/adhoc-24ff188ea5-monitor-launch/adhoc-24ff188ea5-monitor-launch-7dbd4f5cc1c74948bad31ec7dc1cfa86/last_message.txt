### 一、隐藏启动机制

Desktop 脚本通过 `Start-Process` 加 `-WindowStyle Hidden` 参数来启动 Monitor：

```powershell
Start-Process -FilePath 'powershell.exe' -WindowStyle Hidden -ArgumentList @(
    '-NoProfile', '-NonInteractive', '-ExecutionPolicy', 'Bypass',
    '-File', $monitorLauncher
) -WorkingDirectory 'E:\codex-LOOP'
```

关键点：
- 使用 `Start-Process` **不带 `-Wait`**，是完全的 fire-and-forget 异步调用，Desktop 主流程不等待 Monitor。
- `-WindowStyle Hidden` 仅隐藏窗口，进程本身完整运行，符合后台服务语义。
- 没有捕获 `Start-Process` 的返回进程对象，也没有读取 `ExitCode`，Monitor 的启动成败对 Desktop 完全透明。

**结论：** 隐藏启动机制本身设计正确，无阻塞风险。

---

### 二、Mutex / 端口复用保护

Monitor 脚本使用命名 mutex `Local\Codex-LOOP-Monitor-8765-Start` 作为启动锁：

- `WaitOne(15秒)`：防止并发二次启动竞争
- 捕获 `AbandonedMutexException`：正确处理前次异常退出遗留的孤儿 mutex，获取所有权后继续
- 健康检查优先：先 GET `/healthz`，若服务已在 `:8765` 运行则跳过二次启动
- `finally` 块保证 `ReleaseMutex()` + `Dispose()` 无论如何都会执行

**结论：** 幂等保护完善，多次调用或崩溃重启均不会产生端口冲突或 mutex 泄漏。

---

### 三、Monitor 失败对主 Desktop 的影响

Desktop 脚本在调用 `Start-Process` 前只做了一个文件存在性检查（`Test-Path`），调用之后**没有任何错误处理**：

```powershell
if (Test-Path -LiteralPath $monitorLauncher -PathType Leaf) {
    Start-Process ...   # ← 此后直接走到 codex:// URI 启动
}
```

Monitor 脚本内部的 `$ErrorActionPreference = 'Stop'` 与 `throw` 只在 Monitor 自身进程内生效，不会向上传播给 Desktop 进程（因为是独立子进程）。

潜在场景分析：

| 失败场景 | 对 Desktop 的影响 |
|---|---|
| Monitor 进程启动失败（python 不存在、端口占用） | **零影响**，Desktop 继续正常开启 Codex URI |
| Monitor 15秒内未就绪并 `throw` | **零影响**，Monitor 子进程静默退出 |
| Monitor 持续崩溃循环重启 | **零影响**，但 8765 端口上的监控能力丧失 |
| 服务本身功能缺失（LOOP 状态监控中断） | **间接影响**：LOOP 运行时状态不可观测，但 Codex Desktop 本身不受阻 |

### 四、整体风险评级

**风险等级：低（LOW）**

设计上 Desktop 与 Monitor 完全解耦，Monitor 的任何失败都不会阻断或崩溃主 Desktop 流程。现有 mutex + 健康检查幂等保护也足够健壮。

唯一值得关注的**非阻塞隐患**：Monitor 失败时没有任何日志或告警写回主进程，运维可见性为零——如果需要排查 Monitor 为何未运行，没有任何留痕。建议（非强制）在 Desktop 脚本中保存 `Start-Process` 返回的进程对象并记录 PID，便于事后诊断。
