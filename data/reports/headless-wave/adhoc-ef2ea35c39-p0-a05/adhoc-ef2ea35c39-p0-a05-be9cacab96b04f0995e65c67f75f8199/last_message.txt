## 双父公平性验收：结论

### 一、Round-Robin 机制确认

`select_tasks`（`refill_consumer_v2.py`）的调度循环结构：

```
buckets 按 key 排序：
  "legacy"
  "parent:<id_A>"
  "parent:<id_B>"

while sum(remaining) > 0:
    for key in sorted(buckets):   ← 每轮完整扫描所有 bucket
        ...选出该 bucket 中第一个满足约束的包...
        remaining[pool] -= 1
        parent_remaining[parent_id][pool] -= 1
```

**判断：** 这是严格的交替 round-robin。每次外层 `while` 迭代，内层 `for` 依次经过 `legacy → parent:A → parent:B`，每个 bucket 每轮最多被选中一次。当两个父会话都有缺口时，每轮各消耗一个 slot，交替进行，直到全局 `remaining` 或某一父 `parent_remaining` 耗尽。

**公平性：** 两个父会话同时有缺口时，选包顺序由 `sorted(buckets)` 即 key 字典序决定。若 `id_A < id_B`，则 A 每轮先于 B 被服务，但每轮仅各消耗一个全局 slot。理论偏差：当全局 `remaining=1` 时，A 固定先得，B 固定饿死该轮。这是**轻微的字典序偏好**，非公平 weighted round-robin，但不会造成系统性饥饿——每轮 A 拿一个 slot 后，`remaining` 减 1，下一次 actuator 调用时父 B 仍有完整 `parent_remaining` 缺口，下次仍会被服务。

---

### 二、Pool 不匹配（cross-pool 冲突）检测

```python
role_pool = "k3" if role in K3_ROLES else "v4"
if role_pool != pool:
    raise RefillConsumerError("packet %s pool/role conflict: %s vs %s" % ...)
```

`pool` 来自 `pool_for_packet(entry)`，`role_pool` 来自 `role_for_entry(entry)`，两者使用相同的角色→pool 映射（`K3_ROLES`）。**理论上不可能出现不一致**——除非 ledger 中手工写入了 `pool_hint` 与 `role` 相互矛盾的条目（`pool_hint` 优先级高于 role，但 `role_for_entry` 只看 `role`/`state`）。若出现则整个 actuator 事务抛异常终止，不会静默跳过；这是 **fail-loud** 行为，正确。

`per_parent` 的 `parent_remaining[parent_id][pool]` 按实际 pool（v4/k3 分开）扣减，因此两个父 pool 预算互不干扰。**不存在 pool 混淆导致的饥饿**。

---

### 三、空桶（empty-bucket）饥饿分析

**场景：父 A 有 v4 缺口，父 B 只有 k3 缺口，但全局 `remaining["v4"]=0`**

在 `select_tasks` 内层循环中：
```python
if remaining[pool] <= 0:
    continue       ← 全局 v4 用尽，A 的 v4 包被跳过
if parent_remaining[parent_id][pool] <= 0:
    continue       ← B 的 k3 包不受 v4 约束
```

父 A 的 v4 包因全局 `remaining["v4"]=0` 被跳过，不影响父 B 的 k3 包调度。**两个 pool 独立计数，空 pool 不阻塞另一 pool。** ✔️

**场景：两个父同时有缺口，但其中一个 bucket 完全为空（`parent_remaining[id][pool]=0`）**

在 `recompute` 中，`spawnable` 由以下三者取 min 计算：
```python
parent_spawn_total = min(
    parent_debt,
    max(0, parent_target - parent_running - parent_initializing),
    capacity,     ← 全局容量
)
```
若某父 `queued_total == 0`，则 `parent_debt = 0`，`parent_spawn_total = 0`，进而 `parent_remaining[id] = {v4:0, k3:0}`。在 `select_tasks` 中该父的所有包都会被 `parent_remaining[parent_id][pool] <= 0` 跳过，**不消耗全局 remaining**，另一父会话的 slots 完全不受影响。这是正确的**空桶隔离**行为。

**场景：全局 `capacity=0` 时**

`parent_spawn_total = min(..., 0) = 0`，所有父的 `spawnable=0`，`select_tasks` 中所有父包均被 `parent_remaining[pool]<=0` 跳过，`progressed=False`，循环提前退出。两个父同等被阻塞，无饥饿偏好。✔️

---

### 四、潜在隐患（非饥饿，但值得关注）

1. **字典序偏好**：`sorted(buckets)` 使 id 字典序较小的父会话在每次 actuator 运行中总先被服务。当全局 deficit 刚好等于 1 时，较大 id 的父会话在该次调用中被跳过。由于 actuator 会在下次 refill 事件中重新调度，这不构成饥饿，但会在高频场景下造成轻微的 **O(1) 级偏斜**。

2. **`capacity` 是跨父共享的快照值**：`parent_spawn_total` 的 `min(..., capacity)` 使用 `recompute` 时拍摄的全局容量快照，并非在 `select_tasks` 循环中实时递减。这意味着两个父会话的 `spawnable` 总和可能超过 `capacity`，但 `select_tasks` 里用全局 `remaining`（由 `deficit` 初始化）做最终门控，`remaining[pool]` 会在实际选中后递减，因此**不会超发**。✔️

3. **`parent_remaining` 初始化来源**：`select_tasks` 从 `state.get("parents")` 读 `spawnable`，而非重新计算。若 `recompute` 与 `select_tasks` 之间状态变化（如某父会话被标记 inactive），`select_tasks` 开头的 `parent_sessions.json` 检查（`parent.get("active") is not True`）会将其包直接过滤掉，在到达 `parent_remaining` 门控前就已排除。**无双重计数风险**。✔️

---

### 总结

| 检验项 | 结论 |
|---|---|
| 两父同时缺口时的 round-robin | ✅ 交替公平，字典序先后仅有 O(1) 单轮偏斜，不构成饥饿 |
| Pool 不匹配 | ✅ Fail-loud 抛异常，不静默丢包；v4/k3 桶独立，互不污染 |
| 空桶饥饿 | ✅ 空 `spawnable` 父隔离，不消耗全局 remaining，另一父不受影响 |
| 全局容量=0 | ✅ 两父同等阻塞，无偏向 |
| 潜在隐患 | ⚠️ 字典序偏好（非饥饿）；`capacity` 快照共享（被 `remaining` 门控兜底） |

**整体判定：consumer 在双父同时缺口场景下公平性符合设计意图，不存在饥饿缺陷。**
