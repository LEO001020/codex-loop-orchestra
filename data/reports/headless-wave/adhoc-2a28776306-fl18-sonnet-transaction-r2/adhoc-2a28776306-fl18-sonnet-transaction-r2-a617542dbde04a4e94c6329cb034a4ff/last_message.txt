### I6 判定：错误字节是否会生效

**结论：否。错误字节不可生效。**

理由逐步可证：

**（1）stop 阶段：** `systemctl stop researchctld` 必须成功，否则 `die` 导致 EXIT 陷阱触发但 `STOPPED=0`，陷阱不执行任何还原，原 v2 daemon 从未被停止，数据库从未被修改，错误字节无写入机会。

**（2）VACUUM v2备份阶段：** VACUUM INTO 前通过 APSW 做了 `PRAGMA integrity_check` 和 schema_version=2 的双重校验，再执行 `PRAGMA wal_checkpoint(TRUNCATE)` 清理 WAL，然后 VACUUM INTO 生成 `research-pre-v3.sqlite`，紧接着对备份文件再次 integrity_check + schema_version 验证。任何阶段失败均属 Python 退出非零，shell `set -euo pipefail` 捕捉后触发 EXIT 陷阱，此时 `BACKUP_READY=0`，陷阱中的 DB 还原分支不执行，源文件未改动。

**（3）install 阶段（bundle + APSW wheel）：** `INSTALL_STARTED=1` 在 BACKUP_READY 置位后立即设置，安装为 root:root 只读目录（0o555），装入路径与运行中的 v2 daemon 路径无重叠（v2 wrapper/unit 已备份至 `$backup/`）。此阶段失败时陷阱会 `rm -rf /opt/p5/authority-v3 /opt/p5/authority-runtime` 并从 `$backup/` 恢复 wrapper/unit，再 daemon-reload 重启 v2 daemon。安装期间错误字节从未写入 DB。

**（4）migrate 阶段：** 迁移通过 `ResearchDB.migrate()` 以 `BEGIN EXCLUSIVE` 执行。迁移 SQL 内嵌 `_p5_v3_empty_gate` 完整性检查（所有8张权威表行数之和必须等于0），任何非零数触发 CHECK 约束违反，事务整体回滚。若迁移失败：a) SQLite 事务原子回滚，DB 仍为 schema 2；b) shell 非零退出，EXIT 陷阱恢复 `research-pre-v3.sqlite` 覆盖 `research.sqlite` 并清除 WAL/SHM，再重启 v2 daemon。T27/T28 已在 WSL fixtures 中验证迁移确定性与空表守门逻辑（28/28 通过）。

**（5）pre-reload TCB 校验：** `verify_tcb.py --mode pre-reload` 在 `daemon-reload` 前验证 wrapper + base unit + drop-in 的实际哈希与 manifest 一致（S17 确认顺序）。失败即触发陷阱回滚。

**（6）start/live 阶段：** `systemctl start` 后再次执行 `verify_tcb.py --mode live`（S18），随后 `researchctl verify` + `rebuild-check` 均需返回 `"status":"PASS"`。全部通过后才置 `TRANSACTION_COMPLETE=1` 并 `trap - EXIT`。任意一个验证失败，陷阱仍处于活跃状态，均会触发 v2 完整恢复。

**I6 判定：CLEAR（无阻塞）。** 在整个事务链任意节点失败时，错误字节均不会持久写入正典账本。备份验证→原子迁移→TCB三重校验→live验证构成严密的多层防护；陷阱式回滚在 `set +e` 保护下稳定执行，所有失败路径均映射回可恢复的 v2 状态。

### I8 判定：正典账本是否会不可用或损坏

**结论：否。正典账本不会因此序列变得不可用或损坏。**

**（1）备份是 VACUUM INTO，非破坏性：** VACUUM INTO 是只读副本操作，不修改源文件，仅产出一个单文件、无 WAL 的干净副本。操作前 WAL checkpoint 已做，源文件完整性已验证。

**（2）恢复使用 cp -a，非 SQL 操作：** EXIT 陷阱恢复路径先 `rm -f` 清除 WAL/SHM（避免 WAL 状态不一致），然后 `cp -a` 将整个 VACUUM 生成的备份文件覆盖至 `research.sqlite`，随后 `chown` 和 `chmod 0600` 正确设置权限，再 daemon-reload + systemctl start，最后由 v2 daemon 自己重新建立 WAL 模式。这是标准 SQLite 单文件还原流程，不存在损坏风险。

**（3）权限从未降低：** 整个流程中 DB 始终为 `research-writer:research-writer 0600`（S07 确认），目录为 `research-writer:research-client 0750`（S08），WAL/SHM 同样为 0600（S09）；UMask=0077 确保新创建的旁路文件也不向 research-client 暴露（S29）。T21 确认 k3 UID 直接 SQLite 访问被拒（0600 边界）。

**（4）迁移备份链完整：** `migrate()` 方法在 `evidence_dir` 下生成 `-pre.sqlite`（带 integrity_check）和 `-post.sqlite`（带 integrity_check + schema_version 验证），且 `pre.exists()` 检查防止重复运行覆盖证据。

**（5）daemon 重启存活：** T25_DAEMON_RESTART_SURVIVES 确认 daemon 重启后能重新打开有权限的 DB 并正常响应 verify。T26_WAL_SHM_ROTATION 确认 WAL 旋转和已提交数据可在重开后读回。T23/T24 确认 verify/rebuild-check/authority-write 均通过 daemon socket 路径正常工作。

**（6）没有任何阶段操作可导致不可逆损坏：** 所有破坏性操作（migration DROP TABLE、WAL 清除）均在事务内或在已验证的备份就绪后执行；陷阱在 `TRANSACTION_COMPLETE=1` 之前始终挂载；`09_ROLLBACK_PRE_AUTHORITY.sh` 的手动恢复路径在所有8张权威表均为空时才允许执行（S30 确认），额外防止了任何含权威数据的错误回滚。

**I8 判定：CLEAR（无阻塞）。** 正典账本在整个序列中均受到原子备份、幂等恢复、完整性多重校验的保护；DB 文件权限边界全程维持；没有可达执行路径能使账本进入持久不可用或损坏状态。
