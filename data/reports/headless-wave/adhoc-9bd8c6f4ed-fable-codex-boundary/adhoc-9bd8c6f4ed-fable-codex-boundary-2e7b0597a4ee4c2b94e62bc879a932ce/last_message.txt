## 发布前安全审查：Fable（V3）主导 VPS Activation 时本地 Codex 常驻的干扰风险

### 问题本质

当新 Fable 实例（V3）被设计为主导远端 VPS 的激活流程时，如果本地仍有一个持久化的 Codex 会话（loop agent 或后台进程）保持对同一工作区或配置文件的读写能力，则存在以下三类潜在冲突：

---

### 风险一：双写者竞争（Dual-writer Race）

**场景**：Fable V3 向 VPS 写入激活配置（如密钥、服务状态文件、`.env`、systemd unit），而本地 Codex 常驻会话同时也持有对相同路径的写句柄或缓存状态。

**后果**：最后一次写入覆盖另一方，导致配置撕裂（torn write）。在 VPS 激活场景下，这可能使服务以半初始化状态启动，且两端都认为自己已成功写入。

**建议**：激活期间，本地 Codex 会话应退出或进入只读模式。如果 Codex 必须常驻，需通过文件锁（`flock`）或激活令牌文件（sentinel file）明确转移写权。

---

### 风险二：旧会话状态污染（Stale Session Interference）

**场景**：本地 Codex 会话持有一份上一个版本的工作区快照（内存中的文件树、变量、计划列表），而 Fable V3 在服务端已完成状态跃迁。旧会话醒来后，基于过时状态再次执行"补偿写入"或"重试激活"。

**后果**：Fable 认为激活完成，Codex 却在同一资源上重放旧指令。这在幂等性设计不严格的接口上会造成重复初始化或状态回退。

**建议**：为激活流引入版本戳或 epoch 字段，Codex 每次操作前先校验当前 epoch 是否与本地缓存一致；不一致则拒绝写入并上报。

---

### 风险三：会话身份模糊（Identity Ambiguity）

**场景**：Fable V3 和本地 Codex 常驻使用相同的 API 密钥或认证令牌向 VPS 服务发起请求。服务端日志与审计链无法区分两个写入来源，导致出问题时溯源困难。

**后果**：安全审计失效，事故复盘时难以判断是哪个 agent 引入了错误状态。

**建议**：Fable V3 激活时应使用专属 Service Account 或带有 `source=fable-v3` 标签的 token，与本地 Codex 的凭证严格隔离。即便共用底层密钥，也应通过不同的 `client_id` 或请求头区分身份。

---

### 安全建议汇总

| 风险点 | 严重程度 | 推荐处置 |
|--------|----------|----------|
| 双写者竞争 | 高 | 激活前本地 Codex 会话静默或降级为只读；使用文件锁或 sentinel 转移写权 |
| 旧会话状态污染 | 中 | 激活配置引入 epoch/version 字段；Codex 写入前先做版本校验 |
| 会话身份模糊 | 中 | Fable V3 与 Codex 使用不同凭证标识；日志中强制记录 `source` 字段 |

**总结**：只要本地 Codex 常驻会话在 Fable V3 激活窗口内仍保有写能力，上述三类风险均会物化。最安全的做法是在激活握手完成前，通过协议约定（而非依赖人工协调）让本地 Codex 进入写静默状态，待 Fable 广播"activation complete"信号后再恢复。
