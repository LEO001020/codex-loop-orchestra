### Callers That Require Explicit Manifest or Parent Scope

**Only one caller exists in production that exposes scope parameters: the `statemachine_v2.py` CLI entry point (line 759).** It correctly forwards `--manifest-id` / `--parent-session-id` from `argparse` through `args.manifest_id` and `args.parent_session_id`.

**Finding:** The CLI caller in `statemachine_v2.py` *supports* explicit scope but does not *require* it — an unscoped invocation (`python statemachine_v2.py wave-check` with no flags) is legal and falls back to the global ledger check. This is the documented "legacy global-ledger check" behavior.

**Callers that need explicit scope (per the docstring intent):**  
Any caller dispatching parent-manifest work (i.e., `refill_consumer_v2.py`'s headless wave or any orchestrator that runs packets grouped by a `manifest_id` or `parent_session_id`) should pass the appropriate scope key. Currently, `refill_consumer_v2.py` does **not** call `wave_check` at all — it calls `StateMachine(...).step()` after dispatch. If a caller were to poll wave completion for a specific manifest generation, it would need `--manifest-id <id>` to avoid stale packets from a prior generation blocking the check.

**The v1 `wave_check(led)` in `statemachine.py`** has no scope capability. It is only reachable when `routing.mode != "layered"` (cold-start/shadow), where there is typically only one active manifest at a time, so the unscoped global check is safe for that mode.

---

**Conclusion:** No production caller currently calls `wave_check` with an explicit manifest or parent scope. The v2 CLI is the only caller that *can* pass scope, and it does so correctly when arguments are supplied. No callers need to be updated based on current usage — but any future caller operating on a named manifest wave should use `--manifest-id` to prevent cross-generation blocking.
