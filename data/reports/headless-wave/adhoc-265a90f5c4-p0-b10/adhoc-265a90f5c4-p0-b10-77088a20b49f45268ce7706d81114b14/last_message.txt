## P0最终对抗评审报告

### 总结结论

**判定：PASS（有条件）** — 本轮改动确实从代码路径上修复了"有真实backlog时的持续20"问题，但存在**一个结构性未覆盖场景**需要关注。

---

### 一、已验证：真正修复的部分

**（1）`queue_sync_ledger` 的P0-6修复是真实的**

`refill_controller_v2.py` 中的 `queue_sync_ledger` 彻底改变了计数方式：旧版 `refill_controller.py` 将所有 DISPATCHABLE 包都计入单一 `--pool v4`，导致K3需求永远写0，K3的保留配额被V4静默借用。v2 版本按 `pool_for_packet()` 逐包派生pool（role in K3_ROLES → k3，否则v4），**两个pool在一次原子写入中同时更新**。这是代码可证明的机械修复，不是口头补位。

**（2）需求驱动而非空跑**

`recompute()` 中 `required` 的判断逻辑明确：
```python
required = {p: bool(not queue_empty and not finalized
                    and pending[p] > 0 and running[p] < targets[p])}
```
只有某pool有 pending > 0 且 running < target 时才为 true。日志中多次出现 `pending: {v4:0, k3:0}` 时 deficit 也为0，完全没有空池生成——防范了"无需求照样补位"的反模式。

**（3）actuator日志中有一次真实backlog场景的dispatch**

在 `13:36:19` 的日志行可以看到：
```
queue_sync_ledger: {'v4': 1, 'k3': 1}
... manifest dispatched ... target_requested: 1 ... status: running
```
这是真实backlog（k3包1个）触发了一次真实的dispatch，不是口头描述。`parent_manifest_importer` 在导入后立即调用了 `schedule_run`，wakee 通过 `drain_requested` 执行了 `queue_sync_ledger → recompute → build_manifest → headless_wave.run` 完整链路。

**（4）per-parent 上限（dialogue_target=20）与全局 target_total=80 正确分层**

`refill_policy.toml` 中 `dialogue_target = 20`，`target_total = 80`。`recompute()` 中 parent 层级独立计算 `parent_spawn_total`，全局 capacity 守门，两层上限不冲突。

### 二、P0对抗点——一个结构性未覆盖场景

**场景：backlog 被耗尽时，并发自然降到20以下，不触发任何新补位**

actuator日志末段（13:36以后）反复显示：
```
parent_backlog_empty ... pending: {v4:0, k3:0} ... deficit: 0 ... reason: queue_empty
```

当 `manifest_id: auto-refill-proof-20260813` 的 parent backlog 消耗完毕后，parent running 从20逐渐降到12、11……队列始终是 `queue_empty`，故 `refill_required=false`，controller 不产生任何补位请求。这是**正确行为**——没有工作就不造工作。

然而，这也意味着**"有真实backlog时持续20"的证明边界是明确的**：
- backlog存在时：PASS（机械代码路径已覆盖）
- backlog消耗完后：running自然衰减，这不是缺陷，是设计意图

关键反问：**如果新 backlog 以滚动方式不断到来（例如通过第二次 import_manifest），机制是否能重新触发持续20？**

从代码路径看：`parent_manifest_importer.import_manifest` 末尾强制调用 `schedule_run`，这会立即触发 `drain_requested → queue_sync_ledger → recompute`，检测新的 DISPATCHABLE 包，重新建立 deficit 并提交 headless wave。这条路径是代码可证的。但本轮**没有留下"第二次 import 触发第二波 sustained-20"的日志证据**——这是唯一无法从当前日志链中机械验证的部分。

### 四、最终判定

本轮改动（`refill_controller_v2.py`、`refill_consumer_v2.py`、`parent_manifest_importer.py`）在代码层面**真正修复了有真实 backlog 时应触发持续20的逻辑路径**，不是口头补位。actuator日志中存在至少一次真实backlog dispatch的机械证据。

主要未覆盖场景（R1）是滚动多轮 backlog 的端到端实测，但代码路径分析显示机制是完整闭环的。在此基础上判定：**P0修复有效，R1作为后续可观测项保留**。
