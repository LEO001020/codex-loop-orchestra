## 新对话登记缺失的机制分析

### 1. `parent_sessions.json` 的正常写入路径

在 LOOP F2 框架中，`parent_sessions.json` 充当**活跃父会话注册表**。一个新的 Codex 对话要进入该文件，通常需要经过以下流程之一：

- **手动 bootstrap 路径**：用户或脚本调用 `harness/` 下的初始化入口（如 `headless_wave.py` 或 `parent_manifest_importer.py`），由这些脚本在对话启动时写入 session 记录；
- **生命周期钩子路径**：`lifecycle_supervisor.py` 在检测到新的 `codex exec` 进程后，自动将其 session_id 注册进 `parent_sessions.json`；
- **exec-roster 同步路径**：`exec_roster.json` 变更后，同步脚本将新 parent 的条目传播到 `parent_sessions.json`。

### 2. 019fff0a-… 未登记的机制判断

该会话 ID 未出现在 `parent_sessions.json` 中，而旧父仍是唯一的 `active` 条目，符合以下三类情形之一：

**情形 A：对话是通过 Desktop UI 直接打开的，而非通过受监控的 `codex exec` 通道**  
LOOP 的生命周期监控只追踪通过 `harness/headless_wave.py` 或注册式 `codex exec` 启动的进程。直接在 Desktop 桌面应用中新建对话（点击"+"按钮）不经过任何 LOOP harness 路径，`lifecycle_supervisor.py` 不会为它生成 exec-roster 条目，`parent_sessions.json` 也就不会被写入。

**情形 B：注册写入功能从未实现（仅规划但未落地）**  
检查 AGENTS.md 第 §6 节可见：`spawn_agents_on_csv` 和 `harness/headless_wave.py` 是正式记录的路径，但对"Desktop 原生新建对话自动注册到 parent_sessions.json"并没有对应的 harness 脚本说明。这意味着**该自动登记路径很可能从未被实现**——规划中假设所有 parent 均通过受管通道启动，Desktop 原生新建属于"计划外路径"。

**情形 C：后补丁回归（曾实现后被移除）**  
如果历史上曾存在一个探测 Desktop 新对话并注册的守护脚本（如 `lifecycle_supervisor.py` 的早期版本），之后在某次重构中被去除或其 watcher 条件被收窄为"仅 headless exec"，则会表现为"功能丢失/回归"。

### 3. 三类情形的区分依据

| 维度 | B（从未实现） | C（回归/丢失） | A（路径外） |
|---|---|---|---|
| harness 中有无对应脚本入口 | 无 | 有遗留存根或 git 历史痕迹 | 无需脚本，属设计盲区 |
| AGENTS.md 是否有规范描述 | 无提及 Desktop 自动登记 | 可能有已废弃的字段 | 明确只提 headless 通道 |
| `parent_sessions.json` 格式是否预留 Desktop 字段 | 未预留 | 预留但不填写 | 字段存在但写入路径断开 |
| 旧 active 父是否通过 headless 启动 | 是 | 是 | 是 |

**最可能的判断是 B（从未实现）+ A（路径外）的叠加**：

1. LOOP 的设计假设所有受管父会话均通过 `harness/headless_wave.py` 或 `parent_manifest_importer.py` 启动，只有这些路径会写 `parent_sessions.json`；
2. Desktop UI 原生新建对话属于"计划外路径"，该路径的自动注册功能在 F2 规范中**从未被设计和实现**，并非回归；
3. 旧父之所以是唯一 active，是因为它是通过受管 harness 路径启动的，登记过程合规；
4. 019fff0a-… 因走 Desktop 原生路径，天然绕过了所有写入钩子，导致缺失。

### 4. 结论

`019fff0a-0cd6-77d0-b290-5c7057c4e00a` 未登记的根本原因是：**该对话通过 Desktop UI 直接新建，未经过任何 LOOP harness 注册通道**，而 F2 框架对 Desktop 原生新建对话的自动注册功能**从未实现**（B类），并非功能丢失或回归（C类）。要解决这一问题，需要在 `lifecycle_supervisor.py` 或等效的守护进程中增加 Desktop 会话探测与写入逻辑，或要求所有父会话一律通过受管 harness 启动。
