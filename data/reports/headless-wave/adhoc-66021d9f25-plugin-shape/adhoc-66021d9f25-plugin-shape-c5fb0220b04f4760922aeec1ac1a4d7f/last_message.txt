### Hook宿主契约分析

根据对 `E:\codex-LOOP\codex-loop-s-f2` 目录下钩子配置的只读分析，当前Hook系统的运作契约如下：

#### 1. Hook事件与机制
系统中核心Hook机制由 `hooks/` 目录下的 Python 脚本实施，其中 `sol_tool_gate.py` 扮演最为关键的 `PreToolUse` 门控角色（参见 `AGENTS.md` §8），该机制确保在非规划（Planning）、非裁决（Adjudication）或非发布确认（Release Finalize）阶段，根会话（Sol）无法直接执行文件搜索、批量读取或 Shell 操作。

#### 2. Matcher与契约处理
`sol_tool_gate.py` 通过以下维度实施过滤：
- **GATED_TOOLS 列表匹配**：检测根会话发起的工具名是否包含 `shell`、`search`、`read_many_files` 等高风险工具前缀（不区分大小写）。
- **LOOP 状态判别**：`loop_state(root)` 函数由 `data/progress_ledger.json` 中的 `loop_state` 键值决定，若该值缺失，则根据所有 packet 的状态（`ADJUDICATION_STATES` vs `TERMINAL_STATES`）进行动态计算。
- **Agent/Role 旁路**：`child_roles`（如 `worker`, `verifier`）发起的工具调用通过判定逻辑旁路（`if role in CHILD_ROLES: return 0`），即明确指派的子 Agent 不受门控限制。

#### 3. 输入处理（Stdin/Stdout/Exit Code）
- **stdin**：钩子脚本预期接收一个包含 `tool_name`、`agent_type` 和 `cwd` 的 JSON 负载。
- **stdout 协议**：钩子决定拒绝时，通过标准输出打印 JSON 对象：`{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", ...}}`。
- **退出码**：钩子始终以 `exit 0` 退出，即使用户操作被拒绝，该行为本身被视为成功处理，而非执行错误。

#### 4. 生命周期管理（SessionStart/Resume/Clear/Compact）
根据 `data/events.ndjson` 中的事件格式记录：
- **startup 和 resume**：通过 `SubagentStart` 事件记录，关联 `session_id`、`agent_id` 和任务名称。
- **Clear/Compact**：由数据清理脚本在 `data/` 进行，目前并未在 `PreToolUse` 钩子中看到直接的清除或压缩接口，这些路径作为底层持久化状态存放在盘上。

#### 5. PostToolUse 与 Agent 协作
当前Hook架构中 `sol_tool_gate.py` 仅覆盖 `PreToolUse` 事件。系统利用 `subagent_lifecycle.py` 管理子 Agent 的生命周期，确保每个任务（如：`任务名：侦查harness目录结构`）作为独立的 Agent 运行，从而在 `PreToolUse` 门控中获得合法角色旁路权限。

该合同模型依赖：基于 `loop_state` 的动态授权 + 基于 `role`（Agent 类型） 的鉴权 + 自动化审计（`events.ndjson`）。
