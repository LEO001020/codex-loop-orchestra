### Cold-start mode behavior — compatibility constraints

**Current active routing mode:** `cold_start` (set in both `config/orchestration_policy.toml` and `config/orchestration_policy_v2.toml`, `[routing].mode = "cold_start"`).

**Critical compatibility finding:** In cold_start mode, the `trigger_eval.py` (v1) is used as the evaluator. Its `PREDICATES` dict does **not** include the v2 `ek_v2_additions` rules (`timeout_first`, `timeout_second`, `short_result_invalid`, `stale_revision_publish`, `l2_verifier_exec_failed_once/twice`). These predicates are only registered in `trigger_eval_v2.py`.

The cold-start passthrough collapse (`passthrough_enabled=false`) at `trigger_eval.py:303–304` upgrades every non-`direct_l3` action to `direct_l3`, so the absence of `timeout_first`/`timeout_second` predicates has **no functional impact** on routing in cold-start: even if they were present and fired `pass`, they would be upgraded to `direct_l3` anyway.

The t37 budget itself is **state-machine-level enforcement**, not trigger-table enforcement. It fires in `apply_event()` regardless of routing mode:
- `statemachine.py` v1: `if num == 37: count, exceeded = bump_timeout_retry_counter(pid)` — active in cold_start.
- `statemachine_v2.py`: identical guard, active in layered.

The t37 statemachine transition is present in **both** `statemachine.py` (v1, line 62) and `statemachine_v2.py` (line 140), so rollback to cold_start preserves the retry edge.

### retry.py interaction with t37 budget

`harness/retry.py` handles the **retry classification** path (`FAILED → DISPATCHABLE`, t9), not the timeout path (t37). The timeout class in `retry_classes.yaml`:

```
name: timeout
pattern: '(?i)(timed?[ _-]?out|deadline exceeded|job_max_runtime|SIGALRM|ETIMEDOUT)'
action: retry
max_retries: 2
backoff_base: 5
backoff_cap: 60
```

This is for exec failures matched as timeouts (`FAILED` state), not for the watchdog-fired `TIMED_OUT` state. The watchdog transition (t5: `RUNNING → TIMED_OUT`) bypasses `retry.py` entirely — it fires directly from `watchdog()` in-process. The t37 budget counter (`data/timeout_retry_counters.json`) is separate from the `data/.breaker.json` session circuit breaker and the `run_level_retry_budget = 6` run-level budget tracked by `retry.py`.

**Important constraint:** The `retry.py` `timeout` class has `max_retries: 2` and the run-level budget is 6 — but this is orthogonal to the t37 counter. A packet can consume both budgets independently if it first fails (FAILED) with a timeout-class error (consuming from `retry.py`'s budget), and also gets watchdog-fired (consuming from `timeout_retry_counters.json`).

### Statemachine v1 (cold_start) t37 budget guard — full path

1. Watchdog detects RUNNING packet exceeds `job_max_runtime_seconds` → emits `timeout` event → applies t5 in-place → packet is `TIMED_OUT`.
2. On next step, if a `retry_dispatch` event arrives for that packet (emitted by `harness/retry.py` via `triggers_v2.yaml` `retry_dispatch_timeout` event, or by the trigger/dispatch layer), `apply_event()` hits `key = ("TIMED_OUT", "retry_dispatch")` → `num == 37`.
3. `bump_timeout_retry_counter(pid)` increments `data/timeout_retry_counters.json[pid]` and checks `> TIMEOUT_RETRY_MAX (1)`.
4. First call: count=1, not exceeded → packet transitions to `DISPATCHABLE`, attempts incremented.
5. Second call: count=2, exceeded → `to_dead_letter()` with reason `timeout_retry_exhausted`, cap=1 → packet transitions to `DEAD_LETTER`.

In cold_start mode, `statemachine.main()` falls through to v1 code (it only routes to `statemachine_v2.main()` if `routing_mode == "layered"`). The identical t37 guard is active in v1.

### Summary

**Budget:** `TIMEOUT_RETRY_MAX = 1` — single retry for watchdog-fired timeouts; second timeout dead-letters to DLQ, then t38 duty triage gives one zero-Sol pass before final `DEAD_LETTER`.
