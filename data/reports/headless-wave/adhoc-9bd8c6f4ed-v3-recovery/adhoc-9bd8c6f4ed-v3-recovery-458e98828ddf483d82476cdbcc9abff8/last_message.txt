### 核心问题：常驻 Codex vs. Receipts+Workspace State 可恢复性

这是两种完全不同的架构取舍：

**方案 A：常驻 Codex 进程**
- 保持 Codex 进程持续运行（后台 daemon）
- 会话状态驻留在内存中，无需序列化
- 依赖：进程存活 = 状态存活
- **问题**：进程崩溃、重启、容器回收后状态丢失；资源占用持续；不适合 VPS 低资源场景

**方案 B：Receipts + Workspace State 可恢复性**
- 将每次 agent 执行的输入/输出/工具调用序列化为 receipt 文件（通常是 JSONL/JSON）
- 将 workspace 状态（文件变更、环境变量、任务进度）持久化到磁盘
- 进程退出后可通过 receipt 重放或 checkpoint 恢复
- **依赖**：需要明确的 `session_id` → receipt 文件映射；需要 workspace diff 快照

### 判断结论

根据 VPS 场景的约束（资源有限、进程可能随时终止、需要跨会话任务继续），**推荐方向是 Receipts+Workspace State 可恢复性**而非常驻进程。理由：

- VPS 环境进程生命周期不可靠（OOM killer、SSH 断线、容器重启）
- 常驻进程需要 systemd/supervisor 管理，增加运维复杂度
- Receipt-based 恢复天然支持审计、回放、断点续传
- 如果当前 V3 代码中缺乏 `session_id` → 持久化文件的完整映射，这就是需要实现的核心缺口
