### ESTIMATED 是否能压制补位债务？

**三道防线逐一验证：**

**防线 1：时间戳 5 秒门限（代码已引用）**
Observer 响应体必须包含当前 `timestamp`（Unix 秒），与 `time.time()` 之差 >5 秒即返回 `None`，回退到本地 roster。无论 freshness 是 `ESTIMATED` 还是 `LIVE`，超时快照均被丢弃。

**防线 2：Root 精确匹配**
Controller 将自身 `self.paths.root.resolve()` 与 observer 响应的 `root`/`windows_root` 字段做 casefold+正斜杠归一化后集合查找，不匹配则返回 `None`。

**防线 3：`max()` 覆写语义**
即使 observer 通过了前两道门，overlay 代码用 `max(0, int(...))` 赋值：

```python
counts[pool]["running"] = max(0, int(observed_pools.get(pool, 0) or 0))
```

这是**直接覆写**（不是 `max` 取较大值），不是"叠加"。如果 observer 返回 `{"pools": {"v4": 0, "k3": 0}}`（典型 ESTIMATED 场景，仅有 rollout 估算但没有权威 running 行），running 会被置 0，`required = running < target` 为真，`raw_debt` 正数，**补位债务反而会升高，不会被压制**。

**ESTIMATED 触发时 monitor server 的实际行为（来自前波测试和报告）：**
- `freshness = "ESTIMATED"` 当且仅当 `authoritative_running == 0`（只有 rollout 估算行，无 native roster 证明），此时 `pools` 字段仍从 rollout 估算得出
- 若 rollout 估算给出 N 个 running agent，overlay 会将 `counts[pool]["running"]` 设为 N，这**不会低于**本地 roster 的观测（本地 roster 的 TTL 超过 1800 秒则已被 v2 TTL 过滤）

**唯一可能的错误方向（覆写而非取最大）：**
理论上，如果本地 native roster 显示 5 个 running，而 ESTIMATED observer 快照只看到 3 个（估算偏低），覆写后 running=3 会增大 debt。这是**虚增债务**，而非压制债务——方向相反，对 refill 是保守安全侧。

### 安全验收规则（针对 ESTIMATED 的最小充分条件）

ESTIMATED 快照被接受且不压制债务的充分条件：
1. `doc["timestamp"]` 距当前时间 ≤5 秒（5 秒门限）
2. `doc["root"]` 或 `doc["windows_root"]` 与 controller root 精确匹配
3. observer 返回的 `pools` 字段计数 ≥ 实际有效 running 数（保守方向）

条件 3 在 ESTIMATED 场景（authoritative_running=0，仅 rollout 估算）下，估算值往往 ≥ 本地 roster 过期值，overlay 是安全的。若估算偏低，结果是虚增债务（触发更多补位），而非抑制债务。

**结论：ESTIMATED 数据不能错误地压制补位债务。现有三道防线（时间戳门限 + root 匹配 + 覆写语义）共同保证 fail-open refill。**
