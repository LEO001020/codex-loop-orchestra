任务名：JSON哈希交集复核

## 分析：冻结哈希对象类别能否同时满足 p5-pc6-alpha-source/v1 JSON 要求

### 核心问题拆解

问题要求区分两件事：
1. **字节内容**（哈希所指向的数据对象里面存放的实际字节）
2. **哈希值本身**（那串十六进制/base64 字符串）

以及：为什么"命名一个 plan hash"无法满足"source-file hash + JSON 可解析"两个条件。

---

### 已知对象类别分类

**32985 个 Parquet normalized blobs**

这些对象的字节内容是 Parquet 二进制格式。Parquet 文件以魔数 `PAR1`（4字节）开头和结尾，内部是列式压缩二进制编码。任何标准 JSON 解析器都会在读取第一个字节时失败——`P`（0x50）不是 `{`、`[`、`"`，也不是合法 JSON 起始符。因此：

> 32985 个 Parquet blob 的字节内容**不可能**解析为有效 JSON，更不可能满足 `p5-pc6-alpha-source/v1` schema 所要求的非空 JSON 对象结构。

**剩余 11 个对象（code/manifests/aggregate hashes）**

这 11 个被归类为代码、清单或聚合哈希，**没有一个是 source 对象**。它们的字节内容可能是：
- 代码文件（Python/JS 等），起始符为关键字或注释，非 JSON
- 清单文件（YAML/TOML 等），同样不是 JSON
- 聚合哈希记录，通常是哈希列表或键值结构，即便碰巧是 JSON 格式，其 schema 也不会匹配 `p5-pc6-alpha-source/v1` 所要求的 source-file 结构字段（如 `source_path`、`content_hash`、`version` 等源文件元数据字段）

结论：这 11 个对象均非 source 对象，其字节内容不满足 source/v1 JSON schema 要求。

---

### 为什么"命名一个 plan hash"无法满足"source-file hash + JSON 可解析"

这里有一个根本性的类型混淆需要澄清：

**哈希值 ≠ 哈希所指向对象的字节内容**

| 概念 | 是什么 | 示例 |
|---|---|---|
| 哈希值（hash value） | 指向对象的标识符字符串 | `sha256:a3f7...` |
| 对象字节内容 | 该标识符指向的实际数据 | Parquet 二进制、代码文本等 |

当系统要求"source-file hash"时，它要求的是：**某个对象的哈希值，且该对象的字节内容能通过 JSON 解析并符合 source/v1 schema**。这是两个必须同时成立的条件：

- **条件 A**：该哈希值所指向的对象，其字节内容是合法的非空 JSON
- **条件 B**：解析出的 JSON 结构符合 `p5-pc6-alpha-source/v1` schema

"命名一个 plan hash"只是提供了**一个哈希值字符串**，而 plan 对象的字节内容是计划/任务描述数据，其格式（即便是 JSON）也不会符合 source-file schema——plan 对象缺少 source-file 所需的语义字段。

换句话说：哈希值本身只是一个定位符，**不携带被定位对象的字节内容**。用一个 plan hash 来充当 source-file hash，就好比用一张地图的编号来声称自己拥有地图所描述的地形——编号本身不是地形。

---

### 结论

所有 32996 个已知冻结哈希对象（32985 Parquet + 11 code/manifests/aggregate）中，**不存在任何对象的字节内容同时满足**"非空 JSON 可解析"且"符合 p5-pc6-alpha-source/v1 schema"这两个条件。命名一个 plan hash 无法绕过此约束，因为合规性验证针对的是哈希所指向对象的字节内容，而非哈希标识符字符串本身。
