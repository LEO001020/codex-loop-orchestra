### STEPS

排练在隔离临时目录下执行两次独立运行（run `a` 与 run `b`），每次均从相同的确定性 v2 起点开始，不共享任何状态。

#### Step 0 — 构建空 v2 基线库（`make_v2` 函数）

```
1. 新建临时目录 root/{a,b}/
2. apsw.Connection(root/research.sqlite) — WAL + FULL synchronous
3. 执行 research_schema.sql
   → 创建 schema_meta(singleton=1, schema_version=3, ...) — 注意：schema 初始写入 version=3
   → 重写为 version=1: UPDATE schema_meta SET schema_version=1 WHERE singleton=1
4. 执行 P5_STATISTICAL_EXECUTION_LAYER_SCHEMA_MIGRATION_V1.sql
   → 创建 8 张 v2 authority 表（authority_proposals, authority_transitions,
      logical_trials, trial_attempts, owner_conditional_delegations,
      delegation_redemptions, owner_delegation_revocations, amendment_registrations）
   → 最末行: UPDATE schema_meta SET schema_version=2 WHERE singleton=1 AND schema_version=1
5. 断言: SELECT schema_version FROM schema_meta == (2,)
```

**v2 起点状态**：8 张 authority 表均为**空**（零行），这是迁移脚本的关键前提。

#### Step 1 — 调用 `ResearchDB.migrate()`（排练迁移）

```python
db = ResearchDB(root)
result = db.migrate(
    migration_id   = 'p5-direct-repair-v3-' + label,  # 'a' 或 'b'
    from_version   = 2,
    to_version     = 3,
    script_path    = P5_AUTHORITY_SCHEMA_V2_TO_V3.sql,
    evidence_dir   = root / 'evidence',
)
```

`migrate()` 内部完整流程：

```
a. 验证 schema_version == from_version(2)
b. 检查 migration_id 无重复（UNIQUE 约束防御重放）
c. PRAGMA integrity_check — 必须返回 'ok'
d. BEGIN IMMEDIATE → 写入 maintenance_state.active=1
e. VACUUM INTO evidence/{id}-pre.sqlite（前快照）
f. BEGIN EXCLUSIVE → 执行迁移脚本（见 v2→v3 迁移逻辑）
g. UPDATE schema_meta SET schema_version=3
h. INSERT INTO migration_audit
i. COMMIT
j. PRAGMA integrity_check — 必须返回 'ok'
k. VACUUM INTO evidence/{id}-post.sqlite（后快照）
l. 验证 post.sqlite schema_version==3 且 integrity_check=='ok'
m. BEGIN IMMEDIATE → maintenance_state.active=0（维护退出）
n. 返回 {status:'PASS', maintenance_exited:True, script_sha256:...}
```

#### Step 2 — v2→v3 迁移脚本核心逻辑

```sql
-- 1. EMPTY GATE: 用 TEMP TABLE + CHECK(n=0) 验证全部 8 张表均为零行
--    若任意表有行则 CHECK 违规 → 事务 ABORT（fail-closed）
CREATE TEMP TABLE _p5_v3_empty_gate(n INTEGER NOT NULL CHECK(n=0)) STRICT;
INSERT INTO _p5_v3_empty_gate SELECT
    (SELECT count(*) FROM authority_proposals) +
    (SELECT count(*) FROM authority_transitions) + ... ;  -- 8 表求和
DROP TABLE _p5_v3_empty_gate;

-- 2. DROP 8 张 v2 表（因已确认为空，无数据损失）
DROP TABLE trial_attempts, logical_trials, delegation_redemptions, ...;

-- 3. CREATE 8 张 v3 表（与 authority_schema_v3.sql 结构等同）
--    关键升级点：
--    - authority_proposals 增加 resource_policy_sha256 列
--    - authority_transitions 增加 resource_policy_sha256 列
--    - owner_conditional_delegations: state CHECK 改为只允许 'ACTIVE'
--      （v2 允许 'ACTIVE'|'OWNER_DELEGATION_REVOKED'，v3 仅 'ACTIVE'）
--      并增加 resource_policy_sha256 NOT NULL 列
--    - delegation_redemptions 增加 resource_policy_sha256 列
--    - amendment_registrations: 扩展 amendment_id IN ('C','D','A','B')
--      （v2 只有 'C','A','B'），registration_ordinal BETWEEN 1 AND 4
--      （v2 最大 3），增加多个 ledger/session/state 字段

-- 4. CREATE TRIGGER / INDEX（共 ~15 个 trigger + 3 个 partial unique index）
```

#### Step 3 — verify() 断言

### HASH_ASSERTIONS

排练成功后，以下三个哈希值在任何符合规范的运行环境中**必须相等**（run a = run b = 生产预期值）：

#### H1: `schema_digest`（schema_dump 的 SHA-256）

由 `sqlite_schema` 中所有非 `sqlite_*` 对象的 `(type, name, tbl_name, sql)` 四元组 JSON 序列化后的 SHA-256 决定。

**决定性因素**：
- v3 迁移脚本完全确定（DROP + CREATE 顺序固定）
- SQLite `sqlite_schema` 的排列顺序由 DDL 执行顺序决定，脚本为 canonical 顺序
- 触发器和索引与表一一对应

**预期**：两次运行（a、b）的 `schema_digest` 完全相同。若不同，说明迁移脚本含有非确定性元素（如 `IF NOT EXISTS`），但迁移器已明确拒绝 `IF NOT EXISTS`。

#### H2: `script_sha256`（迁移脚本文本的 SHA-256）

由 `ResearchDB.migrate()` 计算：
```python
script_sha = sha256_text(script)  # sha256(script.encode('utf-8'))
```

此值作为固化证据写入 `migration_audit.script_sha256`，用于生产一致性验证。

**关键约束**：
- 脚本中不得含 `IF NOT EXISTS`（migrate() 主动拒绝）
- 脚本内容字节级等同于 `P5_AUTHORITY_SCHEMA_V2_TO_V3.sql` 的磁盘内容

#### H3: `projection_sha256`（来自 verify()）

```python
projection_sha256 = sha256_text(canonical_json(current))
```

其中 `current = {table: [] for table in DOMAIN_TABLES}`（全空 domain 表）。

**预期**：对空库该值为纯 schema 结构的确定性函数，与 run a / b 一致。

#### 三元组断言

```python
assert a == b  # (schema_digest, script_sha256, projection_sha256)
```

### FAILURE_CASES

| 编号 | 失败场景 | 触发机制 | 预期错误 |
|---|---|---|---|
| F1 | **v2 库中有非零权威行** | migration 脚本 TEMP TABLE CHECK(n=0) 违规 | `apsw.ConstraintError` → migrate() ROLLBACK，maintenance_state 保持 active=1（需手工清除） |
| F2 | **重复执行相同 migration_id** | `migration_audit` PRIMARY KEY UNIQUE | `FailClosed("migration id already used")`，脚本拒绝第二次运行 |
| F3 | **schema_version 不是 2** | migrate() 前置检查 `current != from_version` | `FailClosed("migration source version mismatch: N")` |
| F4 | **迁移前 integrity_check 失败** | migrate() 前置 `PRAGMA integrity_check` | `FailClosed("pre-migration integrity check failed")` |
| F5 | **迁移脚本含 IF NOT EXISTS** | migrate() 明确检查 `"IF NOT EXISTS" in script.upper()` | `FailClosed("migration scripts may not use IF NOT EXISTS")` |
| F6 | **verify() authority 表缺失** | `_verify_authority()` 中 required 集合检查 | `{"status":"FAIL","missing_tables":[...]}` |
| F7 | **amendment 顺序/哈希偏移** | `_verify_authority()` 的 `exact[]` 列表比对 | `errors=["AMENDMENT_IDENTITY_ORDER"]` |
| F8 | **rebuild_check diff != 0** | live projection 与事件重建 projection 不一致 | `{"status":"FAIL","diff":1}` |
| F9 | **schema_digest 在两次运行间不同** | 最终 `assert a == b` | `AssertionError: (a_tuple, b_tuple)`，说明 DDL 含非确定性元素 |
| F10 | **DB 权限不足（文件系统）** | `_open()` 时 APSW open flags `READWRITE` | `apsw.CantOpenError: unable to open database file` |
| F11 | **WAL 模式漂移** | `_open()` 后检查 `PRAGMA journal_mode` | `FailClosed("journal mode drift: delete")` |
| F12 | **FULL synchronous 漂移** | `_open()` 后检查 `PRAGMA synchronous` | `FailClosed("synchronous drift: N")` |
| F13 | **runtime 版本过旧**（APSW < 3.53.4 或 SQLite < 3.51.3） | `runtime_info()` 中版本比对 | `RuntimeGateFailed("runtime too old: ...")` |
| F14 | **网络文件系统**（NFS/CIFS/sshfs） | `filesystem_info()` fstype 检查 | `FailClosed("network filesystem forbidden for SQLite WAL: nfs")` |
| F15 | **foreign_key_check 非空**（迁移后 FK 违规） | verify() 中 `PRAGMA foreign_key_check` 断言 | verify['foreign_key_violation_count'] > 0 → status='FAIL' |
| F16 | **owner_conditional_delegations 中 state 不是 'ACTIVE'**（v2→v3 CHECK 改变） | v3 CREATE TABLE CHECK(state='ACTIVE') | 若迁移前 v2 库有状态为 'OWNER_DELEGATION_REVOKED' 的行，empty-gate 先拦截（F1）；若 empty gate 被绕过则 CHECK 违规 |
| F17 | **maintenance_exited 为 False** | migrate() 最后 maintenance_state 清除失败 | `assert result['maintenance_exited'] is True` 失败，排练报告不通过 |

### 补充说明

**authority rows zero 验证**路径：
- 迁移脚本 empty gate（`CHECK(n=0)` temp table）是第一道防线
- `_verify_authority()` 返回 `table_counts` 字典，排练后所有 8 张表应为 `0`
- `verify['authority_verify']['authority_row_count']` == 0

**DB 权限边界**：
- 排练需要对临时目录的 `READWRITE|CREATE` 权限（initialize 路径）
- `os.chmod(root, 0o750)` + `os.chmod(db_path, 0o640)` 在 Linux/Mac 上强制执行
- Windows (`os.name == 'nt'`) 下 `fsync_directory` 为 no-op，`file_lock` 改用 `msvcrt.locking`
- 测试文件系统覆盖（`RESEARCHCTL_ALLOW_TEST_FILESYSTEM=1`）绕过 `/data/k3/research` 路径和 ext4 检查，是排练可在任意目录运行的必要条件
