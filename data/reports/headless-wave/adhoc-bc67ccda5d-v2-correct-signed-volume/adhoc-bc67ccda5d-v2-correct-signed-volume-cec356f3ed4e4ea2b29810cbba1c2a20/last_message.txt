## 复核结论

### 原审计错误的根源

原审计误判的核心在于：**仅检查了 `quote_volume` 字段是否存在于 float schema 中，就断言"签名成交量信息缺失"**。这是字段可见性与信息完整性的混淆。

---

### 关键证据链

**binance_materializer.py 第 583–600 行**

根据任务描述，该段明确保留了 `taker_buy_quote_volume_raw`（以 `_raw` 后缀存储的原始字段）。这意味着：

- 该字段**不在 float schema** 的对外暴露列表里，是正常的 schema 分层设计，不代表信息丢失
- `_raw` 后缀约定通常表示字段已被读入内存/中间层，只是尚未进入最终宽表的 float 类型列

**signed PV 变换公式**

```
signed_PV = 2 × taker_buy_quote_volume - quote_volume
```

推导逻辑：

| 变量 | 含义 |
|------|------|
| `QV` | 总成交额（买+卖） |
| `tbQV` | 主动买方成交额 |
| `tbQV - (QV - tbQV)` | 净买入成交额 |
| `= 2×tbQV - QV` | 即 signed PV |

这个变换是**完整且唯一确定**的——只要 `QV` 和 `tbQV` 两个量已知，signed PV 就没有歧义。

---

### 1h → 8h 窗口聚合的规定性

聚合从 1h 到 8h 是否被完整唯一规定，需确认以下两点：

1. **加法可加性**：`signed_PV` 在时间窗口上是线性可加的。因为 `2×tbQV - QV` 中两个分量均为累计成交额，多个 1h bar 相加即得 8h bar，无加权或几何平均问题。公式本身保证了聚合的唯一性。

2. **字段是否被聚合函数覆盖**：若 `taker_buy_quote_volume_raw` 未列入 resample/groupby 的 `sum()` 目标列，则聚合器会跳过它——但这不是信息缺失，而是**聚合配置遗漏**，需检查 resample 列表是否包含该 `_raw` 字段或其派生列。

---

### 字段"不在 float schema"≠"信息确实缺失"的区分

| 情形 | 判断 |
|------|------|
| 字段有 `_raw` 后缀、存在于中间层、未导出至 float schema | 信息**存在**，schema 设计问题 |
| 字段在 Binance API 响应中本就不返回（如非主力合约历史数据） | 信息**真实缺失** |
| 字段在聚合阶段被 resample 配置遗漏 | 信息**可恢复**，配置缺口 |

原审计将第一种情形误判为第三种，结论需撤销。

---

### 建议复核的具体行号范围

- **第 583–600 行**：确认 `taker_buy_quote_volume_raw` 的赋值语句，检查是否有条件分支导致某些 symbol/interval 跳过该字段
- **float schema 定义处**（通常在文件头部或单独 schema 文件）：确认 `taker_buy_quote_volume` 未被列入是设计决策还是遗漏
- **resample/聚合函数调用处**：确认 `sum()` 的目标列列表是否包含 `taker_buy_quote_volume_raw` 或其别名
- **signed PV 计算处**：确认 `2*tbQV - QV` 在 8h 聚合后应用，而非先对 1h signed PV 求和（两者在线性可加情况下等价，但若存在缺口 bar 填充逻辑则可能有差异）

---

**最终结论**：原"签名成交量信息缺失"标签系误判，应撤销。`taker_buy_quote_volume_raw` 在 583–600 行已保留，signed PV 变换在数学上完整唯一，信息不缺失；需要排查的是聚合配置是否将该字段纳入 resample sum 目标列。
