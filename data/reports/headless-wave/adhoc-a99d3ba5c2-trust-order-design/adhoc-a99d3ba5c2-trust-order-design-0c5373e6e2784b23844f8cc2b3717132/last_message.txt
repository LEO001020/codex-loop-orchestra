### 为什么 owner anchor 只能在 fresh-k3 pretrust PASS 后安装权威事件（核心论证）

这是理解整个 DAG 强制顺序的关键：

**owner anchor 是供应链信任根，但其自身在安装时即面临替换攻击。**

具体攻击路径（`lib/common.sh` L124-150，`03` L43-58，`09_OWNER_CEREMONY_PREREQUISITES.md` "Filesystem precondition"）：

1. 默认 anchor 路径 `/data/k3/research/owner` 的祖先 `/data/k3` 由 agent(k3) 所有。
2. 在 O4 剥权完成（fresh-k3 PASS）**之前**，k3 拥有对 `/data/k3` 的写权限。
3. k3 可以重命名 `/data/k3/research` → 任意路径，然后创建一个同名目录并放入自己的 Ed25519 公钥作为伪造的 owner_ed25519.pub。
4. `03` 的 F7-23 将对这个被替换的公钥验证 owner 签名，永远通过（因为 k3 用自己的私钥签了 manifest）。
5. 所有精确集检查、hash 核验因此变得没有意义——manifest 本身由 k3 控制。

**`assert_owner_anchor_trustworthy` 的逻辑**（`lib/common.sh` L127-148）：
```
遍历 anchor → parent → / 的每一个祖先：
  若 owner = AGENT_USER → die (F10-4)
  若 world-writable → die
  若 group-writable 且 agent 在该组 → die (F-B)
```

因此：
- **O2（安装 anchor）必须在 anchor 路径祖先链已被 reparent 到 root 之后**，或使用 `P5_OWNER_ANCHOR_DIR` 指向 agent 树之外的路径（如 `/etc/p5/owner`）。
- **O3（信任 anchor 并验证签名）必须在 O4 完成（k3 已无法写 anchor 祖先）之后才能让"信任"成立**。即便 O2 以 root 安装了 anchor，只要 k3 在 O4 之前仍有祖先目录的写权限，就可以在 O3 读取 anchor 前完成替换攻击。
- **fresh-k3 pretrust PASS（O5）是 anchor 信任链的负面证明终点**：它从全新登录的 k3 视角证明 anchor 目录不可写（`07` L55-57），此证明才封闭攻击窗口。
- Owner 仪式中的 C/D 签署（O6-O7）产生不可回滚的权威事件，因此 O5 的 PASS 必须先于任何权威事件，否则这些权威事件的信任基础可能建立在一个 anchor 已被替换的环境中。
