### I1：可信任性（Integrity of ceremony tooling）

**裁定：PASS**

证据链完整且无矛盾：

**1. Deterministic C→D→root 顺序（S21 / T01 / T03 / T08）**

`owner_ceremony.py` 的 `command_make_direct` 在构建 D 请求时强制调用 `require_receipt(args.c_receipt, "C")`，`command_materialize_root` 则同时强制 `require_receipt(args.c_receipt, "C")` 和 `require_receipt(args.d_receipt, "D")`。`authority_store.register_delegation` 在数据库层进行额外验证：

```python
expected = [("C", AMENDMENT_C_SHA256, "INTERACTIVE_OWNER_SIGN", "APPLIED"),
            ("D", _amendment_d_sha256(), "INTERACTIVE_OWNER_SIGN", "APPLIED")]
if observed != expected:
    raise FailClosed("EXACT_C_AND_D_DIRECT_OWNER_APPLIED_REQUIRED")
```

静态测试 S21 对源码模式做静态断言；T08 的回归测试证实向后兼容——用一个错误的 C 收据构造 D 请求时工具以非零退出码失败。

**2. Late-bound 字段（S17 template / T04）**

冻结模板 V4 中 `resource_policy` 标记为 `OWNER_LATE_BOUND_WAVE1_WALL_TIME_EXPIRY_REQUIRED_BY_FROZEN_PROPOSAL`；`pin_required_before_signing` 明确列出 `delegation_id`、`owner_identity`、`issued_at_verified_external_time`、`expires_at`、`owner_session_id`、`parent_delegation_nonce` 六个晚绑定字段均无默认值。`verify_scope()` 在签名前检查所有这些字段是否已填充且不含 `LATE_BOUND` 字符串。T04 回归测试去掉 `--owner-session-id` 参数后工具拒绝执行，证明无默认值保证有效。

**3. Outcome-blind resource policy（T05 / authority_runtime.py）**

`validate_resource_policy` 要求：
- `decision_basis.source == "SEALED_SYNTHETIC_FULL_PATH_BENCHMARK_ONLY"`
- `decision_basis.real_p5_labels_read_before_choice is False`

两者缺一不可，否则抛出 `RESOURCE_POLICY_OUTCOME_DERIVED`。T05 回归测试将 `real_p5_labels_read_before_choice` 改为 `True`，工具拒绝执行，PASS。

**4. Canonical signature bytes（S20 / T02 / T06）**

`write()` 函数调用的是 `Path(path).write_bytes(canonical_json(value))`——写入纯二进制，无尾部换行符。`attach-signature` 和 `verify-signed` 均对 `canonical_json(unsigned_payload)` 字节进行 Ed25519 验证，与运行时 `conditional_delegation.verify_ed25519` 使用完全相同的函数。S20 以源码模式匹配静态验证；T02 对比 `json.dumps(…).encode()` 与磁盘字节；T06 用真实 Ed25519 密钥签名后 T07 调用 `verify-signed` 并断言输出包含 `PASS`。

**5. Execution 双门（execution_gate）**

`command_execute_direct` 和 `command_register_root` 均调用 `execution_gate`，该函数要求同时满足：
- CLI 参数 `--allow-production-execution`
- 环境变量 `P5_OWNER_CEREMONY_EXECUTION=YES`
- 进程不得以 root 身份运行

三个条件缺一即以 `SystemExit` 拒绝。工程任务期间这两个命令均未被调用，manifest 的 `production_mutations_by_engineering_mission` 中 `c_registered`、`d_registered`、`root_registered` 均为 `false`。

**6. Scope exclusions（S22 / S23 / DelegationVerifier）**

模板 V4 的 `allowed_amendment_hashes` 仅含 A 和 B 的 SHA256，C 和 D 被显式排除。`verify_scope()` 和 `DelegationVerifier.verify_signature()` 均以不同路径对此进行检查：
- `set(d.allowed_amendment_hashes) != {A_SHA, B_SHA}` → `ONLY_EXACT_A_B_MAY_BE_DELEGATED`
- `C_SHA in allowed_amendment_hashes` → `D_CAN_AUTHORIZE_C=NO`

`explicit_prohibitions` 包含 `H2、D4、H3、E2、MAINNET、CAPITAL、EXCHANGE_API_KEYS、LIVE_ORDERS、HOME_CAPABILITY_EXPANSION、GCP_CAPABILITY_EXPANSION、GCP_EXPANSION、WAVE2` 等，S23 做静态集合子集验证（PASS）。`scope_assertions` 字段亦明文记录 `root_must_not_authorize_C` 和 `root_must_not_authorize_D` 均为 `true`。

**7. 私钥边界（F01/F02 / machine list / ceremony.py docstring）**

- `owner_ceremony.py` 模块文档开头明文："The tool never opens a private key."
- `invoke-signer` 子命令通过环境变量 `P5_CANONICAL_PAYLOAD_PATH` 和 `P5_SIGNATURE_OUTPUT` 调用外部本地签名器，工具本身不传递、不读取私钥字节。
- `command_attach_signature` 接收的是 base64 编码的分离签名，不接受私钥路径。
- 机器列表 `hard_order` 条目 `private_key_boundary` 明确：私钥留在 owner/admin 设备上，只传输公钥、签名和已签名凭证材料。
- functional_fixtures F01/F02/F03 以 `reject_if_private_key` 对 OpenSSH 和 RSA 私钥格式做拒绝测试（PASS）。

### I7：可审计性（Auditability / non-repudiation）

**裁定：PASS**

每条 authority_store 写入均记录守护进程序列号（`daemon_ledger_sequence`）、守护进程时间戳（`daemon_recorded_at`）、不可变会话 ID（`immutable_session_id`）和认证的对端 UID（`authenticated_peer_uid`），并且每条过渡事件都有独立的 `event_sha256`（对 proposal_id + target_state + ledger_sequence 的哈希）。所有者签名哈希（`parent_owner_signature_hash`）在代币赎回路径中被单独记录。这些字段均由守护进程注入，不依赖产生者提供的时间戳作为授权依据（模块文档注："Producer timestamps and payload role strings are never authorization inputs"）。
