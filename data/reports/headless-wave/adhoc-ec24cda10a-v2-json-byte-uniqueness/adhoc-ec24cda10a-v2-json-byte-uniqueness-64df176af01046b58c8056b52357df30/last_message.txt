## 复核结论：V2 JSON 字节唯一性分析

### 关键发现

**`load_source` 的实现（位于 `pc6_alpha_materializer.py` 第302行）**：

```python
def load_source(raw: bytes) -> dict[str, Any]:
    try:
        source = json.loads(raw)
    except ValueError as exc:
        raise FailClosed("PC6_SOURCE_PARSE_FAILED") from exc
    # 后续仅做语义字段验证，不做规范化序列化
    ...
    return source
```

### 字节唯一性漏洞确认

该函数使用 `json.loads(raw)` 解析，然后对语义字段进行验证，**但不对输入字节做任何规范化处理，也不重新序列化为 canonical 形式**。这意味着以下情形下，多个字节不同的输入可产生语义等价的 `source` 对象：

| 维度 | 示例 | 是否产生字节差异 |
|------|------|----------------|
| 空白字符 | `{"a":1}` vs `{"a": 1}` | ✅ 是 |
| 键顺序 | `{"symbols":{},"schema":"...","decision_grid_ts_utc":[]}` vs 不同顺序 | ✅ 是 |
| 数值词法形式 | `1.0` vs `1` vs `1.000` | ✅ 是（`json.loads` 均解析为 `float(1.0)` 或 `int(1)`） |
| Unicode 转义 | `"BTCUSDT"` vs `"BTCUSDT"` (含 `\uXXXX` 转义) | ✅ 是 |
| 尾部换行/BOM | `{"schema":"..."}` vs `{"schema":"..."}\n` | ✅ 是 |
| `close` 字段：`int` vs `float` | `"close": 1` vs `"close": 1.0` | ✅ 是（代码中接受 `isinstance(bar["close"], (int, float))`） |

### 对"唯一规范 source 对象"要求（需求 A）的影响

**结论：这一漏洞 *确实* 阻塞了需求 A，除非存在外部字节规范化规则。**

具体原因：

1. **`load_source` 返回 Python `dict`，而非字节**。调用方（`alpha_execution.py` 第200行：`source = mat.load_source(self.source_path.read_bytes())`）持有的是内存中的 `dict`，而非规范字节序列。

2. **下游哈希依赖 `canonical_json`**（在 `research_db.py` 中定义为 `json.dumps(..., sort_keys=True, separators=(",",":"))`），这是针对 *Python 对象* 的规范化，而非针对 *原始输入字节*。但：
   - `int(1)` 和 `float(1.0)` 经 `canonical_json` 序列化后产生不同输出（`1` vs `1.0`），因此 `close` 字段的 `int/float` 差异会传播到哈希中。
   - 键顺序在 `canonical_json` 中已处理（`sort_keys=True`），所以该维度在下游哈希中是幂等的。
   - 但原始 `raw` 字节从未被哈希，没有任何机制强制"输入字节的单一性"。

3. **没有发现预先存在的字节规范化规则**。在整个代码库中，`load_source` 只接受 `bytes`，只做 `json.loads`，没有任何步骤要求调用方先对 `raw` 做哈希绑定或规范化再传入。

4. **实际攻击面**：攻击者（或意外的重新生成）可以提供两份字节不同但 `load_source` 均接受的文件，在某些字段上导致 `canonical_json(source)` 产生不同哈希（特别是 `int` vs `float` 歧义），从而破坏需求 A 的"单一规范 source 对象"约束。

### 是否存在缓解措施

检查调用栈中是否有补偿控制：

- `alpha_execution.py` 中 `self.source_path.read_bytes()` 后直接传入 `load_source`，无字节哈希绑定步骤。
- `verify_staged_object_file()` 函数（同文件）会对暂存对象做 `sha256` 校验，但这针对的是独立的暂存文件，而非 source 文件本身。
- 没有发现任何位置在调用 `load_source` 之前对 `raw` 字节做 sha256 绑定并与 proposal 中的期望哈希比对。

**因此：漏洞未被现有代码缓解，阻塞确认有效。**

### 修复建议

在 `load_source` 入口处（或调用方）增加字节级规范化断言，即：

```python
def load_source(raw: bytes, expected_sha256: str | None = None) -> dict[str, Any]:
    if expected_sha256 is not None:
        actual = hashlib.sha256(raw).hexdigest()
        if actual != expected_sha256:
            raise FailClosed("PC6_SOURCE_HASH_MISMATCH")
    source = json.loads(raw)
    # 重序列化并写回，强制字节唯一性
    canonical_raw = canonical_json(source).encode("utf-8")
    # 或者：要求 raw == canonical_raw（拒绝非规范输入）
    ...
```

但即便如此，`int/float` 模糊性（JSON 中 `1` 与 `1.0` 语义等价但 Python 类型不同）仍需在 schema 层面显式约束（例如要求所有价格字段为 `float`，所有时间戳字段为 `int`）。
