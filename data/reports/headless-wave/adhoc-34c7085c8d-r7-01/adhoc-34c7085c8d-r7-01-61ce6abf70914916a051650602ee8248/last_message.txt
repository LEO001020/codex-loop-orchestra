## V2坏JSON复核 — 报告

### 发现摘要

`statemachine_v2.py` 中存在**一个确认的行为缺陷**，且**测试覆盖缺口**与之对应。

---

### 坏JSON的处理路径（精确代码位置）

#### `step()` 读取事件循环（第 684–687 行）

```python
try:
    ev = json.loads(stripped)
except ValueError:
    ev = {"packet_id": "malformed",
          "event": "unparseable", "raw": stripped[:200]}
self.apply_event(led, ev)
```

当 `events.ndjson` 中某行无法解析为 JSON 时，v2 构造一个合成事件：
- `packet_id = "malformed"` （合法标识符，通过 `PACKET_ID_RE` 校验）
- `event = "unparseable"`

随后调用 `apply_event(led, ev)`。

---

#### `apply_event()` 对该合成事件的处理（第 391–407 行）

```python
pid = ev.get("packet_id", "?")       # → "malformed"
name = ev.get("event", "?")          # → "unparseable"
if isinstance(pid, str) and pid.startswith(("l2v-", "v2job-")):
    return None   # 不命中
if name in INFO_EVENTS:
    return None   # "unparseable" 不在 INFO_EVENTS，不命中
if pid not in led["packets"] and name not in {"planned", "skeleton_ready"}:
    return None   # ← 命中！"malformed" 不在 led["packets"]，"unparseable" 不是 planned/skeleton_ready
```

**结论：合成事件在第三个守卫被静默丢弃，返回 `None`，不产生 DEAD_LETTER，不产生 SOL_WAKE，完全无声。**

---

### v1 vs v2 行为对比

| 版本 | 坏JSON处理逻辑 | 可见性 |
|---|---|---|
| **v1** `statemachine.py:232–234` | 检测到 `name == "unparseable"` 后立即调用 `to_dead_letter(led, pid, "unparseable_event_line", ...)` | ✅ DEAD_LETTER + SOL_WAKE，fail-visible |
| **v2** `statemachine_v2.py:684–687` + `apply_event:405–407` | 合成事件命中 "未知 packet_id + 非 planned/skeleton_ready" 守卫，静默返回 `None` | ❌ 完全无声，无 DEAD_LETTER |

v1 在 `apply_event` 中有一个 **专用提前检测**（`if name == "unparseable": to_dead_letter(...)`），该分支在 v2 的 `apply_event` 重构中被**删除**，却没有同等替代逻辑。

### 缺陷分类

| 属性 | 分类 |
|---|---|
| **类型** | 行为回归（v2 失去 v1 的 fail-visible 保证） |
| **严重性** | P1（静默失效违反 LOOP 的 "fail-visible, never silent" 原则） |
| **根因** | `apply_event` v2 中删除了 v1 第 232–234 行的 `unparseable` 专用提前处理分支 |
| **影响** | 坏JSON行被静默跳过，cursor 正常推进，不产生任何告警或 DEAD_LETTER |
| **修复方向** | 在 v2 `apply_event` 的 `INFO_EVENTS` 检查之后（或在构造合成事件后直接在 `step()` 内）增加 `if name == "unparseable": to_dead_letter(...)` 分支，并补充对应测试 |
