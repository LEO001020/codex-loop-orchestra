### 三、stale 过滤

**Stale native：**
- 条件：`status=="running"` 且该 `agent_id` 不在当前 rollout 扫描结果中，且 `updated_at` 距今 > 30 秒 → 标记为 `stale_native`，不计入 `running`，不计入任何 plane。**✓ 正确**

**Stale headless：**
- 条件：`state in {starting, running}` 且 `max(heartbeat_at, updated_at)` 为 0 或距今 > 30 秒 → 标记为 `stale_headless`，不计入 `running`，不计入 `planes["headless"]`。**✓ 正确**

**Rollout crash-era 过滤：**
- rollout mtime < `desktop_app_server_started_at` 时跳过，防止 Desktop 崩溃前的旧 rollout 充当活跃并发。**✓ 正确**

**Freshness 标签逻辑：**
- headless 任务若存在且 `headless_age > 30s` → `STALE`（以心跳为准，因为无头任务承诺定期心跳）。
- desktop-only 情形下，若每个展示的 desktop 任务都有对应的 rollout 证据且 `desktop_started_at` 不为 None → `QUIET`；否则 → `STALE`。

**⚠️ 发现问题 2：`headless_updated` 列表构建范围过宽**

```python
for key in ("updated_at", "heartbeat_at"):
    if isinstance(row.get(key), (int, float)):
        updated.append(float(row[key]))
        if state in {"starting", "running", "stale_headless"}:
            headless_updated.append(float(row[key]))
```

当一个 job 变为 `stale_headless` 时，其旧的 heartbeat 时间戳仍然被追加进 `headless_updated`，从而拉低 `headless_age`，使 STALE 判断延迟触发。这是一个轻微的反向保护偏差——单元测试 `test_stale_headless_heartbeat_is_not_hidden_by_fresh_refill` 通过是因为测试使用了时间 mock（`time.time() = 100`、heartbeat = 20），确保 age = 80s > 30s，即便 stale_headless 时间戳也被计入，80s 足够大。但在 heartbeat 约在 25 秒前的边界情况下可能掩盖 STALE 状态。
