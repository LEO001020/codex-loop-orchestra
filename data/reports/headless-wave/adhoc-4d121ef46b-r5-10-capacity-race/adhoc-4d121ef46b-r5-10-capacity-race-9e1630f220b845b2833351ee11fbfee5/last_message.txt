## 80路容量竞态审计 — 审计报告

### 1. 全局 80-cap 门控

**实现位置：** `dispatch.py:before_spawn()`（第245-274行）

```python
if initializing + running >= target_total:
    raise BirthThrottleError("effective+initializing concurrency reached target %d" % target_total)
```

`target_total` 从 `refill_policy.toml` 的 `[concurrency].target_total = 80` 读取，计数来源是 `observed_birth_counts()`，后者委托给 `RefillControllerV2.read_roster_counts()`，即 lifecycle 的 `exec_roster.json` + `native_roster.json` + 8765 observer 三路合并。

**80-cap 门存在且有效**——没有发现硬性绕过路径。

### 2. initializing-debt 与 80-cap 的交互

**关键设计（正确的）：**
- `recompute()` 中：`raw_spawn = max(0, raw_debt[p] - initializing[p])`，即 initializing 的 agent 消耗 spawn 配额，但**不清除 debt**（refill_controller_v2.py，约第462行注释："Starting generations reserve a birth slot but do not clear the visible debt. Only a process-generation-verified running row reduces ``deficit``."）
- 80-cap 检查：`initializing + running >= target_total`，initializing 占用容量，正确防止超出。

**⚠️ P1 GAP — initializing 计入容量但 headless_wave 不查容量**

`headless_wave.py` 的两条生产路径（packet 模式第396-435行，adhoc 模式第460-482行）在调用 `dispatcher.dispatch()` 或 `launch_supervisor()` **之前**不查询全局容量。

容量检查只存在于 `dispatch.py:before_spawn()`，而 `dispatch_v2._spawn()` 通过 `dispatch_v1.dispatch_single()` 调用它（有覆盖）。但 **adhoc headless wave 路径**（非 packet_id，直接调用 `launch_supervisor()`）完全绕过了 `before_spawn()`：

```python
# headless_wave.py:480
supervisor_pid = launch_supervisor(
    supervisor, paths.root, report_dir / "supervisor.log")
if wait_observed(paths.data, packet_id, run_id, args.observe_timeout):
    results.append({...})
```

adhoc 路径里没有调用 `before_spawn()` 或任何等效的容量检查。唯一的约束是 `provider_birth_allowed()` 和 `opencodex_healthy()`——这两者都**不检查 80-cap**。

**风险：** 多个并发 headless_wave.py 进程（adhoc manifest）可以同时通过健康检查并超过 80 的全局上限。

### 3. 一秒间隔的竞态

**dispatch.py 路径（P1 竞态）：**

`before_spawn()` 中的间隔检查是非原子的：
```python
last_spawn = float(state.get("last_spawn_at", 0) or 0)   # 读取（无锁）
remaining = interval - (time.time() - last_spawn)
if remaining > 0:
    time.sleep(remaining)
# ... 之后在 record_spawn_and_gate() 里：
update_throttle_state(last_spawn_at=time.time(), ...)      # 写入（有锁）
```

读取 `THROTTLE_STATE` 和写入 `last_spawn_at` 之间没有持有锁。如果两个并发 dispatch 进程同时读取相同的 `last_spawn_at`，两者都会看到 `remaining ≤ 0` 并在间隔期内同时产生 birth，从而违反「每隔至少 1 秒」的要求。

`update_throttle_state()` 用 `THROTTLE_LOCK` 保护写入，但读取侧不在同一把锁之内（先 `read_json(THROTTLE_STATE, {})` 再 `time.sleep(remaining)` 再写入），存在 TOCTOU 窗口。

**headless_wave.py 路径（P1 竞态）：**

headless_wave.py 的间隔检查更简单，是单进程内的 `time.sleep(interval)`（第402-403行和第462-463行），它只在**同一进程的 for 循环内**顺序生效。多个并发 headless_wave.py 进程之间完全没有协调：每个进程各自睡 1 秒，但它们之间相互不知道对方的 birth 时间，导致实际间隔可以小于 1 秒（甚至同时）。

---

### 4. 80-cap 与 initializing debt 的第二个 P1 交互问题

在 `before_spawn()` 中，容量检查（第256-258行）和间隔检查（第272-275行）**之间没有锁**。流程是：

1. 检查 `initializing + running < 80`（无锁读）
2. 等待间隔（sleep）
3. 调用 `launch_supervisor()`（实际 birth）
4. 写入 `last_spawn_at`

步骤1和步骤3之间窗口可达1秒（加上sleep时间），其他进程可在此期间通过步骤1的检查并追加 births，导致实际同时在途 births 超过 80。

这个问题在 `refill_consumer_v2.py` 的单进程生产循环中影响较小（它是单线程），但在多进程场景（多个 dispatch 或多个 headless_wave 实例）下是真实竞态。
