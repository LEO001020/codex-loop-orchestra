### 根 README 的定位问题与修正建议

**现状**：根目录 `README.md` 描述的是 **Prime Agent**（一个 AI coding agent 框架），完全没有提及 `quant_engine`/`pipelines`/`quant` 三个目录。这三个目录是在 Prime Agent 仓库内的 K3 量化系统叠加层，两套系统共用一个 repo 根但在文档上完全脱节。

**避免把 P5 research 误写成 Harness 默认行为的具体操作规则**：

1. **LiveClock 是 P5 预留接口，绝不是默认时钟**。`quant_engine/clock/clock.py` 里 `LiveClock` 的每个方法都抛 `NotImplementedError("LiveClock 为 P5 预留接口")`。任何文档或配置若把 `LiveClock` 作为"可选时钟模式"描述均属错误——Harness 默认且唯一可用的是 `TestClock`。

2. **`quant/p4_integrations/` 下的策略和因子都处于"三件套 reject 状态"**。G6/G7 报告原文写明"基线 verdict=reject 属预期——G6/G7 交付的是平台接线与裁决管线，非可过线策略"。若在文档中描述"K3 已有可用因子/策略"须明确标注 research-only 且 OOS 未消费。

3. **pipelines/ 下的管线是研究实验，不是 Harness 内置 pipeline**。每条管线有独立 EXP-ID、`oos_consumed` 状态、pipeline_ledger.jsonl，且明确运行在 VPS 真实环境（parquet 数据路径硬编码 `/data/k3/data/parquet`）。把它们写成"引擎内置工作流"会让读者误以为可以直接 `k3 backtest` 跑出研究结论——实际上要先在 VPS 完整环境里跑完十环节并通过三件套门才有资格申请 OOS 裁决。

4. **验证阈值（DSR 0.95 / PBO 0.5 / WFE 0.5）是封闭代码常量，不是可配的 research 参数**。`validation/constants.py` 有双常量锚 + `assert_thresholds_sealed()` 执法，任何"调松阈值以通过实验"的操作都会在裁决时抛 `ValidationError`。文档不应将这些值描述为"推荐默认值"或"可按需调整"。

5. **`quant_engine` 本身不做实时交易**（P5 特性），它只是确定性回测核。任何涉及"实盘连接""实时信号"的描述都属于 P5 范畴，与当前 Harness 无关。
