### What Counts as "Effective Concurrency"

The critical distinction, enforced in `RefillControllerV2.read_roster_counts()`:

**Only `running` clears debt.** The method tracks two separate buckets:

- `running` — native roster `status == "running"` or exec-roster `state == "running"`
- `initializing` — native `status == "pending_start"` or exec-roster `state == "starting"`

The debt formula (in `recompute()`):

```
raw_debt[pool]  = min(pending[p], max(0, target[p] - running[p]))   # running only
raw_spawn[pool] = max(0, raw_debt[p] - initializing[p])             # capacity reservation
capacity        = max(0, target_total - running_total - initializing_total)
```

So:
- `running` reduces **debt** (the refill trigger threshold comparison).
- `initializing` reserves **capacity** (preventing over-spawning) but does **not** lower debt.
- A birth in `starting` state keeps the `refill_required` flag `True` until it transitions to `running`.
- `Popen` success, spawn intent, deny messages, and stale/lost exec-roster rows are all excluded — they never appear in the roster and therefore contribute zero to any counter.

This is tested explicitly: `test_initializing_births_never_clear_debt` places 3 K3 agents in exec-roster `state=starting` and asserts that `unfulfilled_demand > deficit`, confirming debt remains visible.

### The Terminal → Refill State Machine

**Step 1 — Child terminates:**
`LifecycleSupervisorV2.finalize_child()` applies the v2 success condition:  
`rc == 0 AND report.exists() AND validate_short_result(report) == OK AND revision_matches`

Any failure path emits `exec_failed` to `data/events.ndjson`. Success emits `subagent_stop`. In both cases, a fixed-size `Receipt(packet_id, status, report_path)` — ≤200 tokens — is the only object returned to the orchestrating session. Content never rides the tool result.

**Step 2 — Ledger state transition:**
The state machine transitions the packet state out of `RUNNING` (or its equivalent). The `queue_sync_ledger()` method in `RefillControllerV2` re-reads the entire ledger and recomputes both pool demand counts atomically:
- `DISPATCHABLE` packets → their pool's count (by role or `pool_hint`)
- `L2_VERIFY`, `L2_RANK`, `EXPAND_K3`, `L2_VERIFY_PENDING` states → K3 demand

**Step 3 — Roster decrement:**
When a child stops, its entry in `native_roster.json` or `exec_roster.json` transitions out of `running`. On the next `recompute()` call, `running[pool]` drops, which may cause `running[pool] < low_waters[pool]` to become true (re-opening the refill gate).

**Step 4 — Refill gate evaluation (`recompute()`):**
A pool is `refill_required` when all three hold simultaneously:
1. `not queue_empty` (pool has pending work)
2. `not finalized` (not in `release_finalize` state)
3. `running[pool] < low_waters[pool]`

When `refill_required_any == True`, a `refill_required` event is appended to `data/refill/events.ndjson` with per-pool deficit and model-pool list. The consumer that reads this event is responsible for spawning new agents.

**Step 5 — Deficit computation and spawn gating:**
The spawn controller computes `raw_spawn = raw_debt - initializing` per pool, then caps by `capacity = target_total - running_total - initializing_total`. The `max_initializing = 8` throttle in `[spawn_throttle]` limits births in the handshake at once, preventing the initializing count from growing unboundedly and starving capacity for real running agents.

### Borrowable Reservations and Watermark Reclaim

When only one pool has pending work, `recompute()` expands that pool's target to the full `target_total` (80). When K3 demand appears while V4 has borrowed all slots, the next `recompute()` sees `len(active_pools) == 2` and restores the preferred 60/20 split — the watermark reclaim. Tested by `test_watermark_reclaim_once_k3_demand_appears`.
