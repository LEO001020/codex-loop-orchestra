queue_empty = pending_total <= 0        # controller 层全局 flag
parent_reason = "parent_backlog_empty"  # 当 queued_total <= 0 时

`queue_empty` 的计算依赖 `read_queue()` 读取 `data/refill/work_queue.json`，而 `work_queue.json` 的内容由 `queue_sync_ledger()` 写入——后者扫描 `progress_ledger.json` 中所有 state==`DISPATCHABLE` 的 packet（加 K3_WORK_STATES），统计双池 pending 数。

即：**全局 backlog 与父会话 backlog 均已真实耗尽**，当前运行中的 15 个 agent 是上一波 import 时发出的、已无新的 DISPATCHABLE 包可补位。

### 二、Manifest 接续机制（三个触发点）

**触发点 A — 导入时立即唤醒：**
`parent_manifest_importer.py` 在 `atomic_write_json(ledger)` 完成后，直接调用 `schedule_run(paths.root, source="parent_manifest_imported")`。这是唯一在 backlog 变空→重新填入之间会立即触发 actuator 的时机。若调用失败，写入 `refill_actuator_failed` 事件但**不阻塞导入成功**（soft fail）。

**触发点 B — 成功补位后的 1 秒残余跟进：**
`run_once()` 结束后，若 `after.deficit.total > 0`，调用 `schedule_followup_if_debt(..., source="refill_residual_debt")`，延迟 1 秒发一次额外唤醒，覆盖"补位 transaction 进行中又有 agent 结束"的并发窗口。

**触发点 C — 失败后的 backoff 唤醒：**
wave 返回非零 rc 时，调用 `schedule_retry_if_debt`，延迟 `max(30秒, provider_backoff_until+1)` 后唤醒。

**`parent_backlog_empty` 发生后无自动唤醒**：一旦 `queue_sync_ledger` 写出 `pending=0`，actuator 返回 `status:"idle"`，不会再调用任何 `schedule_*` 函数。下次唤醒**只能**来自新的 manifest import（触发点 A）或 lifecycle supervisor 触发的 `adhoc_lifecycle_supervisor` 请求（生命周期钩子每次 agent stop 都调用一次）。

### 三、`queue_empty` 与 `deficit=0` 的语义区分（关键）

| 情形 | `queue_empty` | `deficit.total` | `reason` | 行为 |
|------|:---:|:---:|------|------|
| 无 DISPATCHABLE 包 | `true` | 0 | `"queue_empty"` | idle，不 spawn，正常终止 |
| 有 DISPATCHABLE 但全部为 K3_WORK_STATES（无真实包） | `false` | >0 | `"below_low_water"` | `refill_required=true`，但 `select_tasks` 过滤后返回空，`build_manifest` 返回 None，actuator 仍 idle |
| 有 DISPATCHABLE 包、running≥target | `false` | 0 | `"at_capacity"` 或 `"at_or_above_low_water"` | idle |
| **有 DISPATCHABLE 包、running<low_water** | `false` | >0 | `"below_low_water"` | spawn，正常 P0 |

**关键区分：** `queue_empty=true` 是**真实无包**，`deficit=0` 可能是"有包但 running 已满"。两者都不触发 spawn，但前者是 demand-backed 的自然收尾，后者是容量满载的正常压制。

### 四、合理下降 vs. P0 有任务不补位的边界

**合理（demand-backed）的 active 下降：**
- backlog 已经耗尽（`parent_backlog_empty` + `queue_empty`）
- agent 自然完成/上报（history 显示 `t:4 REPORTED via:subagent_stop`）
- active 计数从最高 29 逐步下降到 15，每次 actuator 触发都确认 `pending=0`

**当前观测：**
refill_actuator.log 末尾 10+ 次记录全部是 `status:idle, pending:0, queue_empty:true`，active 从 29→28→27→17→16→15 的每一步下降，都伴随 actuator 触发并确认无 DISPATCHABLE 包。这是**完全正常的 demand-backed 下降**，不是 P0。

**构成 P0 的条件（现在未触发）：**
- 存在 state==`DISPATCHABLE` 的 packet（`queue_sync_ledger` 会计入 pending）
- 父会话 `active=true` 且 `manifest_id` 匹配
- `running < low_water`（v4<45 或 k3<15）
- actuator 被调用但未 spawn（headless_wave.run 跳过）

只有三个条件同时成立且 actuator 被跳过，才是有任务不补位的 P0。

### 五、B/C/D 场景比较

**场景 B（`parent_backlog_empty`）——当前状态：**
- 父会话 `019feacd-...` 仍 `active:true`，manifest_id=`p0-parent-final-backlog-20260814`
- ledger 中该 manifest 下所有 packet 均为 `REPORTED`（已完成），无 `DISPATCHABLE`
- `queue_sync_ledger` 每次扫描返回 `{v4:0, k3:0}`，父会话 `reason=parent_backlog_empty`
- **正确行为**：不补位，active 自然下降，直到新 manifest 被 import

**场景 C（有 DISPATCHABLE 包但全局满容量 `at_capacity`）：**
- `pending>0` 但 `running_total ≥ target_total=80`
- `deficit.total=0`（capacity=0），不 spawn
- `reason="at_capacity"`，`queue_empty=false`
- **正确行为**：不是 backlog 空，是容量保护。新 agent 完成后 actuator 会立即重新评估并补位

**场景 D（有 DISPATCHABLE 包、K3_WORK_STATES phantom demand）：**
- ledger 中有 `L2_VERIFY`/`EXPAND_K3` 等状态（无 `DISPATCHABLE`）
- `queue_sync_ledger` 把这些计入 k3 pending → `queue_empty=false`，`deficit.k3>0`
- 但 `select_tasks` 只选 `state==DISPATCHABLE` → 返回空 → `build_manifest` 返回 None → actuator idle
- **关键陷阱**：`queue_empty=false` 但实际无任务可派，保护层在 `select_tasks`，不在 `queue_empty` 守卫

### 六、预填充机制验证

AGENTS.md §6 规定："compile 21-80 real, bounded read-only packets into `codex-loop-parent-refill/v1` and admit them once through `harness/parent_manifest_importer.py` with `target_active=20`"

**当前实现满足该规定的路径：**
1. 导入时立即调用 `schedule_run`（触发点 A），不等待 lifecycle 边缘
2. `parent_sessions.json` 记录 `target_active=20`，controller 的 `parent_debt` 计算用此上限
3. 父会话保持 `active:true`，后续 manifest 可复用同一 `parent_session_id` 追加（幂等检查：`prior_entry is not None` → `existing += 1`，不重复导入）

**现存的一个接续空窗风险（代码层面）：**
`parent_manifest_importer.py` 末尾的 `schedule_run` 调用处于 try/except，失败时写 `refill_actuator_failed` 事件并软返回。在 **actuator 进程恰好正在运行**（`_process_generation_alive` 返回 true）的情况下，`schedule_run` 返回 `{"status":"coalesced"}`——新 manifest 的 DISPATCHABLE packets 已入 ledger，但正在运行的 actuator 实例已经完成了它的 `queue_sync_ledger` 快照，不会看到这批新包。`schedule_followup_if_debt` 逻辑只在 `run_once` 结束后检查 `after.deficit`，而那个 actuator 实例的 `after` 是基于旧快照的（pending=0）。**真正保障**依赖 lifecycle supervisor 在下一个 agent stop 事件上触发新的 `adhoc_lifecycle_supervisor` 请求——这提供了一个最长等到下个 agent 自然完成的接续窗口，而非立即触发。此窗口在 backlog 刚导入但前一个 actuator 并发运行时会引入 1 个 agent 周期的延迟（非 P0，但设计上可优化）。

---

**结论：** 当前 `queue_empty=true, reason=queue_empty, parent_backlog_empty` 是**合理的 demand-backed 下降**，全部 64 个 parent packet 均已 REPORTED 或 DEAD_LETTER，无任何 DISPATCHABLE 包被跳过。B/C/D 三类场景语义清晰，保护层各不相同（B 在 `select_tasks` 父会话门禁，C 在 `capacity` 上限，D 在 `DISPATCHABLE` 过滤）。预填充机制在导入时立即唤醒，但存在 actuator 并发导致的单周期接续空窗，属设计权衡而非 P0。
