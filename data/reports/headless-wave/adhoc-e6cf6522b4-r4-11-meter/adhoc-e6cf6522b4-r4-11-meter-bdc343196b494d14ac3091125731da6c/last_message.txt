## Meter Refresh Design Review: Event-Driven Low-Cost Refresh for Headless Completion and Long Desktop Sessions

### 1. 当前刷新路径概述

刷新链由以下几个触发点构成，均不依赖轮询或定时器：

| 触发事件 | 触发方 | 调用链 |
|---|---|---|
| 子代理 Stop（Desktop） | `.codex/hooks.json` → `reconcile_subagent_metering.ps1` | → `reconcile_subagent_metering.py` → `model_token_share_bridge.py` |
| 全量 epilogue | `orchestration_epilogue.run_epilogue()` | → `model_token_share_bridge.refresh()` |
| 终结包完成（canonical packet） | `lifecycle_supervisor.schedule_epilogue()` | → `terminal_packet_epilogue.run()` → state machine + refill（**无 meter 刷新**） |
| Ad-hoc headless 完成 | `lifecycle_supervisor`（`adhoc` 分支） | → `refill_consumer_v2.schedule_run()`（**无 meter 刷新**） |
| CSV 包完成 | `csv_reconcile.py` | → `run_epilogue(source="csv_reconcile")` → 含 meter |
| 状态机 CLI 直调 | `statemachine_v2.py` / `statemachine.py` | → `run_epilogue()` → 含 meter |

防抖控制（`refresh_debounce_s = 60`）在 `model_token_share_bridge.refresh()` 内通过文件锁+时间戳强制执行，避免重复扫描。

### 2. 发现的结构性问题

#### 问题 A（**高优先级**）：headless 完成路径不刷新 meter

`lifecycle_supervisor.py` 在 canonical packet 完成时调用 `schedule_epilogue()`，但该函数只启动 `terminal_packet_epilogue.py`，后者只跑 state machine + refill，**不包含 meter 刷新**。Ad-hoc headless 完成更激进：只调 `refill_consumer_v2.schedule_run()`，根本没有 epilogue。

结论：20/80 个 headless agent 完成后，meter 报告**不会自动更新**。下一次刷新要等 Desktop 的 Stop hook（如果 Desktop 会话最终触发的话）。在纯 headless 波浪中，`model_token_share_v2.json` 可以老化超过 `stale_after_s = 7200` 秒，导致 governor 进入 fail-closed 模式，错误地封锁 Sol 工具调用。

**修复方向**：在 `terminal_packet_epilogue.run()` 中，在 refill 之后、返回结果之前，加入 `refresh_meter(root, sessions, force=False)` 调用（已有 try-except 模式保证 fail-open）。Ad-hoc 分支（`schedule_run`）本身是轻量的，可在 `refill_consumer_v2.run_once()` 末尾触发一次防抖刷新。

---

#### 问题 B（**中优先级**）：长 Desktop 会话中 Stop hook 是唯一的定期触发器，存在空档

Desktop 的 `Stop` hook 仅在**一个 Desktop 会话终止**时触发，而不是在每次子代理工具调用结束后。一个长期运行的 Desktop root 会话在两次 Stop 之间可能有数小时无刷新窗口。唯一降险是 governor 的 `stale_after_s = 7200`（2小时），超时后 STALE 报告让 non-planning 工具调用 fail-closed。

这个设计本质上是正确的（fail-closed 优于 fail-open），但存在假阳性风险：在一个 busy 的长 Desktop 会话里，meter 可能长时间滞留于 `INSUFFICIENT_DATA`（如当前 `rolling_5h` 窗口所示）或 `STALE`，导致合法的 Sol 规划工具被错误拒绝。

**修复方向**：在 `PreToolUse` hook 中（governor 评估后），若 meter 状态为 `STALE` 并且 `planning` 状态合法，可在后台 detach 一次 `model_token_share_bridge refresh --root ...` 进程（不阻塞工具调用，幂等防抖）。

---

#### 问题 C（**中优先级**）：hysteresis 状态残留 HIGH，但 `rolling_5h` 为 INSUFFICIENT_DATA

当前持久化状态：
```json
{ "above": 0, "below": 0, "state": "HIGH" }
```
`rolling_5h.status = INSUFFICIENT_DATA`，`sol_share_5h_effective = 0.0`。

`MeterV2.refresh()` 中的逻辑是：`primary.status == "OK"` 时才向 hysteresis controller 输入 sample。INSUFFICIENT_DATA 不输入，controller 状态冻结在 HIGH。

这意味着如果 rolling_5h 窗口长期缺少数据（例如长间歇后重启），hysteresis 永远停在 HIGH，governor 持续 deny Sol 工具，直到下一次有效数据样本。这是 **fail-closed 但不 fail-visible**——没有任何事件记录说明为何 HIGH 状态持续。

**修复方向**：当 `INSUFFICIENT_DATA` 持续超过 `stale_after_s` 时，应将 hysteresis 状态重置为 NORMAL（或在 governor `budget_signal()` 中检测这一情况并返回 `actuate=False` 同时清除 HIGH 状态）。至少应在 `governor.fail_closed` 事件的 detail 中记录 `hysteresis_state=HIGH` 和 `meter_status=INSUFFICIENT_DATA` 的组合。

---

#### 问题 D（**低优先级**）：bridge 的 session_sources 写死了 WSL 路径

当前 `meter_bridge_state.json`：
```json
"session_sources": ["/home/codexloop/.codex/sessions"]
```
但 hook 是 Windows PowerShell，Stop hook 调用时用的是 `$env:CODEX_HOME` 或 `$env:USERPROFILE\.codex`。bridge 在 WSL 路径下收集的是 headless worker 的 rollout，Windows Desktop 的 rollout 在另一个路径。

当前 `model_token_share.json` 的 `records: 1442`，但 token_ledger 有 45672 行——说明 bridge 只扫描了 WSL 端，大量 Windows Desktop rollout 未被计入 v1/v2 报告。

**修复方向**：`orchestration_epilogue.run_epilogue()` 中的 sessions 路径应传入双路径列表（Windows `~/.codex/sessions` + WSL `/home/codexloop/.codex/sessions`），bridge 已经支持 `list[Path]` 入参。

---

#### 问题 E（**低优先级**）：`SubagentStop` hook 为空

`hooks.json` 中 `SubagentStop` 钩子列表为空。这是一个理想的轻量刷新触发点：每个子代理完成后触发一次 bridge refresh（防抖 60s 保证低开销）。相比于 Stop hook（Desktop 会话结束才触发）更实时，比 terminal_packet_epilogue 路径更早。

**修复方向**：为 `SubagentStop` 添加与 Stop hook 类似的 PowerShell 脚本，调用 bridge refresh（fail-open，timeout 30s）。

---

### 3. 整体设计评估

**优点（保留）**：
- 防抖机制（60s）加文件锁，正确防止并发扫描风暴。
- `stale_after_s = 7200` 的 fail-closed 机制是正确的安全默认。
- Hysteresis 双阈值设计（enter 0.25/2 samples, leave 0.22/2 samples）有效消除 bang-bang。
- Bridge 的幂等 key 设计（sha256 identity）保证重复触发不产生重复记录。
- Governor 的 break-glass 路径有完整的审计事件，从不静默。

**主要风险汇总**：

```
严重度    问题                              影响
HIGH     headless 完成不触发 meter 刷新    长波浪后 meter 老化 -> fail-closed 封锁 Sol
MEDIUM   Desktop 长会话刷新空档            rolling_5h INSUFFICIENT_DATA -> hysteresis 冻结
MEDIUM   INSUFFICIENT_DATA 不重置 HIGH     合法 Sol 工具被持续拒绝，无可见诊断
LOW      bridge 缺 Windows session 路径   v2 meter 未计入 Desktop Sol rollout
LOW      SubagentStop hook 未使用         错过最自然的低成本实时刷新点
```

---

### 4. 建议的最小修复集（优先级排序）

1. **`terminal_packet_epilogue.run()`** — 末尾加 `refresh_meter(root, sessions, force=False)`，用 try-except 包裹，与 refill 并列为 fail-open 步骤。这是覆盖面最大的单点修复。

2. **`MeterV2.budget_signal()`** — 当 `status == "INSUFFICIENT_DATA"` 且 hysteresis 状态为 HIGH 时，返回 `actuate=False`，让 governor 不因冻结的 HIGH 状态封锁工具调用，同时附加 `insufficient_data_overrode_high=True` 字段供审计。

3. **`orchestration_epilogue._run_epilogue_locked()`** — 将 sessions 路径从单路径改为 `[windows_sessions, wsl_sessions]`（动态探测双路径，缺失者忽略），使 bridge 能同时扫描两个 rollout 树。

4. **`hooks.json` SubagentStop** — 注册与 Stop hook 相同的 PowerShell 脚本，用防抖保证轻量。
