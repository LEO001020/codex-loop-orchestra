### F1 — stale_native rows silently disappear from task list [CONFIRMED · mid priority]

**Location:** Lines 635–643 (`snapshot()`)

The task-list append gate is:
```python
if state in {"running", "idle", "shutdown_pending"}:
    ...
    tasks.append(...)
```

When a running native row is reclassified to `stale_native` (lines 614–616: no current rollout AND updated_at > 30s ago), it correctly increments `counts["stale_native"]` but is **excluded from `tasks`**. The agent_id is therefore invisible to the orchestrator — there is no entry to call `close_agent` against, and `counts.running` drops silently, creating a phantom deficit that can trigger spurious refill.

**Test coverage:** `test_stale_native_row_without_current_rollout_stays_stale` at line ~362 asserts `result["tasks"] == []`, which actually **encodes** the buggy behavior rather than catching it. There is no test asserting a stale_native row remains visible with `state="stale"`.

**Minimal fix:** Add `stale_native` to the task-append gate, emit it with `state="stale"` and `plane="Desktop"`, and include `agent_id` so `close_agent` can be called.

### F2 — Rollout fallback can double-count when a native row transitions to terminal early [CONFIRMED · low priority]

**Location:** Lines 703–733 (rollout fallback loop)

`known_native_ids` is built from `native["agents"].keys()` — it includes both running and terminal native rows. A terminal native agent with `status in {"completed", "terminal"}` IS in `known_native_ids`, so its corresponding non-terminal rollout row is correctly suppressed (line 705: `if row.get("agent_id") in known_native_ids: continue`).

**However**, the problematic edge case: if the native roster is written with the agent removed (rather than marked terminal), then after `stale_native` reclassification the agent_id is still in `known_native_ids` (it's in `native["agents"]`), so rollout suppression still works. The double-count can only occur during the 1–5s race window where:
- The native hook removes a row entirely (rather than marking it terminal), AND
- The rollout hasn't flushed a `task_complete` yet

The semantic key deduplication at lines 714–717 provides a second guard but is imprecise for same-name tasks. The risk is real but narrow; the existing `test_terminal_native_id_suppresses_nonterminal_rollout_fallback` test covers the main path but not the row-removal scenario.

### F3 — Mixed Desktop+headless scenario: dead headless plane hidden by fresh refill doc [CONFIRMED · low priority]

**Location:** Lines 791–815 (freshness cascade)

The all-stale guard (lines 791–793) only triggers when `running == 0`. In a mixed wave where Desktop native agents are running and a headless job has gone stale:

- `counts["stale_headless"] > 0` but `counts["running"] > 0` → all-stale guard skipped
- `planes["headless"] == 0` (stale_headless rows don't increment planes) → headless STALE branch skipped
- `headless_age` is computed correctly (~80s in test fixture) but is never consulted since `planes["headless"] == 0`
- A fresh `refill_state.json` (updated_at ≈ now) puts a recent timestamp in `updated` → `age` is small → `freshness = "LIVE"`

The dead headless plane's staleness is invisible to freshness classification when any Desktop agent is concurrently running. An orchestrator reading LIVE while a headless wave is fully dead will not trigger corrective refill.

**Minimal fix:** Add a separate guard: `if counts["stale_headless"] > 0 and headless_age is not None and headless_age > ~5s: force freshness = "STALE"` before the LIVE path, regardless of `planes["headless"]`.
