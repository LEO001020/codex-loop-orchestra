### 路径一：`refill_controller_v2.py` — `capacity` 计算

**文件：`harness/refill_controller_v2.py`**

```
行 433: capacity = max(0, target_total - running_total - initializing_total)
行 434: deficit_total = min(sum(raw_spawn.values()), capacity) if required_any else 0
```

- `capacity` 正确地以 `target_total=80` 为上界，减去已 running + initializing 数量。
- `deficit_total` 是 `min(raw_spawn_total, capacity)`，不会超出 80。**✅ 无突破风险。**

### 路径二：`refill_controller_v2.py` — `parent_spawn_total` 与全局 `capacity` 共享

**行 469-473：**

```python
parent_spawn_total = min(
    parent_debt,
    max(0, parent_target - parent_running - parent_initializing),
    capacity,           # 同一个 capacity 快照
)
```

- `parent_spawn_total` 受 `capacity` 约束（行 472），而 `capacity` 是全局剩余容量的快照。
- **问题**：`capacity` 在每父循环中**不递减**。若有 N 个活跃父会话，每个计算 `parent_spawn_total` 时都使用同一个 `capacity` 值，每父的 spawnable 之和可能超过单次全局容量快照。
- 但 `parent_spawn_total` 只进入 `parent_states[parent_id]["spawnable"]`，**它不直接消耗全局 `deficit`**。
- 实际 dispatch 由 `select_tasks`（`refill_consumer_v2.py` 行 305-343）控制，其中 `remaining` 来自全局 `state["deficit"]`（行 252-254），每发一个任务即 `remaining[pool] -= 1`（行 338）——**全局计数是唯一正确递减的地方**。

**结论**：`parent_spawn_total` 可能在状态快照层面被高估（多个父会话并发时各自看到相同的 `capacity`），但不会导致实际 spawn 超出 80，因为 `select_tasks` 中 `remaining` 受 `deficit` 约束，而 `deficit_total` 已正确被 `capacity` 截断。**⚠️ 状态层面展示的 `spawnable` 可能总和 > 全局剩余，属于显示误差，不是实际超额风险。**

- 单个父 manifest 的任务数上限是 `target_total=80`（全局总量），而非 `dialogue_target=20`。**⚠️ 一个父 manifest 可以携带最多 80 个任务**，这等于整个全局背压容量都被单一父 manifest 占满。虽然 dispatch 时会被 per-parent `spawnable` 和全局 `deficit` 双重约束，但背压队列层面没有 per-parent backlog 上限守卫。

### 路径五：`refill_consumer_v2.py` — 错误清债路径

**`select_tasks` 行 296-299：**

```python
if str(parent_id) not in parent_remaining:
    # A parent task only counts after the same controller snapshot
    # has established real backlog and per-parent capacity.
    continue
```

- 若某父 session 的任务在 ledger 中存在，但 controller 快照的 `state["parents"]` 中没有对应的 `spawnable`（如快照在 parent 注册后、recompute 前产生），该父的任务被**静默跳过而不是纳入全局 remaining 消耗**。
- 这意味着此类任务永远无法在该轮被清掉——这是**守卫行为**（不清债），不是错误清债。**✅**

### 路径六：`refill_controller.py`（v1）— `DEFAULT_CAP=50` vs 全局 80

**行 53：`DEFAULT_CAP = 50`**
**行 150：**

```python
def cap(self) -> int:
    return config_int("agents", "max_concurrent_threads_per_session", DEFAULT_CAP, self.root)
```

- v1 控制器的 per-session cap 默认是 50，不是 80。如果仍有代码路径使用 v1 controller，且 `config.toml` 的 `[agents]` 节没有显式配置 `max_concurrent_threads_per_session`，则全局 80 目标与 v1 的 50 cap 会形成不一致——v1 会在 running+initializing+reclaimable=50 时停止，而全局目标是 80。
- **⚠️ v1/v2 并存时，使用 v1 路径会将有效并发上界压在 50，造成实际容量低于 80 的债务无法清偿，但不会突破 80。**

| 风险类型 | 文件 | 行号 | 严重度 |
