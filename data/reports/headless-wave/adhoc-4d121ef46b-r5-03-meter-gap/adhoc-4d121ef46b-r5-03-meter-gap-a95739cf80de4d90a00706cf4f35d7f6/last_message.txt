## Meter 生命周期缺口审计报告

### 已确认的刷新触发点（有据可查）

**Desktop 路径（`hooks/subagent_lifecycle.py`）：**

- `handle()` 函数末尾第 809 行：`refresh_meter()` 在以下三个事件后触发：`SessionStart`、`SubagentStop`、`Stop`
- `SessionStart` → 触发 `refresh_meter()`（Desktop 会话启动时）
- `SubagentStop` → 触发 `refresh_meter()`（每个 Desktop 子代理终止时）
- `Stop` (parent_stop) → 触发 `refresh_meter()`（根会话关闭时）
- **注意：`SubagentStart` 不触发计量刷新**，仅写入 `events.ndjson`

**Headless 路径（`harness/orchestration_epilogue.py`）：**

- `_run_epilogue_locked()` 第 101 行：调用 `refresh_meter(root, sessions, force=False)`
- `orchestration_epilogue.py` 的 `run_epilogue()` 是 headless 终止事务的执行者
- `lifecycle_supervisor.py` 的 `finally` 块调用 `schedule_epilogue(root, "lifecycle_supervisor")`，后者启动 `terminal_packet_epilogue.py`

---

### 已发现的生命周期缺口

#### 缺口 1：`terminal_packet_epilogue.py` **不包含** meter refresh

`harness/terminal_packet_epilogue.py` 是 headless 任务完成时的主要终止事务执行器，其 `run()` 函数仅执行：`normalize_legacy_reports` → `StateMachine.step()` → `route_terminal_retries` → `run_refill_once`，**完全没有调用 `refresh_meter`**。

Headless 完成后的 meter 刷新依赖于**完整 epilogue**（`orchestration_epilogue.py`）被触发，但 `terminal_packet_epilogue.py` 是生命周期监管器实际调用的终止脚本（`schedule_epilogue` 启动它）。`orchestration_epilogue.py` 的 meter 调用路径仅在该脚本被**直接调用**或由 `run_epilogue()` 的 Python API 触发时才运行。

**证据路径：**  
`lifecycle_supervisor.py:791` → `schedule_epilogue(root, "lifecycle_supervisor")` → 启动 `terminal_packet_epilogue.py` → **无 meter 调用**

#### 缺口 2：长时 Desktop 会话中无定期刷新触发器

`stale_after_s = 7200`（2小时）。Desktop 会话若无子代理活动，则无任何事件触发 `refresh_meter()`：

- 没有定时器/周期性 hook 调用 meter refresh
- `SubagentStart` 不触发 meter
- 只有 `SubagentStop` / `Stop` / `SessionStart` 触发

**场景：** 根会话持续运行超过 2 小时（规划、等待、人工审查），无子代理启停事件 → 报告年龄超过 `stale_after_s=7200` → `read_fresh_report()` 将报告标注为 `STALE` → `root_turn_governor` 的 `meter_status()` 返回 `"STALE"` → `evaluate()` 中进入 `fail_closed` 分支，拒绝非计划态工具调用。

#### 缺口 3：`model_token_share.py`（v1）与 `model_token_share_v2.py` 双轨共存，刷新触发非统一

- `model_token_share_bridge.py` 统一了两者的扫描路径，但 `root_turn_governor.py` 读取的是 v2 报告路径 (`data/usage/model_token_share_v2.json`)
- v1 独立的 `main()` 入口（直接执行时）**不更新** v2 报告；仅 bridge 同时更新两者
- 若某个触发点直接调用 v1 而非 bridge，v2 报告保持陈旧

### 已确认正常工作的路径（非假设）

| 路径 | 触发来源 | 是否刷新 meter | 证据位置 |
|------|---------|--------------|---------|
| Desktop 子代理终止 | `SubagentStop` hook | ✅ 是 | `subagent_lifecycle.py:809` |
| Desktop 会话启动 | `SessionStart` hook | ✅ 是 | `subagent_lifecycle.py:809` |
| Desktop 根会话关闭 | `Stop` hook | ✅ 是 | `subagent_lifecycle.py:809` |
| 完整 epilogue | `orchestration_epilogue.run_epilogue()` | ✅ 是 | `orchestration_epilogue.py:101` |
| Headless 终止事务 | `terminal_packet_epilogue.run()` | ❌ **否** | `terminal_packet_epilogue.py`（无 meter 调用） |
| 长时 Desktop 无事件 | （无触发器） | ❌ **否** | 无定时 hook，仅事件驱动 |

### 潜在测试方案（仅建议，不执行）

1. **headless 缺口验证：** 模拟一个 headless 包完成（`state=completed`），确认 `terminal_packet_epilogue.py` 运行后 `data/usage/model_token_share_v2.json` 的 `generated_ts` 是否更新。预期：不更新（缺口已存在）。

2. **stale 报告触发验证：** 将 `data/usage/model_token_share_v2.json` 中的 `generated_ts` 设为 `now - 7300` 后调用 `root_turn_governor.py status`，应返回 `meter_status: STALE`，然后验证 governor 是否对非计划态工具调用发出 deny。

3. **长会话 stale 路径验证：** 在无子代理活动的 Desktop 会话中，等待超过 `stale_after_s=7200` 后观察 `read_fresh_report()` 是否自动标注 STALE，以及是否导致误判 block。

---

**结论：** headless 完成路径（`terminal_packet_epilogue.py`）**不刷新 meter**，而长时 Desktop 会话依赖事件驱动而无定期兜底，两者均为已证实的生命周期缺口，而非假设。正常工作的路径均通过 `subagent_lifecycle.py` 或完整 `orchestration_epilogue.py` 覆盖。
