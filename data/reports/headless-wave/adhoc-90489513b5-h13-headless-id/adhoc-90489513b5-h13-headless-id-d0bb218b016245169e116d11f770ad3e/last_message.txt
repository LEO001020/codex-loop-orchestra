## Audit Report: Path-Based `task_key` Idempotency Risk

### 1. The mechanism under audit

`task_key` in `harness/headless_wave.py` (line 269–271):

```python
def task_key(manifest: Path, task_id: str) -> str:
    digest = hashlib.sha256(str(manifest.resolve()).encode("utf-8")).hexdigest()[:10]
    return f"adhoc-{digest}-{task_id}"[:96]
```

The `packet_id` that serves as the primary deduplication key in `exec_roster.json` is `adhoc-{10-char path digest}-{task_id}`. This digest is computed exclusively from the **resolved filesystem path** of the manifest file, not from its content.

---

### 2. Idempotency risk characterization

**How the guard works:** When `headless_wave.py` is run against a manifest whose tasks already have roster entries in `exec_roster.json`, the code checks `prior.get("state")` for `"completed"`, `"running"`, or `"starting"` and returns `already_completed` / `already_active` without re-spawning. This guard is keyed entirely on `packet_id = task_key(manifest_path, task_id)`.

**The risk:** If the same `packet_id` is produced for two logically distinct tasks, the guard will wrongly suppress a new spawn — treating the new task as already-done when in fact a different task ran. This can happen in two ways:

| Scenario | Risk level | Condition |
|---|---|---|
| **Manifest file moved/renamed** | Medium | Renamed manifest → different digest → orphaned roster entries, new agents spawn as fresh (no false guard — but history lost) |
| **Manifest file overwritten in place** | **HIGH** | Same path, different content → **same digest, same task IDs** → second run sees all tasks as `already_completed` even though prompts changed |
| **Same `task_id` reused across two manifests at different paths** | Low | Different paths → different digests → no collision |
| **task_id truncation to 96 chars** | Negligible | `adhoc-{10}-{task_id}` at 96 chars only triggers for task IDs > 85 chars, which is prevented by the `TASK_ID` regex (`{0,95}` total) |

**The critical case** is in-place manifest overwrite. If an operator modifies `root_non_ipybox_audit_headless_20260814.json` at its existing path and re-runs the wave, the guard will fire `already_completed` for every task that ran in the prior wave — including any that should be re-run with new prompts. The `manifest_id` field in the JSON (which does change across revisions: `root-non-ipybox-audit-headless-20260814-r2`) is never consulted by `task_key` and provides no protection.

---

### 3. Does this risk block the current fixed-path wave?

**No.** The current wave is not blocked by this risk. Here is the evidence:

1. **Single manifest, one generation.** The manifest file `root_non_ipybox_audit_headless_20260814.json` exists at exactly one path. The exec_roster contains exactly one generation of entries for each `h01`–`h30` task under digest `90489513b5`. There is no evidence of a prior wave using the same file path with different content.

2. **The r3 refill is a separate file path.** `root_non_ipybox_audit_headless_refill_20260814_r3.json` resolves to a different path → different digest → no `packet_id` collision.

3. **`task_key` is stable for this wave.** The manifest file is not being mutated during the wave. All 30 `adhoc-90489513b5-h*` entries were spawned from the same resolved path, and their `already_completed` / `already_active` guards will correctly suppress re-spawns for this run.

4. **The idempotency guard is functioning correctly.** Tasks that completed early (h01–h12, etc.) are protected from accidental re-spawn. Running tasks (h13 = this task, currently `state: "running"`) are correctly guarded as `already_active`.

### 4. Content-based migration: compatibility and design

A compatible content-based `task_key` would hash prompt content (or `manifest_id`) instead of or in addition to the path, providing collision resistance against in-place overwrites.

**Compatible design (no-op if manifest_id is stable):**

```python
def task_key(manifest: Path, task_id: str, manifest_id: str | None = None) -> str:
    if manifest_id:
        # Content-anchored: changes when manifest_id changes
        anchor = manifest_id
    else:
        # Legacy fallback: path-anchored
        anchor = str(manifest.resolve())
    digest = hashlib.sha256(anchor.encode("utf-8")).hexdigest()[:10]
    return f"adhoc-{digest}-{task_id}"[:96]
```

Since the current manifest already carries `manifest_id: "root-non-ipybox-audit-headless-20260814-r2"` at the top level, and each task already carries it as a per-task field (line in manifest: `"manifest_id": "root-non-ipybox-audit-headless-20260814-r2"`), the `manifest_id` string is available at `build_commands` call time (via `task["manifest_id"]`).

**Migration compatibility with existing roster:** Changing the hash input would produce a different `90489513b5`-style digest for all existing entries. Any tasks already in the roster under the old path-digest would be orphaned (not visible to the guard). This is safe for new waves but means the migration cannot be applied mid-wave without either:
- Accepting that completed entries lose their guard (re-run risk), or
- Running a one-time migration script that re-keys roster entries.

**For this wave specifically:** Migration must not be applied mid-wave. The current path-based keys are stable and correct for the `root_non_ipybox_audit_headless_20260814.json` fixed path. Applying the migration now would cause `headless_wave.py` to re-attempt all 30 tasks (new digest → no roster match → treated as fresh).
