## Concurrency Bug Audit

### Root Cause

The roster is keyed by `packet_id` alone, so it's a single-slot register per packet. The sequence is:

```
parent reads  roster[p] → {run_id: r1, state: running}
r1 completes  → roster[p] updated to {run_id: r1, state: terminal}
r2 spawned    → roster[p] overwritten to {run_id: r2, state: running}
parent polls  roster[p] → sees r2/running, never observes r1/terminal
```

This is a classic ABA problem on a keyed mutable register. The parent is waiting for `state=terminal`, but the slot has been recycled and the terminal state was never sampled.

**Root cause in one sentence:** the roster conflates identity with liveness — using `packet_id` as the key means a retry silently overwrites the record the parent is watching, so the terminal transition is invisible.

### Is "read roster[p] and require run_id=r1" correct?

Almost, but not quite. The guard `roster[p].run_id == r1` prevents the parent from mistaking r2's state for r1's, which is the right intuition. But it leaves an uncovered gap: if r1's terminal record is overwritten *before* the parent ever samples it, the condition `roster[p].run_id == r1` becomes permanently false, and the parent will wait forever (or until timeout). The check is necessary but not sufficient on its own.

### Smallest Backwards-Compatible Fix

The fix has two parts: (1) make the terminal record durable for the original watcher, and (2) make the parent's wait predicate robust against missing records.

**Part 1 — Write-once terminal latch per (packet_id, run_id)**

Instead of overwriting the single slot, append terminal events to an immutable log (which likely already exists as `data/events.ndjson`) and add a *separate* terminal-latch map keyed by `(packet_id, run_id)`:

```python
# On worker completion — write-once, never overwritten
terminal_latch[(packet_id, run_id)] = {
    "state": final_state,       # "completed" | "failed" | "cancelled"
    "summary": one_line,
    "report_path": path,
    "ts": utc_now(),
}
# Then, and only then, allow roster[packet_id] to be recycled by r2
roster[packet_id] = {run_id: r2, state: "running"}
```

The latch is append-only: a key is written exactly once, never mutated. This is the single structural change.

**Part 2 — Parent wait loop against the latch, not the roster**

```python
def wait_for_run(packet_id, run_id, timeout_s, poll_interval_s=2):
    deadline = time.monotonic() + timeout_s
    while time.monotonic() < deadline:
        # Primary: check the immutable latch
        record = terminal_latch.get((packet_id, run_id))
        if record is not None:
            return record   # guaranteed to be terminal

        # Secondary: check whether the run was superseded before we could latch it
        # (e.g. a hard-kill that skipped the normal completion path)
        current = roster.get(packet_id)
        if current is not None and current["run_id"] != run_id:
            # r1 was replaced; check events.ndjson as fallback
            record = scan_events_for_terminal(packet_id, run_id)
            if record is not None:
                return record
            # If not in events either, treat as lost — surface as failure
            return {"state": "lost", "run_id": run_id, "packet_id": packet_id}

        time.sleep(poll_interval_s)

    return {"state": "timeout", "run_id": run_id, "packet_id": packet_id}
```

The parent turn stays open, driving this loop for every `(packet_id, run_id)` pair in the wave, and closes only when all return terminal records or a lost/timeout sentinel.

**Explicit detach** is unchanged: the caller simply doesn't invoke `wait_for_run` and returns immediately after the launcher confirms `state=running`. The latch still gets written later; it just isn't consumed by anyone.

### ABA Safety Analysis

| Scenario | Behavior with fix |
|---|---|
| r1 terminates, r2 overwrites roster before parent polls | Latch `(p, r1)` written before roster recycled; parent finds it on next poll |
| r1 terminates, parent polls between latch write and roster overwrite | Parent finds latch immediately |
| r2 terminates before parent even starts polling r1 | Latch `(p, r1)` is still present; latch `(p, r2)` also written; no confusion because key includes run_id |
| r1 hard-killed (latch never written), r2 started | Parent detects `roster[p].run_id != r1`, falls back to events.ndjson, returns "lost" sentinel |
| Retry storm: r1→r2→r3→... all recycle packet_id | Each `(p, rN)` latch is independent; parent waiting on r1 finds exactly r1's terminal record |

The key invariant: **the latch is written before the roster is recycled**. Enforce this with a local lock or by making the terminal-event writer do both operations atomically (write latch, then update roster).

### Timeout and Failure Behavior

- **Timeout:** return `{state: "timeout"}`. The parent wave reports it as a failed run; retry policy in `config/retry_classes.yaml` applies normally.
- **Lost** (hard-kill, no latch, run_id superseded): return `{state: "lost"}`. Treated as failure for retry/DLQ purposes.
- **Both sentinel types** must emit a terminal event to `events.ndjson` so the state machine advances and the slot is freed. The parent must never silently hang.

### Tests to Add

1. **ABA race test:** spawn r1, mark it terminal, overwrite roster with r2 *before* calling `wait_for_run`, assert the result is r1's terminal record (not "timeout" or r2's state).
2. **Concurrent recycle test:** r1 and r2 complete within the same poll interval; assert both `(p, r1)` and `(p, r2)` latches are independently readable.
3. **Hard-kill test:** r1 is killed without writing a latch, r2 starts; assert `wait_for_run(p, r1)` returns `state=lost` within one poll cycle after detecting the run_id mismatch.
4. **Timeout test:** r1 never terminates; assert `wait_for_run` returns `state=timeout` at deadline and emits a terminal event.
5. **Detach test:** caller ignores `wait_for_run`; later reads `terminal_latch[(p, r1)]` directly; assert it is populated correctly and nothing deadlocks.

### What Not to Change

- The roster's `packet_id` key structure — changing it would break all existing consumers.
- The `events.ndjson` schema — it's already the durable log; the latch just adds a fast O(1) lookup layer in front of it.
- The detach interface — the wait is opt-in; the fix only changes what happens when the parent *chooses* to wait.
- Retry dispatch logic — `retry_classes.yaml` continues to own retry decisions; the latch is purely a visibility primitive.
- The one-line summary + report path return contract — `wait_for_run` returns exactly the latch record, which already contains those two fields.
